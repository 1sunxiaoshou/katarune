# 路线图

路线图不绑定日期，按风险和依赖关系推进。第一目标是验证架构闭环，而不是快速堆积功能数量。

## P0 · 项目准备

- [x] 确定项目名称与基本定位。
- [x] 建立独立目录和文档结构。
- [x] 记录首批架构原则与待决策项。
- [x] 制定代码、文档、版本和提交规则。
- [ ] 完成名称的商标、域名及主要分发平台检查。
- [ ] 确定许可证与开源边界。

## P1 · 技术验证

- [x] 验证 Electron 内置 Node.js 运行时及 main/preload/renderer 安全边界。
- [x] 验证并锁定 npm、`electron-vite` 与 `electron-builder` 的兼容版本。
- [x] 锁定 AI SDK 与 assistant-ui 的兼容版本。
- [x] 验证 Electron 开发、`better-sqlite3` 原生模块重建、ASAR 解包与 Windows 打包链路。
- [x] 验证 `better-sqlite3` + Drizzle 稳定版并锁定版本与迁移流程。
- [x] 建立共享的 Zod 契约和最小测试体系。

完成标准：形成一次可复现的技术决策，而不是交付完整产品。

## P2 · 最小垂直闭环

- [x] 接入 assistant-ui 官方成品 Thread 与 shadcn/Tailwind 基础，删除重复基础组件和旧验证页面视觉实现。
- [ ] 显示一个可恢复的聊天线程。
- [x] 建立安全凭据引用、Provider/模型配置持久化、首批 Provider Factory、动态 Registry 与显式连接测试。
- [ ] 通过应用内受信任配置选择一个模型并完成流式回复。
- [ ] 执行一个类型安全、无高权限的本地测试工具。
- [x] 将 assistant-ui / AI SDK 原生格式消息写入 SQLite，并通过关闭、重开恢复测试。
- [ ] 接入一个 TTS Provider 并完成播放。

完成标准：用户能与一个有模型和声音的角色完成一次可恢复的持续会话，并验证完整工具调用链路。

## P3 · 现有能力接入

- [x] 完成供应商、模型和受信任凭据录入的功能链路验证。
- [x] 使用 shadcn 默认组件重新建立设置界面，并保留 Provider、模型与凭据功能链路。
- [ ] 完成默认模型和角色级模型选择。
- [ ] 角色、提示词和资产管理。
- [ ] 按已决定的纵向时间轴视觉语义实现多会话与消息历史，并以独立颜色区分“新建会话”操作。
- [ ] 调查并确定长期记忆的语义模型、生命周期和评估方法。
- [ ] 设计记忆的检索、更新、遗忘以及用户可见、可编辑机制。
- [ ] 分析旧文件记忆并制定数据迁移方案。
- [ ] 调查并确定 VRM 渲染、资产、动作、表情和反馈链路的技术路线。
- [ ] 接入现有 TTS 与 ASR 能力。
- [ ] 制定 ATRI Chat 数据迁移方案。

完成标准：覆盖现有产品的核心使用场景，同时保持新的架构边界。

## P4 · 言奏核心体验

- [ ] 根据技术验证结果接入 VRM 运行时与驱动接口。
- [ ] 统一角色状态、语音与形体表现。
- [ ] 建立可扩展的决策器和行为策略接口。
- [ ] 改善长期记忆的可控性、可见性和可编辑性。
- [ ] 建立工具权限、用户确认和桌面安全策略。
- [ ] 完善角色资产的导入、组织与预览体验。

## P5 · 生态扩展

- [ ] 按实际需求接入 MCP 工具。
- [ ] 评估 ACP/A2A 等外部 Harness 协议。
- [ ] 评估现成文件、脚本执行和长期记忆实现。
- [ ] 建立第三方扩展边界与兼容策略。

P5 不应提前阻塞 P2 和 P3；只有真实需求出现时才引入对应系统。
