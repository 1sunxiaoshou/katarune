# 角色行为与动画系统推进计划

> 状态：讨论中，作为后续 AI 与开发者执行本方向工作的主推进文档。架构边界以[角色行为与动画系统](../02-架构/角色行为与动画系统.md)为准；本页只描述实施顺序、阶段交付物和验收条件。

## 推进目标

用最少的系统代码和三类代表性真实素材，验证“高层行为请求 → 资产解析 → 多通道调度 → 动画混合 → 柔性打断 → 恢复基础状态”的完整链路。在链路稳定以前，不批量制作动作、不建设插件生态，也不继续扩展当前固定四态和固定动作枚举。

核心顺序是：

> 先搭最小系统骨架，立即用真实素材验证；系统和资产共同迭代，但不让任何一侧提前扩大规模。

## 当前基线

当前 Unity Runtime 已具备独立工程、透明桌面窗口、VRM 原子加载、标准化 Control Rig、表情与视线驱动、程序化基础姿态、四种活动循环、固定单次动作、PlayableGraph 混合、Facade 和带 Revision 的权威快照。

这些实现是技术验证基线，不等同于最终行为架构。推进工作应保留模型事务、Facade、快照和 Core / UniVrm / Runtime 分层思想，同时逐步替换固定四态、固定动作枚举和“基础循环 + 全身单次动作”的扩展方式。

## 首轮范围

首轮只验证一个角色、一个基础骨架和三类动作：

1. **基础待机循环**：验证持续底层、循环接缝和恢复姿态。
2. **上半身解释手势**：验证说话、口型、视线和局部身体动作并行。
3. **可中断短表演**：使用十五至三十秒的舞蹈或连续动作，验证全身所有权、安全退出点和自然回待机。

首轮不做：

- 批量动作库和多角色全量兼容。
- 完整动作编辑器或面向用户的素材市场。
- MCP、第三方插件平台和公开逐帧控制接口。
- 生成式人体动作、自动编舞和端到端 AI 骨骼控制。
- 完整移动、攀爬、战斗或游戏式地形交互。
- 为迁就某一个测试模型而在领域层写入 PMX、VRM 或原神特有名称。

## 资产策略与安全边界

### 测试资产分级

- `dev-only`：仅用于本地研究和适配测试，不进入仓库、CI、演示包或安装包。官方公开但禁止再分发或禁止营利的 PMX 模型属于此类。
- `prototype-distributable`：许可允许仓库保存与原型分发，可作为自动化测试和团队共享样片。
- `commercial-ready`：拥有明确商业使用、修改、嵌入和必要分发权，可进入候选产品资产库。

格式转换、重定向、裁剪或修改不会改变授权等级。每项资产必须保存来源、作者、原始许可证、获取日期、允许用途、是否允许修改、是否允许再分发和证明文件；授权不明时按 `dev-only` 处理。

### 获取优先级与数量控制

首轮不建设动作收藏库。同一用途默认只选择一份最合适的素材，并按以下顺序处理：

1. 优先选择免费、授权清楚、质量较高、发布时间或维护状态较新的素材。
2. 免费候选能够满足架构验证时，不再下载同类替代品，也不花预算购买重复动作。
3. 找不到合适免费素材时，再评估低价付费素材；总预算单独确认后才购买。
4. 只有现成素材无法表达所需动作，或后续需要角色专属风格与更高质量时，才使用手机录制、无标记动捕和人工精修。
5. 定制委托属于最终内容阶段，不用于弥补首轮系统尚未验证的问题。

任何外部素材进入 Unity 都仍需完成必要的技术适配，包括骨骼重定向、循环检查、根位移策略、同步点、安全退出点和许可登记。这些属于导入验收，不等于重新创作或美术精修。

### 首轮素材来源

- 模型：可以用官方公开 PMX 作为本机适配样本，但不提交和不打包；同时准备至少一个可分发的标准 Humanoid 测试模型供 CI 和其他开发者使用。
- 待机、移动与短表演：首轮优先从 [Rokoko 免费资源](https://www.rokoko.com/free-resources) 和 Motion Library 的免费动作中选择。官方页面说明其免费动作可用于动画、VFX、游戏和其他 3D 项目，包括商业用途；下载时仍须保存具体资源页、许可文本和获取日期。候选顺序是 everyday idle、walk/run、dance，再从 office 或 TV 类动作中寻找可裁剪的上半身手势。
- 手势补充：Rokoko 免费库缺少合适的解释或反馈动作时，再使用许可清楚的 CC0 / Mixamo 素材，或用手机视频无标记动捕自行制作。
- 短表演不得使用游戏客户端解包动作；音乐、编舞和动作数据分别核对授权，不能因动作文件可用而推定配乐可用。
- 音频：首轮表演可用节拍或无版权测试音频；不得因为动作可用而默认音乐和编舞也获得授权。

### 最小加工流程

```text
获取与授权登记
  → 源文件隔离
  → 骨骼映射与重定向
  → 脚底、重心、抖动和穿模清理
  → 循环、入口、退出与同步标记
  → 通道与兼容性声明
  → Unity 预览验证
  → 打包并生成清单
```

首轮不要求自动化全部加工步骤，但产物必须能由另一位开发者按清单复现。开发期本地受限资产通过外部路径加载，不写入仓库相对路径或机器绝对路径。

## 阶段与交付物

### A · 固化最小领域边界

工作项：

- [x] 将 `BehaviorIntent`、`BehaviorDefinition`、`PerformancePlan` 和 `PerformanceInstance` 的职责落实为 Core 层最小接口或只读数据结构。
- [x] 确认首版六类语义通道：基础身体、全身表演、上半身手势、表情、视线和口型。
- [x] 定义实例生命周期、结束原因及立即取消、安全点退出、暂停、继续和分通道更新的语义。
- [x] 明确调度器是唯一授予和释放通道所有权的组件。

交付物：领域契约、状态转换测试和不变量测试；尚不要求 Electron 接入。

完成条件：领域模型不引用 AI SDK、Electron、UniVRM、PMX、具体 Clip 路径或角色专属骨骼名。

验收记录（2026-08-22）：A 阶段领域契约与纯 Core EditMode 测试已落地。定向测试 20/20、完整 EditMode 回归 110/110 通过；通道策略当前只做无状态冲突判定，尚未建立所有权表或调度器。共享与附加互相兼容是首版最小规则，待 C/D 阶段真实素材验证。

### B · 建立最小资产定义与导入切片

工作项：

- [ ] 定义首版 `BehaviorDefinition` 资产格式，能够声明稳定动作 ID、版本、能力要求、通道申请、入口、循环、同步点、退出段、热更新参数和回退策略。
- [ ] 建立角色 Rig Binding 与通用 Humanoid 动作播放之间的边界，将通用播放职责移出 UniVrm 适配层。
- [ ] 建立最小资产清单与许可证元数据，区分 `dev-only`、可分发原型和商用候选。
- [ ] 对未知字段、缺失 Clip、非法同步点、通道冲突和角色能力不满足给出明确校验错误。

交付物：一个可被 Unity 加载并校验的动作定义、一个可分发测试资产，以及本地受限模型的外部加载说明。

完成条件：替换测试模型或动作文件时，不需要修改调度器代码。

### C · 打通三个素材样片

工作项：

- [ ] 待机循环能连续播放，首尾没有明显跳变，并能作为身体 `GroundState`。
- [ ] 上半身解释手势能通过 Avatar Mask 或等价机制叠加到基础身体，不破坏视线与口型。
- [ ] 短表演声明全身所有权、至少一个安全退出点和一个退出段，完成后自然回到基础待机。
- [ ] 记录每份样片的来源、许可证、骨架、重定向修正、同步点和已知缺陷。

交付物：三份可重复导入的动作样片与对应定义。美术质量只需足够暴露架构问题，不以数量或最终观感作为完成标准。

完成条件：三份素材都通过同一个资产入口加载，不为单个动作增加硬编码枚举或名称分支。

### D · 完成 Unity 调度垂直切片

工作项：

- [ ] 实现请求规范化、资产解析、能力校验、计划编译、通道仲裁、实例创建和终态清理的最短链路。
- [ ] 实现并行、排队、拒绝、立即取消和安全点退出的首版仲裁。
- [ ] 建立可恢复的基础姿态、默认凝视和心境表情；取消动作时只恢复受影响通道。
- [ ] 在调试界面或日志中显示活动实例、阶段、通道所有者、同步点和结束原因。
- [ ] 保留现有 Facade 和 Snapshot 作为外部权威入口，但不再让固定四态拥有全部表现状态。

交付物：可在 Unity 内独立运行的两个验收场景。

完成条件：调度器是唯一通道所有者；所有终态释放资源；重复取消不会产生第二次副作用。

### E · 接入 Electron 协议与 TTS 时钟

工作项：

- [ ] 定义命令、事件和权威快照三类消息；命令与状态不共用一种消息结构。
- [ ] 为请求和运行实例建立独立关联，支持重试去重、迟到事件忽略和断线快照恢复。
- [ ] Unity 只上报已接受、已开始、同步点、退出中、完成、取消和失败等关键事件，不传输逐帧动画状态。
- [ ] 验证 Electron main 生成语音、Unity 作为形体模式唯一播放时钟、renderer 仅作无形体回退的候选链路。
- [ ] 将用户输入规范化为交互事件，不再直接切换一个全局 `Listening` 状态。

交付物：Electron 与 Unity 之间可重连的最小控制链路，以及一段有口型与手势锚点的测试语音。

完成条件：进程重连后 Electron 能通过快照恢复认知；同一语音不会双重播放。

### F · 接入 AI 表达工具和表演目录

工作项：

- [ ] 建立组合表达工具，提交情感、普通手势和注视建议，不解析回复正文中的隐藏格式。
- [ ] 建立表演搜索和显式执行工具，AI 只能从 Unity 报告可用的稳定 ID 中选择命名表演。
- [ ] 工具请求先进入 Electron 意图仲裁器，不直接调用 Unity 动画资源。
- [ ] 验证模型不调用工具、重复调用、调用延迟或当前模型不支持工具时，默认表现仍然正确。
- [ ] 验证明确用户停止与安全策略始终优先于 AI 表达建议。

交付物：一个普通回复加解释手势，以及一次搜索并执行短表演的端到端演示。

完成条件：没有工具调用时聊天与默认形体仍可用；AI 不能指定 Clip、路径、骨骼或逐帧参数。

### G · 扩大资产生产能力

只有 A 至 F 的验收场景稳定后才进入本阶段。

工作项：

- [ ] 依据真实缺陷决定是否制作批量导入、预览、同步点编辑和许可证校验工具。
- [ ] 优先扩充高频待机、倾听反馈、说话手势和情绪过渡，再增加低频长表演。
- [ ] 建立“普通素材自动加工 + 高频素材人工精修 + 招牌内容定制”的成本分层。
- [ ] 评估手机视频动捕、付费视频动捕服务与动画师精修在实际样片上的成本和质量。
- [ ] 当一个表演需要角色专属修正时，使用角色包覆盖，不污染通用行为定义。

完成条件：新增同类动作主要是增加资产和清单，不需要修改调度核心。

## 两个强制验收场景

### 场景一：说话与解释手势

1. Electron 发起一次测试语音与“解释”语义动作。
2. 基础身体持续运行，Unity 启动口型并保持看向用户。
3. 上半身手势在指定词语或语义标记到达 `stroke`。
4. 手势完成并回收，口型继续，其他通道不被清空。
5. 语音结束后角色回到由当前心境决定的默认表现。

通过标准：无全身硬切、无双重音频、无口型与手势明显漂移、终态无通道泄漏。

### 场景二：舞蹈中用户插话

1. 短表演获得全身通道，表情与视线按资产策略继续运行。
2. 用户开始输入时，视线先做可逆的注意反射，舞蹈不被立即清空。
3. 普通附和只产生反馈；普通问题请求最近安全点退出；明确停止立即取消。
4. 安全退出时完成合法过渡并恢复基础身体，随后才启动互斥的新行为。
5. Unity 返回完整的退出阶段与结束原因，Electron 不猜测动画状态。

通过标准：输入不自动触发全局 `Listening`，明确停止可靠生效，安全退出期间新实例不会提前抢占未释放通道。

## 扩张门槛

以下条件全部满足前，不批量制作资产或接入外部 Agent：

- 两个强制场景可以稳定重复执行。
- 至少更换过一次测试模型和一次动作文件，调度器无需修改。
- 所有活动实例在完成、失败和取消后都能释放通道。
- 本地受限素材不会被版本控制、CI 或打包流程收集。
- 调试信息能够解释一次动作为何执行、排队、被拒绝或被打断。
- 至少一次断线重连能通过快照恢复，而不是重放不确定的历史命令。

如果真实素材证明六类通道或当前动作定义不足，应先更新架构文档并补测试，再继续实现；不得通过动作名称特判绕过领域模型。

## 迁移与旧代码清理规则

新旧实现只允许在迁移切片期间短暂并存。一个新组件通过验收并接管职责后，必须在同一阶段完成以下清理，不长期保留“以后可能有用”的兼容代码：

- 使用引用搜索、程序集编译和测试确认旧类型、枚举、入口与资源已无有效调用方。
- 删除被替代的脚本及其 `.meta`，同时清理 asmdef 引用、场景/Prefab 挂载、资源清单、测试和文档入口。
- 检查场景和 Prefab 不存在 Missing Script，运行时没有两个组件同时写同一骨骼、表情或通道。
- 删除只为旧架构保留且没有真实消费者的适配器、Facade 重载、序列化字段和回退分支。
- 保留旧实现时必须在推进文档写明仍由哪个验收场景依赖、何时删除；不能仅以“保险”为理由保留。
- 每次提交只包含一个可验证迁移结果，提交前检查生成物、本地模型、测试输出和无关脏改动没有进入暂存区。

当前四态与预设动作仍是可工作的技术基线，直到 D 阶段的新调度垂直切片实际接管对应职责；A、B 阶段不得为了追求目录整洁提前删除它们。D 阶段接管后，应删除或降级被替代的固定动作枚举、超级状态分支和重复播放入口，不允许两套调度体系长期并行。

## 后续 AI 的执行规则

任何接手续写或实现本计划的 AI 应先读取：

1. 根目录 `AGENTS.md`。
2. [角色行为与动画系统](../02-架构/角色行为与动画系统.md)。
3. 本推进计划。
4. 与任务直接相关的当前代码、锁定依赖和项目级 Skill。

每次只领取一个可独立验收的阶段切片。开始前先检查工作树并保留用户未提交改动；不得以“完成未来架构”为理由重写现有 Unity 工程。完成后运行与风险相称的测试，只在验收证据存在时勾选工作项，并记录实际发现的新边界、风险和未完成事项。

阶段内字段名和实现细节可以调整，但如需改变 Unity 是表演运行时、AI 只提交高层意图、调度器唯一拥有通道、VRM 只是模型适配器或受限资产不分发等边界，必须先回到架构讨论，而不是在代码中隐式改变。
