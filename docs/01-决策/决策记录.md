### D-004 · 使用 AI SDK 与 assistant-ui

- 状态：已决定
- 日期：2026-07-29（修订）
- 决策：AI SDK 承担模型调用、工具调用、流式输出与基础 Agent 循环；assistant-ui 承担聊天交互框架。首批兼容基线锁定为 `ai@7.0.31`、`@ai-sdk/react@4.0.34`、`@assistant-ui/react@0.14.27` 与 `@assistant-ui/react-ai-sdk@1.3.41`。
- 理由：这组版本满足 React 19、Zod 4 和 Electron 43 内置 Node.js 的要求；确定性 mock model 已验证 Provider Registry、`ToolLoopAgent` 与流式输出，assistant-ui 的 AI SDK runtime 已在 sandboxed renderer 中成功挂载。真实 Provider、工具聚合与 Electron 本地消息流已经按 [D-026](#d-026--electron-本地-ai-消息流) 和 [D-027](#d-027--统一工具平面) 接通。
- 代价：AI SDK 7 已是 ESM-only，要求 Node.js 22 以上；assistant-ui 尚未到 1.0，升级必须作为独立任务验证。官方默认传输面向 HTTP API 路由，言奏因此需要维护 D-026 所述的 Electron `MessageChannel` 薄适配并跟随 AI SDK UI message stream 与 assistant-ui ChatTransport 契约演进。
- 复查条件：锁定版本出现无法规避的安全或兼容问题，Electron 内置 Node.js 不再满足要求，或 assistant-ui 无法可靠适配言奏的本地流传输与持久化边界。

### D-006 · 复用优先

- 状态：已决定
- 决策：非核心能力优先选择成熟库、Provider、协议或外部 Harness。框架已经提供稳定类型、消息格式、协议、生命周期、编码器或持久化 adapter 时，以其原生抽象作为单一来源；言奏只实现连接 SQLite、Electron IPC、安全边界和产品领域语义所需的薄适配，不建立镜像模型、重复转换层或没有真实迁移对象的兼容层。
- 理由：减少重复实现、格式漂移和升级时的双向转换成本，让框架自身承担其公开契约的演进。
- 代价：本地数据需要保存框架要求的格式标识或版本信息；框架升级仍需通过 adapter 测试验证既有数据可以读取。
- 例外：只有框架原生结构无法表达言奏的核心语义、安全要求或用户可控性，且已通过实际用例证明时，才引入独立领域模型或转换层。

### D-007 · 项目级 Agent Skills

- 状态：已决定
- 日期：2026-08-16（修订）
- 决策：AI SDK、assistant-ui 与按当前任务需要选择的 Unity 官方 Skills 作为项目级开发配置存放在 `.agents/skills/`，并通过 `skills-lock.json` 保持来源一致。Unity Skills 只从 `Unity-Technologies/skills` 单项安装，不批量预装，也不得安装到用户全局目录。讨论、规划、实现或评审 Unity 功能前，必须先确认项目锁定的 Editor 与 Package 版本，再查询对应的 Unity 官方 Manual、Scripting API 或包文档；UniVRM 等第三方能力同时核对其官方上游资料和项目锁定源码。根目录 `AGENTS.md` 负责规定 Skill 路由、版本核实、安装、升级和安全规则。
- 理由：快速迭代的外部框架容易因编码 Agent 的过时知识产生错误；项目级 Skills 能在不同电脑和不同兼容 Agent 之间复用维护者提供的过程知识。
- 代价：Skill 安装和更新也属于供应链变更，必须经过来源、风险提示、文件 diff 与锁文件审查，不能自动追随最新版本；Skill 只能提供工作流约束，不能替代与项目准确版本对应的官方资料和实际测试。

### D-008 · 工程变更规范

- 状态：已决定
- 日期：2026-07-29（修订）
- 决策：项目统一采用严格 TypeScript 边界、语义化版本与 Conventional Commits；代码、文档、依赖和验证要求以[工程规范](../04-开发/工程规范.md)为准。自动化测试锁定为 `vitest@4.1.10`，根级 `npm test` 作为非交互统一入口；跨进程数据使用共享 Zod Schema 校验并由其推导 TypeScript 类型。格式化与 Lint 工具在出现足够代码规模后独立选择。
- 理由：先固定跨工具、跨运行时都成立的质量与协作约束，同时避免在技术验证前用脚手架反向锁定待决策项。
- 代价：Node 单元测试不替代真实 Electron 边界；仓库因此分别维护不可见窗口 UI、Electron ABI 数据库、`safeStorage` 与 Windows unpacked 产物验证。安装器、签名和更新行为仍未覆盖；格式化与 Lint 暂时仍依赖人工检查和 TypeScript 编译器约束。
- 复查条件：运行时、仓库组织或发布模型发生根本变化。

### D-010 · TypeScript 服务运行时

- 状态：已决定
- 日期：2026-07-19
- 决策：使用 Electron 内置的 Node.js 主进程作为可信 TypeScript Harness 运行时；第一阶段不引入 Bun 或独立的 Node.js sidecar。
- 理由：AI SDK、数据库和桌面生态可以直接运行在 Electron 的 Node.js 边界内，降低进程编排、IPC 与打包成本。
- 代价：接受 Electron 内置 Chromium 与 Node.js 带来的安装体积和资源占用；耗时或高风险任务仍可能需要 Electron utility process 或外部 Worker。
- 复查条件：关键原生依赖无法在 Electron 中可靠运行，或资源占用无法满足目标体验。

### D-011 · 桌面容器

- 状态：已决定
- 日期：2026-07-19
- 决策：桌面容器采用 Electron。React 与 VRM 运行在 sandboxed renderer；密钥、AI SDK、数据库、文件系统和高权限工具留在 main process，通过 preload 暴露最小、类型安全的 IPC 接口。
- 理由：相较 Tauri 加 Node.js sidecar，Electron 与 Node.js/TypeScript 生态直接结合，能显著降低开发、调试和打包链路的复杂度。
- 代价：Windows x64 的 Electron 运行时本身带来约百兆级下载体积和数百兆磁盘占用，需要持续控制生产依赖与静态资产体积。
- 复查条件：实际启动、内存、安装体积或安全边界验证不达标。

### D-012 · 持久化方案

- 状态：已决定
- 日期：2026-07-19
- 决策：本地持久化采用 SQLite，驱动锁定为 `better-sqlite3@12.11.1`，Schema 与类型安全查询锁定为 Drizzle ORM 稳定版 `drizzle-orm@0.45.2`，迁移生成工具锁定为 `drizzle-kit@0.31.10`。Schema 位于 main process；迁移 SQL 生成后纳入版本控制，并由 main process 在打开窗口前对用户数据目录中的数据库执行。会话元数据沿用 assistant-ui 的 `RemoteThreadListAdapter` 语义；消息通过 `ThreadHistoryAdapter.withFormat` 保存框架提供的 `id`、`parent_id`、`format` 与编码后 `content`，不复制或解析 AI SDK 的消息模型。
- 理由：该组合符合本地优先、事务可靠、应用版本演进和 TypeScript 开发体验要求；Electron 的构建与分发工具链可处理原生模块重建，避免引入独立数据库服务。
- 代价：Electron 升级时必须验证并重建原生模块；同步查询不得在 main process 中执行长耗时工作；标准 SQLite 文件默认不提供静态加密；`drizzle-kit` 当前开发依赖链存在 moderate 级 esbuild 审计提示，虽然不进入生产依赖，仍需在后续稳定版本中复查。
- 复查条件：原生模块分发不可靠、需要近期云同步，或明确要求数据库级静态加密而现有方案无法满足。

### D-014 · 模型运行时管理

- 状态：已决定
- 日期：2026-07-19
- 决策：模型运行时统一使用 AI SDK Provider Registry。官方供应商优先使用对应的 AI SDK Provider；自定义兼容端点使用 `@ai-sdk/openai-compatible`；没有官方 AI SDK Provider、但已确定接入的供应商只实现对应 AI SDK 模型接口的薄 Provider。言奏只实现用户配置到 Provider 实例与 Registry 的薄适配层，不自研通用模型协议或重复的模型注册中心。供应商配置使用 `provider_configs`：唯一且稳定的内部主键 `id` 同时负责数据库关联并作为 AI SDK Registry 的 `providerId`，`provider_type` 作为受控判别字段选择 Provider factory；其余字段为 `display_name`、可空 `base_url`、可空 `credential_ref`、可空非敏感 `settings`、`enabled`、`created_at` 与 `updated_at`。`provider_type` 的唯一来源是共享常量 `PROVIDER_TYPES`；运行时使用官方 factory 或项目内薄 Provider 构建实例，并在配置变化后重建 AI SDK Registry。不使用容易与 assistant-ui 混淆的 `adapter` 命名。Provider 身份单一来源由 D-023 修订确认。
- 理由：AI SDK 已提供多 Provider 注册、统一模型 ID、模型别名、默认设置、可用模型限制、middleware 与 fallback 等运行时模型管理能力。
- 代价：不同供应商的能力、选项和模型发现接口并不完全一致；产品层仍需处理配置持久化、密钥安全、连接测试和无法自动发现模型列表的端点。以 UUID `id` 组成的内部 Registry 模型标识不适合直接展示，日志和界面必须改用 `display_name` 与 `provider_type`；API Key 与 Token 不进入该表，`credential_ref` 只引用操作系统安全存储。
- 复查条件：目标供应商无法通过官方 Provider、OpenAI-compatible Provider 或 AI SDK 自定义 Provider 接入。

### D-015 · Electron 工程工具链与打包方式

- 状态：已决定
- 日期：2026-07-19
- 决策：包管理器锁定为 `npm@11.8.0`；桌面运行时锁定为 `electron@43.1.1`；开发与代码构建锁定为 `electron-vite@5.0.0` 与兼容的 `vite@7.3.6`；可分发产物锁定为 `electron-builder@26.15.3`。当前已验证 Windows x64 unpacked 与无签名 NSIS 产物生成；首版安装目标、签名阶段与更新边界由 [D-032](#d-032--首版桌面分发安装卸载与更新策略) 继续约束。
- 理由：项目当前是单应用，npm 能减少依赖布局和原生模块工具链的额外变量；`electron-vite` 以单一配置覆盖 main、preload 与 renderer，并适合 React 开发；`electron-builder` 提供 Windows 安装包、签名、更新和 Electron 原生依赖重建能力，能覆盖 `better-sqlite3` 的分发需求。
- 代价：`electron-vite` 与 `electron-builder` 是社区工具，不属于 Electron 官方支持的 Forge 路线；Electron 42 起不再通过安装脚本下载运行时，当前开发命令需显式确保运行时已安装；排除原生依赖构建中间文件和 renderer 依赖副本后，当前 Windows x64 unpacked 产物约 382.96 MiB，无签名 NSIS 安装器约 111.30 MiB。安装后的实际占用与跨版本差分下载量仍需在分发候选版中测量。
- 复查条件：工具间版本兼容性不稳定，`better-sqlite3` 无法可靠重建或分发，Windows 签名/更新能力不满足需求，或项目演进为需要 pnpm workspace 的多包仓库。

### D-016 · 角色级 Memory Wiki

- 状态：已决定
- 日期：2026-08-03
- 决策：长期记忆采用由 main process 托管的角色级 Markdown Wiki；`characters` 继续作为角色与 Agent 的唯一实体，每个角色以稳定 ID 绑定 `userData/memory/agents/<character-id>/`，其中 `index.md` 与 `profile.md` 是每轮受限注入的核心页，`topics/`、`relationships/` 与 `timeline/` 保存按需检索的扩展页。Markdown 是长期记忆正文的事实来源，SQLite 继续只负责角色、会话、模型配置和产品设置，不建立 `memories` 镜像表。
- 工具与上下文：main process 为每次已校验的角色聊天创建闭包绑定的 `wiki_search`、`wiki_get` 与受限 Codex 补丁语义 `wiki_apply_patch`；模型输入不包含角色 ID，工具默认无需审批。核心页带 SHA-256 revision 注入，扩展页使用受限本地词法检索；写入必须携带基于当前内容的 revision，并通过跨进程角色锁、临时文件和原子替换避免静默覆盖或部分写入。
- 安全与生命周期：工具只接受限定目录中的 UTF-8 Markdown，相对路径必须通过 Windows 路径、保留名、符号链接、Junction/Reparse Point、页数与容量校验。角色删除先暂存对应 Wiki，再执行数据库删除；数据库失败时恢复，成功后清理。renderer 不获得文件系统或绝对路径访问能力，聊天中只显示不泄露正文与补丁的紧凑工具状态。
- 记忆策略：角色可自动记录明确、稳定且未来有用的用户事实、偏好、关系、承诺和纠正；写入前应检索并更新既有事实，用户要求忘记时删除对应内容。首版不验证写入依据，不保存修订历史，因此错误但已提交的内容只能通过后续补丁纠正；密码、API Key、Token、临时闲聊和未经确认的推断不得进入记忆。
- 非目标：首版不实现独立记忆管理页、SQLite FTS、Embedding/向量检索、外部 Vault、旧 ATRI Chat 记忆迁移、完整审计历史、恢复 UI、静态加密或 Provider 专属记忆工具。
- 理由：文件 Wiki 与角色的长期、可演进知识结构一致，能复用模型熟悉的搜索、局部读取和补丁工作流，同时保持本地优先、跨 Provider、用户可检查以及 main process 的权限边界。核心页加按需检索可以限制每轮上下文成本，不需要引入外部记忆服务或第二套 Agent Runtime。
- 代价：词法检索对同义表达的召回弱于语义检索；Markdown 与 SQLite 形成两个用途明确的本地事实来源；无历史版本意味着误写不可直接回滚；自动写入质量依赖模型遵守记忆提示策略。
- 复查条件：真实对话评估证明词法召回不足，用户需要直接浏览、编辑、恢复或同步记忆，多个应用实例的文件锁无法满足一致性，或需要跨角色共享用户画像。

### D-017 · 用户供应商配置

- 状态：已决定
- 日期：2026-07-19
- 决策：非敏感供应商配置通过 `provider_configs` 持久化，main process 提供经过共享 Zod 契约校验的创建、读取、更新和删除能力；内部 `id` 由系统生成并保持稳定，`provider_type` 创建后保持稳定。当前 `provider_type` 只允许 `gateway`、`openai-compatible`、`openai`、`anthropic`、`google`、`fish-audio`、`deepseek`、`xai`、`moonshotai` 与 `alibaba`。除 Fish Audio 外的对应官方 Provider 包已按与 AI SDK 7 兼容的稳定版本锁定；Fish Audio 在没有官方 AI SDK Provider 的情况下实现最小 `SpeechModelV4`。数据库配置只有在启用、凭据可解析且 factory 创建成功后才进入 Runtime Registry。
- 理由：AI SDK 已提供具体厂商 Provider、OpenAI-compatible Provider、可扩展 Provider 接口与 Provider Registry，但 Registry 不会根据数据库字符串自动创建实例。言奏只需保存用户配置，并将受控 `provider_type` 映射到官方 factory 或单一能力的薄 Provider。
- 代价：部分供应商不提供模型发现接口或不返回能力类别；角色与应用默认模型选择器只展示已启用供应商下已启用的语言模型。数据库中存在配置不等于该配置已可调用。
- 复查条件：AI SDK 提供可直接承担本地配置、凭据和动态 Provider 生命周期的稳定实现，或当前字段无法表达已确定要支持的官方 Provider 配置。

### D-018 · 系统安全凭据存储

- 状态：已决定
- 日期：2026-07-19
- 决策：API Key 与 Token 使用 Electron 43 的异步 `safeStorage` API 加密，密文按不透明 UUID 引用保存在用户数据目录的独立 `credentials/` 中；SQLite 的 `provider_configs` 只保存 `credential_ref`。凭据仓库只存在于 main process；preload 只暴露替换和清除凭据的写入式操作，不暴露读取、列举 secret 或由 renderer 指定 `credential_ref` 的能力。操作系统加密不可用时失败关闭，不降级为明文。
- 理由：`safeStorage` 复用 Windows DPAPI，并由 Electron 负责异步初始化、临时不可用和密钥轮换信号；独立密文文件可保持数据库不接触 secret，同时无需增加原生凭据依赖。
- 代价：Windows DPAPI 防护边界是当前登录用户，不能抵御同一用户权限下的恶意进程；renderer 中输入的 secret 在提交前仍短暂存在于受控表单状态，提交成功后必须立即清空。开发用真实测试密钥只允许放入被 Git 忽略的 `.env.local`，且必须使用专用测试变量显式读取。
- 复查条件：目标平台需要更强的硬件密钥保护、系统凭据管理器条目共享，或 `safeStorage` 的平台安全语义不满足要求。

### D-019 · 最小模型配置与连接验证

- 状态：已决定
- 日期：2026-07-30（修订）
- 决策：`model_configs` 保存此前确认的字段，并对 `(provider_config_id, model_id)` 建立唯一约束；每个供应商模型只保存一个可编辑的 AI SDK Registry `model_type`。模型发现优先调用供应商端点获取实际模型 ID；Gateway 类型使用其 `getAvailableModels()` 返回值，其他供应商类型采用 LiteLLM 模型目录的 `supported_endpoints` / `mode`，不采用普通供应商列表中的类型字段或方法声明。未填写 Base URL 的预设供应商直接按 `provider_type + model_id` 精确匹配。填写自定义 Base URL 时，先按规范化后的地址精确匹配已知目录供应商；预设供应商未命中该供应商模型时再按用户选择的 `provider_type` 匹配，最后才按裸 `model_id` 搜索整个目录。`openai-compatible` 没有预设供应商回退，地址未命中后直接进入裸 ID 查询。裸 ID 的全部目录命中只有得到同一类型时才自动采用；全链路无记录或类型冲突时保持未知，并在添加时强制用户选择一个类型。供应商端点不支持或暂时失败时，仅对识别为官方地址的 Base URL 使用随应用提交的 LiteLLM 完整 JSON 快照回退，未知自定义地址不得用供应商完整目录冒充代理的实际库存；本地快照未命中时再查询 LiteLLM 上游 JSON，并在单次 main process 生命周期内复用请求结果。随应用分发的目录为 `src/main/ai/litellm-models.json`，来源和获取时间记录在同目录的 `litellm-models.meta.json`；二者只通过 `npm run models:snapshot` 显式更新，普通安装、启动和构建不联网刷新。当前发现契约只返回模型 ID、显示名称、单一类型及类型来源，不解析或展示目录中的能力字段；完整原始快照继续保留，后续出现明确产品需求时再扩展。发现结果不自动写入 SQLite。`provider_configs.settings` 与 `model_configs.settings` 的 IPC 外层只约束为不超过 64 KiB 的 JSON Object 或 `null`；写入与调用前必须再通过对应 Provider Definition 和 Model Capability Adapter 的 Zod Schema。语言模型沿用当前受控 settings，当前 SpeechModel settings 只接受 `null`，尚未实现调用的类别也只接受 `null`。已持久化但 Adapter 缺失或 Schema 失效的记录保持原样并标记为不可用。连接测试委托给已注册的 Capability Adapter；未实现调用的类别仍可登记和区分。
- 理由：LiteLLM 已维护跨供应商的主要 API 类型与兼容端点，直接同步其 MIT 许可数据文件可避免言奏维护第二套模型分类规则，也不引入 Python 或运行时 SDK。当前快照中同一规范化模型 ID 跨供应商出现时未发现类型冲突，但实现仍要求唯一结果，不把目录偶然顺序当作结论。一个模型保存一个类别符合现有目录事实，也避免把 `/responses` 与 `/chat/completions` 等同类 HTTP 路径误建成多条模型配置。暂不输出未被产品消费的能力数据，可保持 IPC、渲染状态与测试边界最小。
- 代价：不同供应商的发现端点仍需薄适配；未知或反向代理地址不会通过模糊匹配获取目录信息。完整快照增加约 1.7 MiB 源码体积，并需通过 `npm run models:snapshot` 显式更新。AI SDK 没有跨供应商统一的无费用 ping，现有语言模型连接测试仍可能产生少量费用。
- 复查条件：AI SDK 提供统一连接探测，或后续模型发现与角色选择需求证明当前边界不足。

### D-023 · Provider 身份使用单一来源

- 状态：已决定
- 日期：2026-07-22
- 背景：`provider_configs.id` 与 `registry_id` 都被定义为唯一、稳定且创建后不可变的供应商实例身份。锁定的 `ai@7.0.31` Provider Registry 只把注册对象的字符串键作为 `providerId`，并用它查找 Provider 实例；它不要求该键具有人类可读语义。
- 决策：删除 `registry_id`。`provider_configs.id` 同时作为 SQLite 主键、模型外键目标和 AI SDK Registry 的 Provider Key；`provider_type` 只负责选择 Provider factory。运行时组合标识 `${providerConfig.id}:${modelConfig.modelId}` 仅供内部解析，不在产品界面中展示。
- 理由：保留两个同样唯一且不可变的身份会增加 Schema、校验、迁移、表单和运行时映射成本，却没有已经确认的外部引用需求。复用 `id` 仍然允许同一 `provider_type` 存在多个账号或端点，并符合身份单一来源与不提前建立兼容层的原则。
- 代价：Registry 内部标识由 UUID 组成，不适合人工阅读；诊断信息应同时记录供应商显示名称与类型。已有数据库需要迁移删除冗余列和唯一索引，但模型外键与凭据引用不变。
- 复查条件：未来出现需要跨数据库导入导出、用户手写配置或外部协议稳定引用的人类可读 Provider 命名空间。

### D-024 · 角色即 Agent、活动角色与会话绑定

- 状态：已决定
- 日期：2026-07-31（修订）
- 决策：`characters` 是角色与 Agent 的唯一实体，不建立平行 `agents` 表。角色保留稳定 ID、名称、立绘资产外键、卡片专用取景焦点 `portrait_focus_x/y`、`portrait_zoom`、模型软引用、系统提示词和时间戳；取景范围分别为 `0–1`、`0–1` 与 `1–3`，旧记录默认顶部居中 `0.5 / 0 / 1`。空库从校验后的默认角色资源初始化，既有数据库始终优先。单行 `app_state` 以受限外键保存活动角色。每个 `threads.character_id` 以 `ON DELETE RESTRICT` 外键固定绑定创建时的角色，普通切换不得迁移旧线程；线程查询、初始化、读取与修改均在角色范围内执行。`activeCharacter` 只表示当前可见和可操作的角色；renderer 为窗口生命周期内访问过的每个角色保留独立 assistant-ui Runtime，切换角色不取消未结束运行，切回时恢复该角色原先选中的线程和运行状态，首次访问才从空白新对话开始。
- 交互：聊天页弹性侧栏顶部和角色页列表复用同一个 `CharacterCard` DOM、排版、选中态、取景参数、名称、拼音和星标；卡片下方只展示活动角色的普通会话，设置与会话显隐入口固定在侧栏底部。角色页初始选中活动角色，列表点击只改变候选角色；返回聊天或前往设置时提交候选角色，失败则停留并显示错误。角色列表按 `createdAt + id` 倒序展示，标题栏的图标按钮在列表顶部插入 renderer 草稿并聚焦名称；离开草稿时，无改动的默认草稿直接丢弃，有名称、模型或提示词改动时才通过 main process 生成正式 ID 并持久化。角色页的“导入立绘 / 编辑立绘”是卡片取景主入口，右键菜单只显示“添加立绘 / 调整立绘”快捷项；编辑器以同一组参数实时预览普通与紧凑卡片，大幅完整立绘不裁切。换图、位置和缩放只在保存时整体生效，取消不修改角色。删除需通过通用确认框，唯一角色不可删除，确认后先取消该角色全部运行，再在事务内删除角色的全部线程和消息，活动角色切换到相邻角色。提交新活动角色后，聊天页显示目标角色 Runtime 的星轨与当前线程；后台角色继续生成和持久化，但不渲染聊天 DOM。最终评审参考为 [`character-card-entry-concept-v2.png`](../assets/character-card-entry-concept-v2.png)。角色手动排序或拖拽调整顺序仍不在本次范围。
- 理由：角色本身已聚合模型、提示词和后续记忆、语音、形体能力，再建立 Agent 镜像会制造身份同步问题。固定线程归属可以保持上下文和角色语义稳定；独立且持续挂载的角色 Runtime 则避免切换 UI 时丢失流和 history adapter 的完成持久化。
- 代价：被删除或禁用的模型软引用会继续保留并由角色页显示不可用状态；访问过的角色会在窗口关闭前保留一套轻量 Runtime 与流状态，当前不做 LRU 回收或后台状态标记。角色删除不可恢复，孤立立绘资产暂不自动清理。默认配置更新只影响全新数据库，跳跃升级中的无角色旧线程由迁移内冻结的星澜快照引导。
- 复查条件：角色导入导出、共享会话、多角色协作或一个角色包含多个可切换 Agent 配置进入实现范围。

### D-025 · 通用资产注册表与托管协议

- 状态：已决定
- 日期：2026-07-31（修订）
- 决策：SQLite `assets` 表登记稳定 UUID、类别 `character_portrait/character_vrm/chat_attachment`、唯一 `storage_key`、`ready/missing` 状态、MIME、字节数、SHA-256、原始文件名和时间戳；迁移前资产统一回填为 `character_portrait`，`ready` 记录必须具备完整元数据。三类物理文件均以无扩展名的不可变对象保存到用户数据目录 `assets/<uuid>`，替换文件生成新资产 ID。立绘由 main process 校验 PNG/JPEG/WebP 扩展名、文件签名与 10 MiB 上限，经暂存和角色事务提交；聊天附件允许未知格式，直接通过临时文件与原子 rename 复制进对象库。`character_vrm` 本期只固定存储类别，不开放导入、校验、预览或运行时。
- 协议：renderer 使用 `katarune-asset://asset/<uuid>` 消费正式资产，并仅以 `katarune-asset://staged/<uuid>` 预览 main process 当前已登记的暂存项；后者返回 `no-store`，未知或遗留 UUID 一律拒绝。scheme 在 Electron `ready` 前声明为 secure、standard、fetch、CORS 和 stream capable，`ready` 后由 `protocol.handle()` 提供 GET/HEAD。处理器严格校验 UUID、资产状态和托管目录边界，正式资产返回登记 MIME 与 immutable cache，不启用 `bypassCSP`，也不暴露 storage key 或物理路径。旧 `character-assets/<uuid>.<ext>` 在启动时精确搬迁并补齐哈希；文件缺失时保留 `missing` 记录和 UI 占位。
- 理由：立绘只是首个文件资产，注册元数据、物理存储和消费 URL 应独立于角色字段；协议 URL 避免 Base64 IPC 和绝对路径泄露，并为后续 VRM、音频等资产保留统一边界。
- 代价：数据库与文件系统之间仍需启动期对账；聊天附件已有消息引用驱动的回收，成功替换后的孤立立绘仍不自动回收。
- 复查条件：引入大体积流媒体、远程同步、内容寻址去重、资产版本树或用户可见资产库。

### D-026 · Electron 本地 AI 消息流

- 状态：已决定
- 日期：2026-07-27
- 决策：assistant-ui 继续通过 `useChatRuntime` 与 `AssistantChatTransport` 使用 AI SDK 原生 UI message stream；Electron renderer 不运行 Provider Registry，也不引入本地 HTTP 服务。每个访问过的角色持有独立 `RemoteThreadListRuntime`，其中每个线程 Runtime 持有独立 `AssistantChatTransport`，preload 再为每次模型运行建立独立 `MessageChannel`；renderer 以 pull/cancel 控制帧请求数据或取消，main process 每次 pull 只读取并返回一个 AI SDK SSE 字节块。main process 根据线程绑定读取角色，并以角色的模型软引用和系统提示词创建无工具 `ToolLoopAgent`；renderer 提交的模型、system、tools 和调用设置均不作为可信配置。main 登记活动流的窗口、角色与线程归属，在线程或角色删除前定向取消对应运行。assistant-ui 首次运行完成后调用 `generateTitle`，main 使用同一角色绑定模型和系统提示词创建独立、无工具、短输出的标题 Agent，生成结果直接持久化，调用失败时降级为首条用户文本；标题 Agent 不复用聊天实例、消息历史或取消信号，实例本身不进入 SQLite 或 Runtime 池。线程以独立 `last_message_at` 表达最近消息活动并据此排序，重命名和归档只更新元数据时间；消息持久化后 renderer 通过 assistant-ui 的线程列表 `reload()` 刷新运行中时间与顺序。已完成的消息继续通过 `ThreadHistoryAdapter.withFormat` 保存，当前不提供生成中断后的跨重启续传。
- 理由：`AssistantChatTransport` 已提供 assistant-ui 所需的 AI SDK 消息转换、远程线程初始化和 SSE 解码；MessagePort 只替换默认 HTTP fetch，既保持框架原生协议，又将凭据、Registry 和模型调用留在可信 main process。线程级 transport 与角色级 Runtime 隔离避免切换会话或角色时复用可变传输状态；运行级 MessagePort 与 pull 驱动允许跨线程、跨角色并发生成，同时避免无界地向 renderer 推送数据，并为取消语义提供每次运行隔离的通道。非活动角色只挂载 Runtime 内部 Hook 树，不渲染消息列表。
- 代价：preload 需要管理 MessagePort 生命周期和跨隔离上下文的字节帧；应用退出会终止正在生成的回复。每个新会话增加一次受限的标题模型调用及相应延迟和费用。工具调用仍需在同一协议上单独验证工具定义、执行权限、结果和用户确认。
- 复查条件：Electron 提供更适合的原生流传输，assistant-ui/AI SDK 改变 ChatTransport 或 UI message stream 契约，或产品明确要求生成中断后的恢复。

- 状态：已决定
- 日期：2026-07-28
- 决策：聊天 Agent 使用基于 assistant-ui `AISDKToolkit` 的应用级工具聚合层，不建立言奏自有 Tool Registry。Electron main process 注册可信的 AI SDK、Provider 与后续 MCP 工具；renderer 通过 `AssistantChatTransport` 上传的工具仅携带名称、描述和 JSON Schema，经共享 IPC 契约校验后作为无 `execute` 的 frontend tools 合并。前端工具名与任一可信工具冲突时拒绝请求。`ToolLoopAgent` 负责工具调用、结果回灌与最多 8 步的基础循环；assistant-ui 在前端工具结果或审批响应完成后自动续跑。标题 Agent 保持无工具。main 提供无参数、无高权限的 `get_current_time`，以及按 D-028 受会话范围和请求预算约束的 `view_chat_image`；后者对所有语言模型注册，实际多模态结果能力交由 AI SDK Adapter 与 Provider 判断。Web 能力直接使用锁定 Provider SDK 的原生工具定义：OpenAI 与 xAI 装配 `web_search`，Anthropic 装配 `web_search` 与 `web_fetch`，Google 按官方约束装配 `google_search` 与 `url_context`，AI Gateway 按模型 ID 的上游 Provider 前缀选择同一组定义。其他 Provider 不注册 Web 工具，且当前不引入第三方搜索工具包或自研计算器。
- 理由：AI SDK 已提供工具类型、校验、执行与 Agent 循环，assistant-ui 已提供前端工具上传、Toolkit 聚合、工具消息和 UI 生命周期；只扩展现有 Electron transport 的受控字段即可覆盖不同工具来源，无需重复实现工具协议或状态机。前端工具 schema 可以参与模型调用，但不能借此取得 main process 的执行权限。
- 代价：聊天 IPC 增加受限的 `frontendTools` 字段；renderer 工具结果仍属于客户端提供的对话内容。Provider 原生 Web 工具的名称、结果格式、模型支持范围、费用和账户开关由各 Provider 决定，言奏不提供跨 Provider 的虚假兼容层；不支持原生 Web 的 Provider 当前没有降级搜索后端。高权限工具的审批、持久授权和审计策略尚未建立，MCP 连接也只有聚合入口、尚未实际启用。
- 复查条件：AI SDK 或 assistant-ui 提供更直接的 Electron 工具传输，实际工具数量需要按角色动态授权，或高权限工具进入实现范围。

### D-028 · 本地附件事实来源与按需物化

- 状态：已决定
- 日期：2026-08-03
- 决策：言奏的通用 `assets` 注册表和用户数据目录中的不可变托管文件是聊天附件的唯一事实来源。renderer 使用自定义 `KataruneAttachmentAdapter` 将选择、拖拽和剪贴板文件经类型化 IPC 复制到 main process，并生成 URL 为 `katarune-asset://asset/<uuid>` 的 AI SDK 原生 `FileUIPart`；消息继续按框架原生格式持久化，`message_assets` 只记录引用关系。模型上下文只保留最后一条用户消息的原始附件，更早附件投影为包含稳定资产 ID、文件名、MIME 和字节数的轻量文本引用。当前消息仍由 `ToolLoopAgent.experimental_download` 临时物化；需要查看历史图片时，模型调用所有语言模型均可见的 `view_chat_image`，main 按角色、会话和资产引用复验归属、类别、状态、对象边界、存在性、25 MiB 上限、字节数与 SHA-256，再通过 AI SDK `toModelOutput` 返回图片文件内容。工具执行结果只持久化元数据；图片 Base64 只存在于当前请求的 `toolCallId` 内存映射，后续请求重放旧工具结果时只返回文本回执。首版不调用 Provider Files API、AI SDK `uploadFile()`，不保存 `providerReference` 或远端引用缓存；不维护模型能力表，Adapter 或 Provider 不支持多模态工具结果时返回脱敏中文错误。
- 理由：assistant-ui 已提供附件生命周期与工具 UI，AI SDK 已提供 `FileUIPart`、发送时下载回调和多模态 `toModelOutput`。以本地资产为稳定身份可让原文件移动或删除后仍恢复消息；历史二进制按需读取避免会话增长时每轮重复上传全部图片，同时把 Provider 差异留给既有 Adapter。
- 限制与回收：单文件上限 25 MiB，当前消息最多 10 个附件且合计不超过 50 MiB；每次回复最多按需读取 4 张历史图片且合计不超过 50 MiB，当前与历史模型输入合计不超过 100 MiB。历史图片默认将最长边缩至 2048px 并转为 PNG，模型明确需要时可请求原图。同一请求重复读取同一资产复用内存结果。移除草稿只删除无消息引用副本；启动时清理上次退出遗留的全部无引用聊天附件，删除消息或线程时只尝试回收本次删除产生的候选资产，避免清理其他活动草稿。不清理立绘或 VRM 类别，非图片历史附件当前只保留引用。
- 非目标：当前不引入 Uppy、FilePond、独立文件管理 Runtime、Provider Files API、云附件服务、通用文件系统、文件工具、文件沙箱、内容解析或 RAG。
- 复查条件：目标 Provider 普遍提供稳定的 Files API 且远端复用收益可验证，产品改为云端同步附件优先，或 AI SDK 提供可直接覆盖 Electron 本地托管资产的官方 Adapter。

### D-029 · 动态上下文、工具提示与缓存边界

- 状态：已决定
- 日期：2026-07-28
- 决策：模型输入按作用域复用 AI SDK 原生能力，不建立言奏自有的通用上下文协议或全局工具提示词。角色身份、长期行为与安全规则保留为稳定 `instructions`。main process 将按用户时区计算的 `currentDate` 和 IANA `timeZone` 作为类型安全 call options 传入 Agent，由 `callOptionsSchema` 校验，并由 `prepareCall` 在稳定角色 instructions 末尾生成两行环境说明。其他只有模型确实需要推理或回答的请求级数据，也沿用 call options 与 `prepareCall` 进入 prompt。只影响 Agent 执行、生命周期或观测的共享状态使用 `runtimeContext`，工具专属配置、凭据、权限与默认值使用 `toolsContext` 和 `contextSchema`，两者均不因传入 AI SDK 而自动暴露给模型。工具何时使用、输出含义和调用限制优先写在工具 `description`，参数语义写在 Schema 描述中；只有模型选择工具确实依赖当前工具 context 时才使用动态 description。按请求或步骤控制工具可见性、顺序和审批时分别使用 `activeTools`、`toolOrder` 与 `toolApproval`/`prepareStep`，不靠提示词伪装权限边界。
- 环境格式：内容由可信 main process 生成，不接受 renderer 提供同名 system message。字段使用固定顺序和 `YYYY-MM-DD` 日期格式；当前契约如下，新增字段必须通过新的决策明确其模型价值、更新频率与缓存影响。

  ```text
  Current date: 2026-07-28
  Time zone: Asia/Shanghai
  ```

- 缓存约束：模型可见的稳定 instructions、工具名称、Schema、基础描述与发送顺序尽量保持不变，两行环境说明固定放在稳定角色 instructions 之后且不写入时分秒。同一日期和时区内内容保持逐字节一致；日期或时区变化导致的缓存前缀变化属于明确接受的低频代价。高频变化且模型无需知道的值不得进入 prompt 或工具描述。精确时分秒只通过 `get_current_time` 按需获取，不写入每轮 instructions；工具结果包含 UTC 偏移和 IANA 时区，避免模型从 UTC 自行换算。Provider 缓存继续通过各官方 Provider 的原生 `providerOptions` 与 AI SDK `prepareStep` 组合实现；不得把 Anthropic cache breakpoint、OpenAI prompt cache key 或 Google cached content 镜像为一个虚假的跨 Provider 协议。
- 理由：日期与时区会影响“今天”“明天”、问候和日程等常见角色交互，采用与 Codex 相同的信息内容并保持极简格式，可让模型在首次推理前稳定获得这两个值，同时避免把秒级时间写入每轮提示词。AI SDK 7 已提供 `callOptionsSchema`、`prepareCall`、`runtimeContext`、`toolsContext`、动态工具 description、`activeTools`、`toolOrder`、`toolApproval` 和标准化缓存 token 用量，足以继续表达其他请求、Agent 与工具作用域。将所有能力说明拼入角色系统提示词仍会扩大耦合、增加无关 token，并使动态值过早改变 Provider 的可缓存前缀；让工具契约随工具定义存在则更容易按能力启用、测试和演进。
- 代价：不同 Provider 的 prompt 缓存机制、最小 token、TTL、费用和显式断点能力不一致；动态 description、动态工具集合或变化的工具顺序仍可能降低缓存命中。接入缓存优化时必须通过 `usage.inputTokenDetails.cacheReadTokens`、`cacheWriteTokens`、实际请求消息和 Provider 原始请求体测量，不能只根据配置声明成功。
- 非目标：本决策不要求立即实现通用 Prompt Builder、缓存中间件、所有 Provider 的缓存优化或长期记忆注入；长期记忆的检索与上下文策略仍由 D-016 单独决定。
- 复查条件：锁定 AI SDK 版本改变 context、call options、工具 description 或缓存用量契约；实际 Provider 无法保持工具定义顺序；角色、记忆与工具出现已验证的跨域上下文需求，且现有原生作用域不能表达。

### D-030 · Renderer 统一通知中心

- 状态：已决定
- 日期：2026-07-30
- 决策：renderer 使用应用根节点挂载的统一通知中心管理瞬时操作反馈，业务只调用言奏的 `notify`、`dismissNotification`、`clearNotificationScope` 和作用域 Inline outlet。首期渠道只有全局 Toast 与 Inline；Toast 直接复用已锁定 `@base-ui/react@1.6.0` 的 manager、Provider、Portal、堆叠、计时和无障碍能力，固定显示在窗口右上角；Inline 按 scope 仅在需要用户就地修正的 Dialog 或表单中显示，并由 Zustand 内存 store 管理。同一 dedupe key 原位更新，同一 Inline scope 只保留最新通知。通知不持久化，不进入 IPC 或 SQLite。
- 边界：页面级一次性操作的成功、警告、失败与短时加载统一使用 Toast，模型列表、角色页和会话列表不挂载 Inline outlet；只有需要用户在当前 Dialog 或表单中就地修正的校验与保存错误使用对应 scope 的 Inline。页面加载/空状态、字段值、角色自动保存、确认框内部错误和 assistant-ui 模型生成、流与工具错误继续由所属组件或 Runtime 表达。会话删除失败只留在确认框，避免重复播报。首期不公开未实现的 Dialog 或系统通知渠道。
- 理由：Base UI 已提供稳定的 Toast 生命周期、键盘导航、播报优先级和上限控制；言奏只需维护渠道策略、作用域和产品样式，无需引入 Sonner 或自研第二套 Toast primitive。将通知与页面事实状态分开，可避免短暂成功消息挤占布局，也不会把需要用户就地修正的错误移到远离问题的位置。
- 代价：通知只在当前窗口进程内有效，应用重启或窗口销毁后不会恢复；后续系统通知需要单独处理 Electron 权限、窗口焦点和 main/renderer 边界。业务仍须正确区分通知与持久页面状态，不能把所有错误无差别改成 Toast。
- 复查条件：产品需要通知历史、跨窗口同步、后台任务完成后的系统通知，或 Base UI Toast 无法满足桌面无障碍与交互需求。

### D-031 · 单次生成式 TTS、角色声音与派生缓存

- 状态：已决定
- 日期：2026-07-30
- 决策：TTS 作为独立 Capability 接入，不扩张 `provider_type` 或建立第二套供应商 Runtime。模型继续登记在供应商实例下并使用 `model_type = speechModel`。共享 `ProviderDefinition Registry` 以 `provider_type` 穷尽声明凭据模式、已实现模型类别、默认 voice 和首选输出；main Definition 再提供 settings Schema、AI SDK Provider/Model factory、连接测试、音频规范化与校验。OpenAI 是首个且当前唯一 Speech Adapter，但通用 Runtime、缓存、IPC 与 renderer 不以 OpenAI 允许列表判断能力，也不内置 `alloy` 或 MP3。角色以可空软引用 `speech_model_config_id` 和成对出现的、不透明 `speech_voice` 选择声音；OpenAI Adapter 的默认 voice 为 `alloy`。assistant-ui 原生 `SpeechSynthesisAdapter`、`Speak` 与 `StopSpeaking` 管理消息朗读状态和纯文本提取；renderer 根据实际 `mediaType` 播放完整音频、停止、隔离迟到结果并回收 Object URL。main process 根据角色配置调用 `generateSpeech()`，持有凭据与取消信号，并通过归属到 `webContents + requestId` 的严格 IPC 返回成功、取消或清洗后的错误。TTS 不修改消息、线程活动时间或 SQLite 会话记录。
- 音频与缓存：非流式朗读透传供应商原生、浏览器可播放的输出；Adapter 优先选择原生无损格式，只有裸 PCM 时才负责无损封装为 WAV，供应商只支持压缩格式时不重复转码。OpenAI 首版选择 WAV。生成音频是可丢弃的派生数据，保存在 `userData/tts-cache`，不进入 `assets`、消息或 SQLite。请求指纹包含缓存版本、只去除首尾空白的文本、Provider 类型与 Base URL、模型 ID、voice 和 Adapter 输出格式，文件名为 SHA-256 加经过校验的格式扩展名。命中更新 mtime 并再次使用 Adapter 校验音频；启动与写入后按 mtime 清理到 512 MiB。写入使用独立临时文件和原子 rename；零字节、损坏音频、遗留临时文件、超限单文件和已取消结果不保留。凭据轮换不改变缓存键。
- 自动朗读边界：renderer 可选地监听当前可见角色从运行中转为稳定完成，在确认没有工具自动续跑后调用 assistant-ui 当前消息的 `speak()`；只处理有最终文本且具备有效语音能力的新助手消息，并按消息 ID 去重。后台角色、中间工具消息、无文本消息和无声音配置均跳过；手动朗读与停止朗读始终保留。自动朗读偏好只保存在当前设备 renderer 本地。
- 形体接入修订：当 Unity 形体运行时可用时，[D-046](#d-046--unity-提供表演工具与-agent-完成屏障) 的阻塞 `speak` 工具接管语音播放与口型时钟；本节 renderer 播放保留为无形体模式和手动朗读回退，同一段语音不得双重播放。
- 非目标：当前不切句，不实现流式 TTS、ASR、电话/VRM 状态机、空的 `VoiceSessionController` 或用消息朗读 Adapter 模拟双向会话。未来流式音频使用新的 MessagePort Capability；电话/VRM 由独立 `VoiceSessionController` 协调 ASR、Agent、流式 TTS 与打断，并通过 assistant-ui `RealtimeVoiceAdapter` 接入。
- 理由：AI SDK 已提供 SpeechModel Registry 与 `generateSpeech()`，assistant-ui 已提供消息朗读生命周期。把凭据和文件系统留在 main、把播放留在 renderer，可以维持 Electron 安全边界；内容寻址缓存减少重复费用和等待，同时不让可再生音频污染会话事实数据。
- 代价：首版必须等待完整音频才开始播放，长文本直接受供应商限制；缓存占用最多 512 MiB 且没有应用内独立清理 UI，卸载时的缓存清理由 D-032 约束；删除、禁用、改变类别、settings 失效或 Adapter 缺失后角色继续保留软引用并显示不可用。新增供应商必须同时补齐共享元数据和 main Definition，不支持运行时动态插件。
- 复查条件：接入第二个 TTS Provider、需要低延迟首包播放、双向语音打断、缓存需要用户控制，或 assistant-ui/AI SDK 改变 Speech 与 Realtime Voice 契约。
- 修订：供应商级模型类别、默认 voice 和共享 Speech 元数据的部分已由 [D-033](#d-033--provider-自主发现与模型级音色元数据) 取代；缓存、IPC、播放和非流式边界继续有效。

### D-032 · 首版桌面分发、安装卸载与更新策略

- 状态：已决定
- 日期：2026-07-31
- 决策：正式应用标识固定为 `app.katarune.desktop`。Windows 首版只发布 x64 NSIS 离线安装器，采用 one-click、per-user、无 UAC 安装，创建开始菜单快捷方式但不默认创建桌面快捷方式；macOS 分别发布 x64/arm64 的 DMG 与更新用 ZIP；Linux x64 发布 AppImage 与 DEB。日常验证优先使用 unpacked 产物，不提供 Portable、NSIS Web、MSI 或 Squirrel。应用保持 ASAR，`better-sqlite3` 只显式解包运行时 `.node`，Windows 使用 normal、7z 和差分感知包。NSIS 使用默认脚本与 `installer.nsh` 扩展钩子：手动卸载先确认卸载，再显示清理范围；默认删除程序、TTS 缓存、资产暂存和更新下载缓存并保留 SQLite、角色资产、会话、设置与加密凭据，用户可额外选择不可恢复地删除全部本地数据。`/S` 默认保留个人数据，只有显式 `--delete-app-data` 删除全部；自动更新卸载始终跳过页面和所有用户数据清理。

- 签名边界：普通内部包在首版发布前保持无签名且不公开；首发前制作一个内部签名 RC 验证完整链路，公开 Windows 产物使用个人 IV Authenticode 云 HSM、SHA-256 与 RFC 3161 时间戳，公开 macOS 产物使用 Developer ID、Hardened Runtime、公证与 Stapling。SSL.com IV + eSigner 只是待大陆个人资格预审的候选供应商，不作为已采购事实；Linux 发布 SHA-256 和 CI 产物证明。当前不购买证书、不写入凭据，也不启用发布上传。
- 理由：NSIS 是锁定 electron-builder 版本的默认消费者安装目标，支持 per-user 无提权安装、默认脚本扩展和 `electron-updater` 签名校验；AppImage 原生携带差分 blockmap。默认保留用户数据可避免卸载重装误删角色与会话，同时通过只清理明确的应用自有缓存目录减少残留。使用官方 include 钩子而非替换完整 `.nsi`，可继续复用 electron-builder 对安装、更新、卸载器生成和签名的维护。
- 代价：首版卸载清理页沿用 NSIS 原生组件页，不与应用 Web UI 保持一致；选择删除全部数据不可恢复。Windows 无签名 NSIS 生成、blockmap、更新元数据和隔离首启烟测已经验证，但安装/卸载行为、差分回退、更新器、托管、签名证书、macOS 公证及 macOS/Linux 产物仍需后续实现与实际机器验收；Windows SmartScreen 信誉需要在真实发布后逐步积累。
- 复查条件：出现企业 GPO/Intune 部署、Microsoft Store 优先、应用资源大到离线安装器不合适、卸载数据需要更细分类、差分更新收益不足，或锁定 electron-builder/NSIS 更新协议改变。

### D-033 · Provider 自主发现与模型级音色元数据

- 状态：已决定
- 日期：2026-07-31
- 决策：每个 `ProviderDefinition` 自行实现 `discoverModels()` 与 `inspectModel()`，统一编排层不再根据 `provider_type` 处理 URL、认证、分页或 ID 规范化。导入或更换模型 ID 时，main process 使用安全凭据检查模型；供应商返回的明确类型为权威结果，无法识别时才要求用户确认单一类型。共享 Provider 配置只保留凭据模式，不维护 `supportedModelTypes`、供应商默认 voice 或 Speech 输出元数据；模型是否可调用由 Definition 实际存在的 Capability Adapter 和当前配置动态得出。未实现的类别仍允许登记，但标记为不可调用。
- 模型数据边界：`model_configs.metadata` 保存由模型检查得到、可重新获取并整体替换的能力描述；`model_configs.settings` 保存用户拥有的模型级调用默认值。两列使用通用 JSON Object 外层并限制为 64 KiB，再由 `model_type` 对应的 Definition/Capability Schema 校验具体结构；不为 Speech、Image、Embedding 等类别持续增加可空专用列，也不使用 EAV 键值表。Provider Definition 可以在首次检查具体模型时返回建议初始 settings，但建议值写入该模型自己的记录后即成为模型级用户设置，后续元数据刷新只替换 `metadata`，不得读取或改写 `settings`。
- 音色：`speechModel` 的 `metadata.voices` 保存模型级音色列表，`voices = null` 表示无法枚举；`settings.defaultVoiceId` 保存该模型的可空默认 Voice ID。获取方式完全由 Provider Definition 决定，核心不记录 API、静态清单或无法枚举等来源策略。导入时检查并保存，用户可显式刷新；刷新失败保留旧 metadata。音色列表只服务搜索与快捷选择，不是 Voice ID 白名单；无论目录是否存在，角色都可手动输入不透明 Voice ID，保存与调用不做供应商语义校验，交由实际 Provider 判定。默认 Voice ID 只属于具体模型，可在 `speechModel` 专用模型编辑区从目录建议选择或手动填写；连接测试只读取该模型 settings，不得回退到供应商级默认值。
- 目录边界：现有 Gateway 原生发现与 LiteLLM 完整快照、在线未命中查询、官方地址回退、认证错误和未知自定义地址限制保持不变。LiteLLM 只辅助模型库存和类型识别，不承载音色信息。
- 验收实现：OpenAI Speech Adapter 将内置音色随模型检查结果保存，并为具体模型建议初始 `defaultVoiceId = alloy`；Google Definition 使用锁定的 `@ai-sdk/google` SpeechModel，向具体 Gemini TTS 模型返回 30 个预置音色并建议初始 `defaultVoiceId = Kore`；Fish Audio 作为独立供应商实现薄 `SpeechModelV4`，发现当前官方 TTS 后端，并在导入时分页保存账号自有且已训练的 Voice Model。建议值只在创建模型记录时写入该模型的 settings，不进入 `provider_configs`。三者统一输出并校验 WAV。2026-07-31 使用 Fish Audio `s2.1-pro-free`、用户指定的 Voice ID 和正式 TTS/cache 路径完成真实合成，得到有效 WAV 且二次请求命中缓存；项目负责人据此确认 P2 首个 TTS Provider 验收通过，本次不再要求保留音频文件或追加 Chromium 人工播放。
- 非目标：不建立全局 Voice 实体、音色来源/TTL/版本模型、不预定义尚未接入的模型类别详情 Schema、不建立通用模型详情镜像、语音克隆工作流、流式 TTS 或 ASR。
- 理由：模型类型和音色都依赖供应商账号与具体模型，放在供应商级静态能力表会产生错误关联和重复维护。Definition 已是供应商行为边界；把检查结果持久化到模型配置，可在角色界面直接选择，同时保持运行核心对获取方式无感知。将可刷新的检查结果与用户设置分列，也从结构上避免刷新覆盖模型默认 Voice ID。
- 代价：导入和刷新可能访问外部端点；固定音色发生变化时需要对应 Provider 实现更新。目录无法枚举时不能提供下拉选择；手动 Voice ID 可能直到真实调用时才发现无效，但不会因目录不完整而误拒绝公开、共享或新克隆音色。
- 复查条件：供应商提供稳定的跨模型 Voice 资源身份、需要用户克隆音色生命周期，或单个模型必须同时以多个 AI SDK 模型类别调用。

### D-034 · 应用默认模型与设备级常规偏好

- 状态：已决定
- 日期：2026-08-01
- 决策：使用字段明确的单行 `app_settings` 表保存可空 `default_language_model_config_id`，不建立通用 KV 或 JSON 设置表。共享 Zod IPC 只允许写入当前可调用的语言模型；删除模型或所属 Provider 时以 `ON DELETE SET NULL` 自动清空，暂时禁用时保留选择并由界面显示不可用。模型解析顺序固定为“角色专用模型 → 应用默认模型 → 禁止发送”，角色明确选择但不可用时不得静默回退；聊天回复与会话标题生成复用相同解析规则。角色空模型的产品语义改为“跟随应用默认”。
- 偏好边界：亮暗主题、自动朗读回复与“减少动态效果”属于设备级 renderer 偏好，继续保存在 Electron profile 的 `localStorage`；应用默认模型属于产品数据，进入用户数据目录的 SQLite。主题和动效在 React 挂载前初始化。应用开关开启时以根元素属性压缩非必要动画、转场与平滑滚动；系统 `prefers-reduced-motion` 始终独立生效。当前不增加“跟随系统”主题。常规页以单一方角外边框和内部无边框连续列表呈现这四项设置。
- 理由：默认模型参与 main process 的可信调用决策、需要外键清理和跨窗口一致性，适合进入结构化 SQLite；视觉与播放行为只影响当前设备和 renderer，不值得扩大 IPC 或数据库 Schema。单一设置 Context 可使已挂载 Runtime 与常规页即时共享变化。
- 代价：清除浏览器配置或选择“删除全部本地数据”会重置设备偏好；暂时不可用的默认模型会保留 ID，恢复 Provider 后可重新生效。当前应用仍是单窗口，未来多窗口需增加设置变更广播。
- 复查条件：引入账号同步、多窗口、跟随系统主题、更多需要事务和外键的应用设置，或设备偏好需要集中备份与导出。

- 日期：2026-08-05

### D-037 · Unity 原始材质与桌面灯光基线

- 状态：已决定
- 日期：2026-08-05
- 决策：桌面角色渲染继续留在独立 Unity Runtime，并将“模型原始材质”“可选描边覆盖”“角色灯光”和“程序化行为”分层。默认不覆盖运行时 MToon10 的明暗、颜色、贴图、GI、边缘光、MatCap 或描边。`AvatarVisualProfile` 只保存柔和描边参数和材质角色覆盖，`AvatarVisualController` 只在开关启用时按脸、皮肤、头发、眼睛、面部细节、服装和通用材质应用分级屏幕空间描边；眼睛和细节默认不描边。UniVRM 官方 MToon Outline Render Feature 同时挂入 PC 与 Mobile Renderer。
- 灯光与抗锯齿：启动场景预挂一盏无阴影的柔和方向光，方向、颜色、强度与阴影完全由 Unity 原生 Light 组件保存，环境光由场景 Render Settings 保存；不设置运行时 Profile、覆盖脚本或灯光模式，也不在 HUD、命令行或 Presentation Snapshot 中暴露灯光参数。2026-09-10 修正桌宠正面背光与暖色偏色：默认主光为中性白 `RGB (1, 1, 1)`、强度 `0.7`、世界旋转 `Euler (18, 155, 0)`，关闭色温乘色；从相机所在的 `+Z` 一侧偏上照向角色，避免旧方向光从背面照射。Flat 环境光为中性 `RGB (0.35, 0.35, 0.35)`，为背光侧提供基础亮度。编辑器场景即为构建事实来源且不修改模型材质。PC 基线统一使用 4× MSAA；2× 基线在实际桌面观感中仍存在明显轮廓锯齿，因此提高几何边缘采样，同时接受全分辨率透明覆盖层更高的显存带宽与 Resolve 成本。HUD 只保留柔和描边等与灯光档位无关的展示开关。
- 生命周期：描边覆盖纳入 `AvatarRuntimeSession` 的 `load → validate → commit`。候选模型准备完成后才与行为驱动一起提交；迟到或失败的加载会释放临时材质快照，不改变当前模型。重复应用先恢复捕获的四个描边字段，再根据开关计算目标值，避免参数累积漂移，并保留原 Material 引用以兼容 VRM Expression 的材质绑定。
- 透明边界：当前仍使用 URP Alpha Processing 与 UniWindowController Alpha 合成；默认不增加运行时自阴影、材质边缘光、几何描边、Bloom 或全屏调色。不透明排障模式使用固定的浅色背景和地面，便于同模型对照。
- 界面修订：早期 IMGUI 开发面板已由 [D-040](#d-040--unity-ui-toolkit-桌宠-hud) 的黑白径向 UI Toolkit HUD 替代；正式 HUD 只保留柔和描边开关，灯光统一读取默认 Profile，不提供风格预设、材质覆盖强度或画质档位。
- 理由：来源不同的 VRM 已包含作者认可的 MToon 表现；通用覆盖无法可靠推断脸部、头发和服装的专属美术意图，反而会让原始模型失真。保持原材质并将桌面明暗交给灯光层，既可预测又方便比较；柔和描边作为单一、可逆的小范围选项保留。
- 代价：模型之间的原始材质质量和亮度仍会不同；灯光只能改善整体可读性，不能替代模型专属脸部 SDF、材质 ID、阴影遮罩或头发流向数据。
- 复查条件：重要角色开始制作专属脸部 SDF/遮罩，透明合成需要 Alpha 安全的局部 Bloom 或调色，或现有 MToon 无法表达眼睛、头发和脸部的目标表现时，再引入 Katarune 自有 Shader 家族和角色离屏合成，不把试验性后处理直接叠加到透明桌面窗口。

### D-038 · Unity Runtime Facade 与模型事务边界

- 状态：已决定
- 日期：2026-08-06
- 决策：Unity Runtime 以 `IAvatarRuntimeFacade` 作为 UI 和未来外部输入的唯一控制入口；Facade 公开带单调 `Revision` 的不可变 `AvatarRuntimeSnapshot`、显式 `AvatarLoadResult`、分组的行为与表现设置以及瞬时 viseme/眨眼输入。语义状态变化才发布 `Changed`，每帧姿态只通过 `CurrentPose` 读取。任何 UI 都不得直接操作 Session、Behavior 或 Visual Controller。
- 生命周期：`IAvatarModelLoader` 在隐藏候选对象上完成路径校验、UniVRM Runtime、标准化 Driver、材质快照、表达能力与 Bounds 准备；`AvatarRuntimeSession` 只在候选完整有效且请求仍为最新时交换模型、Driver、Visual 与 Framing。提交前旧角色保持活动，提交失败恢复旧绑定与相机，成功后才释放旧角色；迟到、取消和 Unload 后返回的候选必须释放且不得改变当前状态。
- 依赖方向：Unity 代码拆为 `Katarune.Avatar.Core`、`Katarune.Avatar.UniVrm` 与 `Katarune.Avatar.Runtime`。Core 保存状态、行为、Pose 与抽象契约且不引用 UniVRM 或 UniWindowController；UniVrm 封装 Loader、Driver、Expression 与 MToon 描边；Runtime 负责组合根、Facade、Session、场景、灯光、窗口和 HUD。继续使用显式组合，不增加依赖注入或响应式框架。
- 渲染修正：`AvatarRuntime` 场景关闭 Camera Post Processing、移除 Global Volume，并保留一个无组件的 URP 默认 Volume Profile，确保 Bloom、Vignette、Tonemapping 与 Motion Blur 不会介入原始材质基线。
- 非目标：本决策不选择 Electron/Unity 进程承载或传输协议，不增加 PMX、VRMA、真实音频、动作库或自有 Shader；未来协议适配器只能依赖 Facade，不得直接穿透到底层控制器。
- 理由：统一入口和权威快照避免 HUD、未来 Electron 与其他输入源各自复制校验和状态机；候选事务把格式加载和活动角色所有权分开，使失败 Reload、并发 Load 与 Unload 具备可验证的一致语义。
- 代价：Unity 工程增加两个程序集和少量跨程序集契约；当前仍需维护手写 C# 状态类型，直到真实跨进程协议确定后才能评估是否引入代码生成。
- 复查条件：接入 Electron 生命周期/协议、需要高频音频或动作流、增加第二种运行时模型格式，或现有 Facade 无法表达中断与优先级语义。

### D-039 · Unity 预设动作第一阶段

- 状态：已决定
- 日期：2026-08-06
- 决策：Unity Runtime 使用 Humanoid `AnimationClip` 与 `PlayableGraph` 建立首批预设动作技术闭环。基础待机持续运行；`GreetWave`、`Explain`、`Celebrate`、`Cough` 是该技术切片的一次性动作样本，通过 `IAvatarRuntimeFacade.RequestAction` 请求。一次性动作采用 latest-wins、可重启、可取消并在结束后返回基础姿态；不接受任意文件、骨骼帧或模型生成的动作数据。
- 混合边界：动作写入 UniVRM `ControlRigAnimator`，并在动作库可用时独占四肢姿态；程序化层按当前表演权重附加躯干与头部偏移，一次性动作淡入时该偏移降至零。只有动作库缺失的回退模式才由程序化层控制手臂，避免作者动作与基于中性姿态的手臂旋转重复写入同一骨骼。表情、视线、眨眼和 viseme 始终由正交表现管线驱动。模型候选事务同时准备和交换 MotionInstance，失败或迟到候选释放自己的 PlayableGraph 且不改变当前动作。动作库缺失只关闭动作能力，程序化基础姿态保持可用。
- 控制边界：运行时与正式 HUD 只允许四个预设动作，不提供任意 Clip 或骨骼控制入口。早期用于挑选素材的全量 Preview Service、PreviewLibrary 和界面随后由 [D-040](#d-040--unity-ui-toolkit-桌宠-hud) 删除；素材比较回到 Editor 导入阶段，不进入 Player。
- 资产边界：默认待机采用仓库内自有的 9.6 秒 `KataruneQuietIdle` Humanoid Muscle 循环；它固定根节点和四肢，只保留轻微呼吸、身体侧移感与头部微动，并由确定性 Editor 生成器维护。其余第一批技术样片使用 Quaternius Universal Animation Library 1/2 Standard 的 CC0 包，通过 Editor 导入器生成 `Assets/KataruneLocal` 本地库；源 FBX、生成资产、许可副本和截图不进入版本控制。当前 Standard 包缺少名为 `Wave` 与 `Coughing` 的 Clip，导入器分别以 `Interact` 与 `Consume` 作为明确记录的技术替代，不将其视为最终动作美术。
- 非目标：本阶段不接 Electron/AI 协议，不支持 VRMA、运行时自定义动作、动作队列、行为树、模型专属绑定、Root Motion、手部 IK、脚锁定或动画编辑器。
- 代价：共享 Humanoid 动作可能在不同身材模型上出现穿插或姿态差异；本地 CC0 样片无法由 CI 直接验证真实重定向，仓库因此使用合成与 Fake 测试覆盖控制语义，并用仓库外 VRM 做本地烟测。
- 复查条件：确定最终动作资产、接入 Electron 高层意图与 TTS 时间线、需要角色专属动作修正，或实际模型兼容性要求 IK/足部约束时。

### D-040 · Unity UI Toolkit 桌宠 HUD

- 状态：已决定
- 日期：2026-08-16
- 决策：Unity Runtime 使用 `UIDocument + PanelSettings + UXML + USS` 实现正式桌宠 HUD，替换并删除旧 IMGUI `AvatarDebugPanel`。HUD 以 1920×1080 为参考分辨率并采用 `Scale With Screen Size`，默认只显示可拖动的四角星入口；四角星展开模型、表情、动作、视线、角色展示和更多入口，分类再展开第二圈选项。选择后保持展开以便连续比较；再次点击当前分类或四角星逐级收起。角色、行为与渲染状态只从 `AvatarRuntimeSnapshot` 刷新并通过 `IAvatarRuntimeFacade` 修改；不进入产品设置协议的本地角色展示交互由 HUD 直接协调 `AvatarSceneRig` 与 `AvatarWindow`。
- 功能边界：模型入口通过内部 `IAvatarVrmFilePicker` 封装 UniWindowController 原生文件选择器，只接受单个 `.vrm`；当前目录优先取当前模型目录。Neutral 清零其他情绪并回到模型基础脸，其余情绪默认使用作者预设的完整强度 1.0；权重只留作混合与过渡参数，不在直接选择表情时统一削弱。动作入口只选择当前可用能力并提供停止；一级菜单的角色展示默认关闭，开启后左键水平旋转角色并以受限镜头俯仰观察上下方，滚轮改变投影倍率，中键通过物理镜头位移调整屏幕构图；更多包含柔和描边、左上摘要卡开关和恢复默认行为。加载、能力缺失和动作库缺失均从 Snapshot 决定禁用态，错误只在摘要卡已开启时局部显示。恢复默认行为不卸载模型，也不改变灯光或描边；恢复角色展示视图则独立重置角度、倍率和构图偏移。
- 视觉与资产：HUD 采用项目角色图鉴的黑白编辑部风格。左上摘要卡与屏幕保留 28px 设计间距，左上角与右下角为直角、其余两角为圆角；卡片使用完全不透明的 `#E9ECEF` 背景且不绘制描边，以纯黑圆形头像占位、模型名和黑底白字胶囊构成，胶囊以图标和文字显示当前表情或行为实例；摘要卡启动时默认隐藏。控制区不再绘制弧线、连接线或同心圆，中央入口保持 74px 的完全不透明黑色无描边圆形底，内部以 36px 绝对居中的白色 Painter2D 四角星作为操作图标。一级和二级控制均为完全不透明的纯图标圆形按钮，以错峰淡入、缩放和平移动画展开；常驻文字标签全部删除，悬停时由共享 `AvatarHudTooltipElement` 显示无尾巴的上方黑底白字圆角提示。`AvatarHudIconButton` 统一图标结构和状态着色，各操作图标由项目锁定的 `lucide-react@1.25.0` 导出 SVG 并以 Unity VectorImage 导入。中文、模型名和提示统一使用由 OFL Noto Sans SC 可变源字体固定生成的 Regular 400 字重，避免 Unity 直接采用可变字体默认 100 字重。
- 点击与拖动边界：项目只使用 UI Toolkit，因此不再在场景中创建 `EventSystem`/`StandaloneInputModule` 兼容桥，运行时事件由 UI Toolkit 内置事件系统分发。UniWindowController 的帧尾自动 Raycast 命中关闭；Windows 薄适配器读取原生全局光标，转为 Player 客户区坐标，再通过 `RuntimePanelUtils.ScreenToPanel` 与 `panel.Pick` 判断光标下是否为已启用的实际 `Button`，只据此切换窗口点击穿透。UXML 根、文字、提示和布局容器统一 `PickingMode.Ignore`；加载的 VRM 层级继续进入 `Ignore Raycast`。中央入口由 `AvatarHudDragManipulator` 独占指针交互并区分点击和 5px 阈值拖动，按下即用 Pointer Capture 保持窗口交互，帧末采样最新原生光标并用 `style.translate` 与 `DynamicTransform` 移动独立的 74×74 锚点，以当前 Panel 实际 Bounds 约束至全屏；不再启用全屏透明捕获 Button。可复用的 `AvatarRadialMenu` 自定义 UI Toolkit 元素统一暴露一、二级半径、边/角扫过角和安全边距 UXML 参数，以极坐标实时生成按钮位置；四边采用朝内 180° 半圆，四角采用朝内 90° 四分之一圆，数量不足时在弧线上自动居中；不再为八种朝向维护独立 USS 坐标。平时人物、顶部状态和透明区域继续穿透；角色展示开启期间是唯一例外，整窗暂时接收拖拽和滚轮，同时转台输入在 UI Button 下被阻断，关闭或模型卸载后立即恢复局部命中与桌面穿透。
- 显示语义：HUD 启动时可见，F1 是唯一显示/隐藏入口；隐藏会清除菜单展开状态，再次显示从顶部状态和中央入口开始。界面内不显示 F1 提示，删除 `--debug-ui`。自动截图继续强制隐藏 HUD。
- 窗口语义：`Run In Background` 只负责 Unity Player 失焦后继续更新，真正的置顶由 UniWindowController 在原生窗口句柄绑定成功后设置并读取验证。初次绑定、显示器配置变化和应用焦点变化时允许有限重申置顶状态；不按帧修改 Z 顺序、不调用前台激活，也不争抢输入焦点。这里的“置顶”指位于普通窗口之上，不承诺覆盖系统安全桌面、任务管理器等其他强制置顶窗口。
- 清理：删除运行时动作全量浏览服务、PreviewLibrary、导入器预览资产生成和对应测试。视线角度、手动 viseme、微动作强度、FPS、Revision 与任意动作浏览均不迁入正式 HUD。
- 非目标：本决策不接 Electron、托盘或 IPC，不加入人物拖动、位置预设、多显示器、模型图库、自定义动作或新的渲染控制；角色仍位于主显示器右侧安全区。
- 理由：桌宠控制需要保持人物与桌面为主体，传统矩形调试面板和常驻控制文字都会遮挡内容。UI Toolkit 让 UXML/USS 可由 UI Builder 持续调整，共享图标按钮、Tooltip 与 Drag Manipulator 避免各控制项复制交互逻辑；Snapshot/Facade 边界则保证视觉重做不影响运行时事务、动作混合和渲染逻辑。UI Toolkit 原生事件加手动 Panel Pick 把“看得见”与“可交互”分开，并避开 UniWindowController 在 `WaitForEndOfFrame` 中执行全局 Raycast 的额外延迟和分配。
- 代价：径向布局更适合有限白名单，不适合任意长度列表；当前模型选择仍是系统文件对话框，未提供图库。超宽屏和不同 DPI 需要持续视觉烟测，复杂文字回退会增加字体资源体积。
- 复查条件：接入 Electron 托盘或协议、需要拖动角色/多显示器、模型与动作数量超过径向菜单容量，或产品需要键盘/手柄无障碍导航时。

### D-041 · Unity 角色行为 Core 最小领域边界

- 状态：已决定
- 日期：2026-08-22
- 决策：Unity Core 将一段行为拆为只读 `BehaviorIntent`、`BehaviorDefinition`、Unity 内部构造的 `PerformancePlan` 与受控状态转换的权威 `PerformanceInstance`，不把外部请求、资产能力、编译结果和运行状态合并。首版调度语义固定为基础身体、全身表演、上半身手势、表情、视线和口型六类通道；每项通道申请声明独占、共享或附加占用。实例生命周期明确区分 requested、accepted、running、paused、exiting 及 completed/cancelled/failed 终态，终态必须带结束原因；立即取消、安全点退出、暂停、继续和分通道更新使用不同命令语义。立即取消不可被定义关闭，其余控制能力由定义与计划显式声明。
- 所有权边界：A 阶段只在 Core 提供无运行状态的通道所有权冲突策略，用于保证不同实例不能同时获得同一独占通道；共享与附加之间暂时兼容，直到真实混合样片证明需要更严格规则。该策略不授予、不释放也不保存所有权；后续调度器是唯一允许执行这些变更的组件。
- 依赖边界：这些类型不引用 Unity 表现资源、UniVRM、PMX、Electron、AI SDK、具体 Clip 路径或角色骨骼名。VRM 继续只是模型适配器，外部宿主只能在未来协议边界提交高层意图，不能构造内部计划或控制运行状态。
- 验收：纯 Core EditMode 测试覆盖六通道、定义不可变副本、独占冲突、合法与非法状态转换、全部终态识别、终态原因、重复取消/终结幂等、暂停/继续、安全退出、分通道更新和外部类型引用边界；锁定 Editor 下定向测试 20/20、完整 EditMode 回归 110/110 通过。
- 理由：先固定职责和不变量，可以在不改动现有运行时闭环的前提下为后续资产定义与调度垂直切片提供稳定词汇，并避免协议、模型格式或动画资源倒灌到领域层。
- 代价：当前没有实际通道所有权表、队列、优先级、抢占、资源释放或表现图接线；共享与附加的混合细节也尚未由真实资产验证。`PerformanceInstance` 暂不进入权威 Snapshot，不能视为完整调度器已经完成。
- 复查条件：B 至 D 阶段的真实上半身手势或可中断短表演证明六通道、占用模式、暂停状态或控制能力不足，或第二种模型适配器无法复用该领域边界。

### D-042 · Unity 行为资产定义与通用 Humanoid 播放边界

- 状态：已决定
- 日期：2026-08-22
- 决策：B 阶段使用版本化 `.kbehavior` JSON 作为可审查的行为定义源，由 Unity `ScriptedImporter` 严格解析并编译为 `BehaviorDefinitionAsset`。首版字段只覆盖稳定行为 ID、定义版本、角色能力要求、通道申请、单个 Humanoid `AnimationClip`、入口/循环/退出段、命名同步点与安全退出标记、回退策略和许可证元数据；Clip 通过 Unity GUID 引用，不在定义中保存绝对路径、骨骼名或模型格式类型。未知字段、缺失或非 Clip 引用、非法段/同步点、重复通道、能力不足及不完整许可证元数据均返回带错误码的明确校验结果。
- Rig 边界：新增 `Katarune.Avatar.Motion` 程序集，承接 `AvatarMotionLibrary`、`AvatarMotionController`、`AvatarMotionInstance`、PlayableGraph 和通用 Humanoid Rig Binding；`Katarune.Avatar.UniVrm` 只从 UniVRM Control Rig 构造 `ICharacterRigBinding` 并交给通用播放层，不再拥有通用动作库和播放实现。现有模型 `prepare → validate → commit`、Facade 与 Snapshot 行为不变，新行为定义暂不接入运行时调度。
- 资产与许可证：分发成熟度固定区分 `dev-only`、`prototype-distributable` 和 `commercial-candidate`，同时保存来源、作者、许可证标识、许可证地址和备注。首个定义使用仓库已有的 `KataruneQuietIdle`，其基准来自 Unity Timeline 的 `HumanoidDefault`，按 Unity Companion License 记录为可分发原型；项目整体公开许可证仍未决定，因此不把它标记为商用候选，也不新增第三方原始素材。
- 理由：严格文本源便于审查、版本控制和替换 Clip，编译后的 Unity 资产保留稳定对象引用；独立 Motion 程序集让后续第二种模型适配器只需提供统一 Rig Binding，不需要复制 PlayableGraph 播放器或把 UniVRM 类型泄漏给行为资产。
- 代价：首版导入器包含一个只服务 `.kbehavior` 的最小严格 JSON 读取器；定义目前只支持单 Clip，不提供完整资产包、迁移器、Timeline、多 Clip 图或调度接线。`commercial-candidate` 只是清单分类，不等同于法律审查通过。
- 复查条件：C/D 阶段的三份真实样片需要多 Clip、Avatar Mask、参数范围、等待循环或更复杂退出图；第二种模型格式无法映射当前 Humanoid Binding；或 Unity 提供已锁定且不增加不必要依赖的严格 JSON 方案时。

### D-043 · 桌面态语音陪伴与文字对话双模式

- 决策：产品采用同一角色与持续状态下的桌面态/全屏世界态双态结构；本决策只固定桌面交互。桌面态默认是完全穿透的语音陪伴模式，底部复用逐句上移字幕/转写、用户输入波形与 AI 回复，麦克风由用户手动开关且关闭时明确显示静音。切换到对话模式后，同一底部区域提供文字输入，只有输入面板接收鼠标与键盘；进入时临时暂停麦克风，退出时恢复进入前的开关状态。Electron 继续保存完整历史，Unity 与桌面表现层不新增历史面板；文字和语音共享同一对话上下文。
- 快捷交互：小圆球从放射菜单改为向屏幕内侧展开的一排快捷按钮。默认显示“进入世界、文字输入、实时语音、更多”；实时语音开启后显示“进入世界、文字输入、静音、结束语音”。键盘/返回语音按钮、全局快捷键和 `Esc` 负责模式切换；除 `Esc` 外的具体键位待定。低频设置留在常规设置或“更多”。
- 表现边界：小圆球只表达默认、正在听/检测到用户说话、AI 正在说和静音，不承载思考或任务进度。麦克风开启必须持续可感知，用户与 AI 波形不得只靠颜色区分。正式桌面摄像机是否固定、是否允许旋转，依据构建与实机调试确定；当前展示转台主要用于调试（2026-09-09 修订，见 D-048）。产品缩放目标仍为有限稳定档位；字幕与输入复用同一底部区域。
- 非目标：本决策不实现 UI、Electron、Unity、ASR 或实时语音功能，不决定全屏世界态玩法，也不预设桌面工坊、AI 小镇、VRChat 或大世界。具体视觉样式、尺寸、动效、波形形式、缩放档位和全局快捷键键位留待视觉稿与实机验证。详细边界见[桌面交互设计](../00-项目/桌面交互设计.md)。
- 理由：默认穿透保留轻量陪伴感，临时可编辑输入兼顾键盘对话且不让透明桌面变成完整聊天窗口；复用底部区域和同一上下文可降低模式切换的认知与实现分叉。
- 代价：输入焦点、麦克风临时暂停/恢复、点击穿透和全局快捷键必须跨 Electron 与桌面表现层协调；在这些链路实测前，本文只能作为产品约束，不能视为已交付能力。
- 复查条件：输入法、无障碍、全局快捷键冲突、多显示器、麦克风权限或双向语音实测证明当前模式切换语义不可用，或全屏世界态需要不同的角色状态连续性边界。

### D-044 · Unity 三样片资产表达与安全退出锚点

- 状态：已决定
- 日期：2026-08-22；2026-08-23 修正素材通道声明
- 决策：C 阶段继续使用单个 Humanoid `AnimationClip` 的 `.kbehavior` 定义，并补充有限 `loopIterations`、退出段对应的命名 `exitSyncPoint` 和可选 `AvatarMask`。实机复查确认 UAL1 `Idle_Talking` 是完整全身动作，不能只因用途叫“解释”就裁掉腿、头和根节点；该样片改为无 Mask 的独占全身表演。`AvatarMask` 与 `Gesture.UpperBody` 能力仍保留给未来真正按局部身体创作或验证过裁切质量的素材，当前不伪造样片。短全身表演继续用十五次一秒循环、下一次 0.5 秒稳定站姿安全点和一秒退出段组成 16.5 秒表演。可选入口/循环/退出段以显式存在位保存，许可证元数据增加取得日期、原始格式、商用/修改/再分发权与仓库收录策略。
- 资产与许可：待机沿用 `KataruneQuietIdle`。全身解释和短表演分别由 Quaternius Universal Animation Library 1 Standard 的 `Idle_Talking` 与 `Dance` 生成；官方页及包内许可证均为 CC0 1.0。仓库只保存规范化 Unity `.anim`，原始 UAL1 FBX 与许可证副本留在 Git 忽略的本地源目录。Root/Motion 曲线固定到待机基线，退出只混合 Humanoid 肌肉且禁止插值过冲。
- 理由：真实 `Dance` 循环边界并不是安全人体姿势，证明“有安全点”和“退出段”不足以保证两者能合法连接；显式锚定可让后续计划编译器在安全姿势跳入对应退出段。有限循环次数则让一秒 CC0 Clip 能声明十五至三十秒首轮表演，不需要提前引入 Timeline 或多 Clip 图。
- 代价：当前仍没有调度器、通道所有权表或运行时自动跳转；生成器对 UAL1 源 Clip 名称的映射只存在于 Editor 素材适配工具，不进入运行时解析。`commercial-candidate` 是资产清单分类，不替代正式法律审查。
- 复查条件：第二套真实素材要求一个退出段对应多个不同安全姿势、需要循环等待/分支、多 Clip 或 Timeline，或 D 阶段计划编译无法从当前字段无歧义地产生播放步骤。

### D-045 · Unity 行为调度器与单 PlayableGraph 接管边界

- 状态：已决定，待产品 VRM 实机验收
- 日期：2026-08-22；2026-08-23 修正全身播放与过渡
- 决策：D 阶段由 Core `PerformanceScheduler` 保存新行为实例的唯一通道所有权表，负责计划实例化、并行、排队、拒绝、中断、终态释放和队列提升；Motion 层只解析 `BehaviorDefinitionAsset`、推进单 Clip 段/同步点游标并向同一个每模型 `AvatarMotionInstance` 提交播放。现有 Animator 输出保持一个 `AnimationLayerMixerPlayable`，稳定基础循环是地面层，当前两个解释/短舞蹈样片通过同一个无 Mask 的全身 Performance Mixer 覆盖；不得为调度行为建立第二个 Animator 输出或让 Facade、HUD、模型适配器直接授予通道。上半身通道是保留的调度语义，不代表可以把任意全身 Clip 直接套 Mask。
- 状态与入口：`IAvatarRuntimeFacade` 新增高层行为请求和按实例命令，带 Revision 的 `AvatarMotionSnapshot` 返回运行实例数、排队计数与可解释诊断；实例状态只来自调度器。全身表演淡入时逐步压低程序化身体，表情、视线和口型继续由正交通道驱动。基础姿态与调度身体实例共享同一个 Animator 输出和互斥闸门。
- 过渡与退出语义：调度全身表演使用固定秒数与 SmoothStep 权重曲线；首帧淡入 0.20 秒、自然完成回待机 0.25 秒、安全退出尾段回待机 0.20 秒、立即取消视觉缓冲 0.12 秒。动作间由同一 Performance Mixer 对互补权重归一化，Foot IK 保持启用，Root Motion 保持关闭。安全退出请求在最近命名同步点进入对应退出段，实例在退出段完成前继续持有通道，互斥队列不得提前启动。立即取消在 Core 立即终结和释放所有权，Motion 只冻结最后采样姿态并做 0.12 秒视觉淡出；该尾迹不继续推进动作，也不重新取得通道。完成、失败和取消使用同一终态通知路径，重复终结返回 `AlreadyTerminal` 且不产生第二次播放副作用。
- 验收：仓库保存口型加解释动作、舞蹈中安全退出与明确停止两个独立 Unity 场景；自动化测试覆盖通道并行、排队/拒绝、终态释放、重复取消、真实三样片游标、Facade/Snapshot 与本地 Humanoid PlayableGraph。场景只模拟手动口型、凝视和中断，不接 Electron 或真实音频。当前产品 VRM 的最终视觉观感仍待确认；2026-09-09 修订为按实际接入的能力验收，不再把完整舞蹈与打断验收作为文本 AI 控制的前置条件。
- 理由：将语义仲裁与 Unity 资产播放分开，可以保持 Core 无框架依赖、复用 VRM 之外的未来 Rig 适配器，同时让真实同步点决定资源何时释放；复用现有单图可直接消除新旧组件同时写同一 Animator 的风险。
- 代价：首版播放编译器仍只支持 B/C 阶段的单 Clip、单退出锚点和当前占用规则；诊断快照使用进程内字符串供 Unity 验收，尚不是 E 阶段跨进程事件协议。手动动作与调度身体实例通过互斥检查共享播放图。2026-09-09 修订：普通动作可通过 Facade 复用现有动作库，补齐工具所需的完成反馈与冲突处理；需要分段或安全退出的表演再使用行为定义。
- 复查条件：产品 VRM 显示 Mask、重定向或退出恢复缺陷；第二种动作需要多 Clip、多退出锚点、真正的动画加法混合或优先级抢占；或 E 阶段协议需要结构化快照与增量事件时。

### D-046 · Unity 提供表演工具与 Agent 完成屏障

- 后续修订：D-054 取代本节 `speak` 与阻塞式工具完成屏障方案；当前由 Unity 按原生事件顺序调度对白、表情与动作，工具只等待接收确认。
- 状态：能力归属继续有效；完成屏障已被 D-054 取代
- 日期：2026-08-28
- 决策：Unity Avatar Runtime 是形体能力的工具提供方。它按当前角色、表情映射和动作资产公布宿主中立的能力清单、工具描述、受限参数 Schema 与稳定语义 ID；Katarune Electron main 只校验该清单、适配为受信任的 AI SDK 工具并转发调用，不硬编码第二份表情枚举或表演目录。Unity 的工具入口再映射到内部 `BehaviorIntent`、语音实例或表情命令，AI 仍不能接触 Clip、路径、骨骼、BlendShape、帧或混合权重。
- 表情：情绪等同于 `set_expression` 的有限语义表情枚举。具体可用值以 Unity 当前工具描述为唯一事实来源；`neutral`、`happy`、`sad`、`angry`、`surprised` 只是一组初始示例，不是 Electron 常量。调用在 Unity 接受或拒绝后立即返回，不等待平滑混合完成；映射、降级和平滑都由 Unity 负责。
- 完成语义：`speak` 与动作工具异步等待 Unity 完成或失败后返回，表情工具确认设置后返回。工具并发和步骤续跑直接复用 AI SDK；Electron 不另建表演完成状态机。长表演的精确同步与用户打断按实际需要后接。
- 语音边界：TTS Provider、凭据、缓存与格式标准化继续位于 Electron main；Unity 通过宿主中立的语音合成端点取得音频，并作为有形体模式唯一的播放和口型时钟。因此 `speak` 是 Unity 提供的表演工具，但供应商调用仍由 Electron 代理。长舞蹈、唱歌或剧情演出对 AI 保持一个高层表演 ID，其内部音频、动作与退出编排由 Unity 完成，不把细粒度时间轴交给模型。2026-09-09 按 D-053 调整实施顺序：先提供只有字幕的文本 `speak`，按阅读时长反馈完成；TTS、真实口型与语音锚点后接。
- Agent 与消息：工具化对白使用 `speak.text`，通过框架原生消息显示和保存；普通正文不重复作为字幕播放。2026-09-09 按 D-053 修订：仅增加工具，循环的继续与结束使用 AI SDK 既有行为，不增加结束工具。无活动形体的普通聊天沿用原有输出。
- 状态边界：用户输入和模型生成使用事实事件，语音播放与表演使用权威实例；协议不以覆盖整个角色的阶段驱动身体 Clip。
- 理由：项目锁定的 `ai@7.0.31` 会并行执行同一步工具，并在工具结果回灌后继续 Agent 循环，能够天然形成“并行表演管道 + 最慢阻塞工具完成屏障”。把能力 Schema 留在 Unity 可以让同一组件随角色和资产即插即用，也避免 Electron 与 Unity 对可用表情和表演产生双重事实。
- 代价：长工具会让一个 Agent 运行在本地等待数秒或数分钟，必须实现取消、超时、Unity 失联、重连、迟到结果和应用退出语义；工具化对白还需要把 `speak.text` 正确投影为普通助手消息，避免暴露内部工具 UI 或产生重复持久化。不是所有 Provider 都同等可靠地产生并行工具调用，因此降级路径和确定性默认表现仍是验收项。
- 复查条件：目标 Provider 无法稳定并行调用工具，AI SDK 的工具并发或停止条件发生变化，长时间本地等待导致不可接受的恢复问题，或真实角色证明有限表情枚举不足以表达核心体验。

### D-047 · 退役历史 Quiet Idle，重新建立默认姿态基线

- 状态：已决定；身体静止与环境风主驱动的临时基线已由 [D-049](#d-049--待机微动改为身体驱动二级物理) 替代
- 日期：2026-08-29
- 背景：`KataruneQuietIdle` 是早期技术样片，用 Unity Timeline 的中性 Humanoid Clip 生成固定 9.6 秒循环；其数值与动作表现没有经过当前默认模型的美术验收，生成的 `.anim` 也已随三份历史样片退役。继续保留生成器、行为定义和 Catalog 引用会制造“当前仍有正式待机资产”的错误事实。
- 决策：删除 `KataruneQuietIdle` 生成器、`.kbehavior`、Catalog 条目、专用测试和预览入口；历史表演定义不再回退到该行为。当前无正式基础动作资产时，由程序化眨眼、固定/指针二态视线和默认骨骼姿态提供最低可用表现；呼吸与身体微摆从行为设置协议和骨骼驱动中删除。模型内 VRM 1.0 SpringBone 继续负责二级物理，并接收独立于身体动作的连续世界空间环境风。新的默认姿态与待机资产必须以当前默认模型重新实机调校和验收，不能沿用历史样片的通过结论。
- 首轮基线：身体暂时保持稳定的中性初始姿态，不以程序噪声模拟完整游戏待机演出。视线跟随由一级 HUD 手动开关控制且默认关闭；关闭时固定正前方，开启时持续跟随鼠标，不存在定时自动切换、随机偏移或外部手动角度。鼠标像素由摄像机射线与摄像机朝向的虚拟窗口平面求出世界目标，再从 VRM 眼睛原点和角色根朝向计算角度，不把屏幕偏移直接乘固定角度。眼睛先响应目标变化，头部只在偏角越过死区后延迟并以带速度连续性的阻尼平滑跟随；UniVRM 的眼球输入扣除头颈已经承担的角度。环境风通过 UniVRM 0.131 的模型级 Spring Bone `ExternalForce` 在物理解算前逐帧注入，不修改模型作者设置的弹簧关节参数。
- 理由：程序化层与历史 `AnimationClip` 的职责重叠，而且后者已没有随仓库分发的 Clip；删除死入口能让后续默认姿态和物理调优只有一个事实来源。
- 代价：动作库重新选定基础循环前，`AvatarMotionController` 不提供作者制作的身体基底，角色身体保持中性静止；没有 VRM Spring Bone 的模型不会表现环境风，弹簧参数差异也会使不同模型的风响应不同。历史 Quaternius 生成工具只能恢复到 Unity 中性 Humanoid 参考姿态。
- 复查条件：新的角色专属基础循环通过循环边界、重定向、与程序化层混合、SpringBone 响应和许可证验收后，再以新行为 ID 接入，不恢复 `KataruneQuietIdle`。

### D-048 · 桌面角色展示采用角色转台与投影构图

- 状态：已决定的调试能力；正式桌面摄像机交互待验证
- 日期：2026-08-30（2026-09-09 明确产品边界）
- 使用定位：当前展示转台主要服务模型、动作、材质和取景调试，继续保留。正式桌面摄像机是否固定、是否允许旋转及开放哪些操作，依据构建过程中的调试与实机体验确定；既不把转台直接作为最终用户交互，也不预先禁止正式桌面旋转。桌面交互目标见[桌面交互设计](../00-项目/桌面交互设计.md)。
- 背景：摄像机围绕角色运行仍然呈现为游戏镜头控制，拖动时画面背景、观察方向和角色视线关系一起变化；这与以固定画框旋转模型的成熟角色展示界面不是同一种交互。缺少跟手阻尼和松手惯性又进一步放大了机械感。
- 决策：桌面角色展示把角色根旋转、受限纵向观察、投影倍率和屏幕构图拆为互不改写的状态。模型提交时把 VRM 根节点规范化到世界原点 `(0,0,0)`；Renderer Bounds 只用于计算初始纵向取景与安全宽度，不再充当转轴。左键水平拖动把根节点绕自身世界 Y 轴的目标角度保存为不折返、不归一化的连续标量，根节点位置在任意角度始终为零；使用 Unity `Mathf.SmoothDamp` 保持跟手阶段的速度连续，不使用会在跨越 180° 时选择圆周最短路径的 `Mathf.SmoothDampAngle`。松手后将采样角速度写入同一个连续目标并以指数阻尼衰减。左键垂直拖动只让摄像机围绕固定取景目标在上下各 `45°` 内俯仰，角色保持直立。滚轮只改变以正切空间定义的投影放大倍率；中键拖动只改变相对初始值的物理镜头 `lensShift`，并把构图中心限制在 viewport 的 `8%–92%`。倍率与构图均使用独立 `SmoothDamp`，不改变角色世界位置、初始取景中心或基础相机距离。角色展示关闭时立即停止未完成惯性并保留当前角度、倍率和构图；重新加载模型或显式恢复展示视图才回到默认正面、水平视角、`0.6×` 与右下角 `8%` 安全边距构图。Main Camera、`AvatarSceneRig` 和主方向光由启动场景预挂载；相机视觉基准通过 Inspector 调整，方向光参数由原生 Light 组件保存，环境光由场景 Render Settings 保存，不设置运行时灯光配置层。模型替换事务同时捕获并恢复旧角色 Transform、画框、倍率和构图状态；鼠标视线继续从最终摄像机和当前角色根朝向计算，不新增设置协议字段。
- 理由：用户主要操作的是“转动陈列角色”，而不是在虚拟世界中驾驶自由相机。VRM 作者根轴比包含长发、披风等非对称几何的 Renderer AABB 更能表达角色自身中心；否则包围盒会把轴拉向背部。转台允许连续多圈，因此拖动方向是比模 360° 后的最短路径更重要的不变量；无界标量阻尼可避免高速跨过 180° 时短暂反向。缩放使用 FOV、构图使用 `lensShift`，两者与相机世界位姿解耦；有限俯仰只提供角色展示所需的上下观察，不扩张为自由镜头。Unity 自带的标量与向量阻尼 API 已足以实现这些交互，不需要引入完整摄像机框架。
- 代价：桌面展示不提供自由环绕、世界空间平移、碰撞或遮挡处理；纵向观察仍会改变实际摄像机朝向，视线追踪因此按最终相机姿态重新投影。构图平移属于投影偏移，极端偏移会产生非对称透视，因此必须保留 viewport 边界。若某些不规范模型的作者根轴没有位于人体中线，后续需要通过明确的模型展示元数据修正，不能再次从动态 Renderer Bounds 猜测转轴。
- 复查条件：进入虚拟世界模式并需要角色移动跟随、场景碰撞遮挡、多个镜头混合、手柄输入或多角色取景时，为世界态建立独立摄像机系统，不把桌面角色转台扩张为通用游戏摄像机。

### D-049 · 待机微动改为身体驱动二级物理

- 状态：已被 D-050 的本机 VRMA 默认循环替代；环境风与二级物理保留
- 日期：2026-08-30
- 背景：D-047 的稳定中性身体加连续环境风虽能让 Spring Bone 工作，但视觉上容易形成“角色不动、头发被风扇吹”的割裂感，较大的统一世界外力也会让不同长度和刚度的弹簧链同时出现阵风式摆动。
- 决策：无正式基础 Clip 时，Core 提供确定性的 `AvatarIdleMotion` 作为 fallback：以约 `4.2` 秒周期、胸椎链总俯仰不超过约 `0.65°` 的呼吸，加上约 `7–12` 秒周期、颈头链不超过约 `0.25°` 的独立摆动。该层只旋转标准化 Control Rig 的 Spine、Chest、UpperChest、Neck 与 Head，不缩放胸腔、不上下移动角色根，也不暴露新的运行时设置。程序化姿态在作者动作之后、UniVRM Spring Bone 之前应用；作者全身动作继续通过已有权重压低它。视线输入补偿整条待机旋转链，保持固定正前方与指针目标不漂移。`AvatarAmbientWind` 继续通过模型级世界空间 `ExternalForce` 注入，但上限由 `0.06` 降为 `0.006`，只用于避免完全静止，不修改模型作者的关节、重力、阻尼和碰撞设置。
- 理由：头发、饰品和衣角应主要因身体根部运动产生惯性、滞后与回弹；同一身体运动经过模型各自的 Spring Bone 参数后会自然产生差异，比统一强风更接近角色自身的生命感。项目现有执行顺序为动作 `9000`、程序化姿态 `10000`、UniVRM `Vrm10Instance` `11000`，无需增加 Animation Rigging 或第三方物理依赖。
- 代价：程序化微动仍是通用 fallback，不等于角色专属的美术待机；不同模型的骨长、骨轴和 Spring Bone 参数会改变最终观感，没有 Spring Bone 的模型只能看到身体微动。视线补偿按小角度骨链近似叠加，当前幅度下足够稳定，但不替代复杂全身瞄准约束。
- 复查条件：默认角色专属基础循环完成美术验收后，让 Clip 承担主要身体生命感并降低或关闭 fallback；若模型批量验收显示特定骨轴异常，再引入角色级姿态元数据，不增加面向普通用户的物理参数面板。

- 状态：已决定，已实现 Windows 开发基线
- 日期：2026-09-10

- 播放：Unity 将 `text-start` 建立的对白节点和 `tool-input-available` 建立的动作、表情节点放入同一时间线，按原生事件出现顺序推进。对白节点在实际字幕阅读完成后结束；表情节点到达游标时切换并保持；动作节点在动作真正开始后根据 `allowSpeech` 决定是否放行后续对白。AI 原生流结束即关闭聊天流并释放下一条用户输入；桌宠播放、等待和完成状态由 Unity 内部维护，后续轮次继续进入 Unity 队列。Electron 后台等待 drain 仅用于安全回收该轮借给 Unity 的音频文件，不阻塞 UI 或下一轮生成。后续 D-056/D-057 已将 TTS 接入同一对白节点，以实际音频播放进度取代阅读时长。
- 替代：取代 D-053 中工具化对白与按句阻塞的部分；继续使用现有聊天入口、Unity 字幕样式和不打断的输入队列。
- 验证：234 项单元测试、182 项 Unity EditMode 测试、Electron 生产构建、实际 Windows Player 的源顺序表情切换与 `allowSpeech` 两种动作路径通过；未调用付费模型或 TTS Provider。

- 2026-09-10 调试修订：字幕以自然句、段落和长句停顿分页，去除多余空白；流式输入不等整段完成。用户确认仅在桌宠控制可用时追加身体提示，说明普通文本即对白、动作与表情使用工具、由 AI 自主选择时机，不强制每句调用。角色原有设定保留。

- 会话生命周期：连接桌宠只关联框架已有的本地会话 ID，不调用会话初始化或写入空白记录；首次发消息时再沿用框架初始化和自动标题。移除基于默认标题的 runEnd 补偿，不另建标题触发逻辑。

### D-055 · Unity 从启动即覆盖显示器的无边框窗口

- 状态：已决定
- 日期：2026-09-10
- 背景：桌宠需全屏可达，并为未来世界态的画面过渡保留完整显示区域。旧的 `Windowed` 启动与插件后置 `FitToMonitor` 会产生可见的窗口尺寸跳变。
- 决策：Windows Player 使用 Unity `FullScreenWindow` 和原生显示器分辨率；启动场景关闭 UniWindowController 的 `forceWindowed` 与 `shouldFitMonitor`，由 Unity 管理全屏窗口几何，插件只继续提供透明、置顶和点击穿透。Electron 通过 `-screen-fullscreen 1 -window-mode borderless` 覆盖旧版本记住的窗口模式，并使用 `windowsHide: false` 正常显示这个 GUI 窗口。
- 启动材质：明确传入 UniVRM 的 `UrpVrm10MaterialDescriptorGenerator`。项目只使用 URP；首帧之前 `RenderPipelineManager.currentPipeline` 可能为空，不能依赖此时的自动检测，否则会误选未打包的 Built-in Shader。
- 验证：本机 2880×1800 Windows Player 的首个可见窗口即覆盖显示器，透明插件接管后位置与尺寸保持不变；实际桌面确认透明渲染，并保留局部输入与穿透。隐藏启动标记会使插件接管后窗口隐藏，因此不把 Unity 当作隐藏的后台辅助程序启动。
- 边界：此决定仅落实窗口启动方式。世界玩法、模式过渡动画、角色拖拽、多显示器选择策略及跨平台支持仍待后续任务；不提前创建第二个窗口、渲染进程或新的模式协议。
- 复查条件：显示器切换、混合 DPI、世界态输入与画面合成，或 UniWindowController 升级后出现兼容问题。参考 [Unity FullScreenWindow](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/FullScreenMode.FullScreenWindow.html) 与 [Player 启动参数](https://docs.unity3d.com/6000.3/Documentation/Manual/PlayerCommandLineArguments.html)。

### D-056 · uLipSync 实时语音口型

- 状态：已决定，首版本地实现与验收通过
- 日期：2026-09-10
- 决策：Unity 在播放语音的同一个 AudioSource 上使用 uLipSync 3.1.5（提交 `ece3272762f2148dd8d3e658ec04fcbd79d4d97e`）分析实际音频。A/I/U/E/O 映射为 Aa/Ih/Ou/Ee/Oh，经 Runtime Facade 和行为系统写入 VRM；第三方组件不直接操作模型。
- 音量与静音：元音比例乘音量开合，噪声及未知音素保留闭口份额；暂停、停止、结束及释放时清除口型。平滑复用行为系统。
- Profile：复用上游原生 Profile 与校准能力，默认示例用于初始验证，不代表特定角色音色已经校准。最终校准使用角色 TTS 音色，覆盖五元音与呼吸/噪声。
- 供应商接口：普通 `SpeechModelV4.doGenerate()` 与 Fish `/v1/tts` 保持不变；时间戳作为语音模型可选的独立 `generateWithTimestamps()` 能力，经现有解析入口暴露。普通连接测试不切换端点。Fish 接收 SSE 音频与累计 alignment，按 chunk_seq 替换快照并加一次音频偏移；完整产物使用 WAV；增量 PCM 播放见 D-057。
- 播放：每个原生 text 块结束后由 main 合成，以运行 ID 与对白 ID 将音频补入 Unity 同一个对白节点。完整文件路径一个请求运行、最多预取下一块；D-057 增量路径在 Unity 到达对白后开始合成，合成不阻塞原生事件与工具步骤。Unity 音频结束后才推进对白；drain 在后台确认该轮资源已使用完，不延长聊天运行状态。聊天流关闭时解除其取消信号与桌宠播放的绑定，语音合成和预取持续到 Unity 完成；断开或停止桌宠时统一取消和清理。Unity 清空表演队列时确认其中的资源回收请求，避免前轮后台等待悬挂。匹配当前会话的活动桌宠始终启用对白语音，无声音配置或合成失败则走文字字幕；设备级自动朗读开关只控制无匹配桌宠时的朗读，不再随聊天请求传入 main。
- 时间：字幕使用 AudioSource.timeSamples / clip.frequency。字幕内容始终来自去除 Markdown 格式标记后的原文，保留标点、大小写与数字；供应商片段仅用于匹配原文分段边界和显示时间，不直接显示其正规化文本。忽略标点、空白和大小写后无法完整匹配时，不使用供应商文本替换原文。字幕统一按原文分句，长句优先在逗号、分号、冒号等位置拆分，目标上限 32 个可见字符，完整英文词和句尾标点可略超限；压缩多余空白，保留词间空格，闭引号随句尾，文字居中。有声与无声共用 Unity 分页函数。有声优先使用片段时间戳，页边界位于粗粒度片段内部时按片段内字符位置估算；对齐缺失或无效则按原文位置与音频总时长估算页时间，不代表逐字精确对齐。短于等于 0.8 秒的页间停顿保留上一页，长停顿隐藏；无声沿用阅读时长。缓存保留原始供应商对齐信息，读取时应用展示映射，无需重新合成。
- 手动朗读：自动表演期间禁用并在 main 校验；空闲时匹配桌宠走 Unity，没有匹配桌宠才回退 renderer。不得因 Unity 播放失败自动转浏览器重播。凭据和音频文件由 main 管理，renderer 不提供路径。
- 代价：MFCC 窗口与帧调度产生延迟，准确度需角色语音实测；ASR、强制对齐与逐字高亮后续单独接入；增量播放见 D-057。默认 Profile 不是音色校准验收。
- 依据：[uLipSync](https://github.com/hecomi/uLipSync)、[Unity 6.3 OnAudioFilterRead](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/MonoBehaviour.OnAudioFilterRead.html)。

- 验收：供应商与服务单测覆盖首块提前返回、PCM 字节边界、异步消费背压与缓存；Unity EditMode 覆盖缓冲、取消和字幕单调推进。Windows Player 慢流实测首批 PCM 后开始播放、断流时钟冻结、恢复、口型与取消。真实 Fish 调用和复用真实 PCM 的 Player 测试分别运行，首音网络耗时与本地启动耗时分开记录。
