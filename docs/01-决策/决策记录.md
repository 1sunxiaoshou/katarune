### D-004 · 使用 AI SDK 与 assistant-ui

- 状态：已决定
- 日期：2026-07-19
- 决策：AI SDK 承担模型调用、工具调用、流式输出与基础 Agent 循环；assistant-ui 承担聊天交互框架。首批兼容基线锁定为 `ai@7.0.31`、`@ai-sdk/react@4.0.34`、`@assistant-ui/react@0.14.27` 与 `@assistant-ui/react-ai-sdk@1.3.41`。
- 理由：这组版本满足 React 19、Zod 4 和 Electron 43 内置 Node.js 的要求；确定性 mock model 已验证 Provider Registry、`ToolLoopAgent` 与流式输出，assistant-ui 的 AI SDK runtime 已在 sandboxed renderer 中成功挂载。
- 代价：AI SDK 7 已是 ESM-only，要求 Node.js 22 以上；assistant-ui 尚未到 1.0，升级必须作为独立任务验证。官方默认传输面向 HTTP API 路由，而言奏的可信 Agent 位于 Electron main process，因此 main 与 renderer 的最终流传输仍需单独设计。
- 复查条件：锁定版本出现无法规避的安全或兼容问题，Electron 内置 Node.js 不再满足要求，或 assistant-ui 无法可靠适配言奏的本地流传输与持久化边界。

### D-005 · Harness 定位

- 状态：已决定
- 决策：言奏自身是一套产品 Harness，核心投入集中在角色、记忆、语音、VRM、桌面能力与策略组合，不自研通用 Agent 框架。

### D-006 · 复用优先

- 状态：已决定
- 决策：非核心能力优先选择成熟库、Provider、协议或外部 Harness。框架已经提供稳定类型、消息格式、协议、生命周期、编码器或持久化 adapter 时，以其原生抽象作为单一来源；言奏只实现连接 SQLite、Electron IPC、安全边界和产品领域语义所需的薄适配，不建立镜像模型、重复转换层或没有真实迁移对象的兼容层。
- 理由：减少重复实现、格式漂移和升级时的双向转换成本，让框架自身承担其公开契约的演进。
- 代价：本地数据需要保存框架要求的格式标识或版本信息；框架升级仍需通过 adapter 测试验证既有数据可以读取。
- 例外：只有框架原生结构无法表达言奏的核心语义、安全要求或用户可控性，且已通过实际用例证明时，才引入独立领域模型或转换层。

### D-007 · 项目级 Agent Skills

- 状态：已决定
- 决策：AI SDK 与 assistant-ui 的官方 Skills 作为项目级开发配置存放在 `.agents/skills/`，并通过 `skills-lock.json` 保持来源一致。根目录 `AGENTS.md` 负责规定 Skill 路由、版本核实、升级和安全规则。
- 理由：快速迭代的外部框架容易因编码 Agent 的过时知识产生错误；项目级 Skills 能在不同电脑和不同兼容 Agent 之间复用维护者提供的过程知识。
- 代价：Skill 更新也属于供应链变更，必须经过来源和 diff 审查，不能自动追随最新版本。

### D-008 · 工程变更规范

- 状态：已决定
- 日期：2026-07-19
- 决策：项目统一采用严格 TypeScript 边界、语义化版本与 Conventional Commits；代码、文档、依赖和验证要求以[工程规范](../04-开发/工程规范.md)为准。自动化测试锁定为 `vitest@4.1.10`，根级 `npm test` 作为非交互统一入口；跨进程数据使用共享 Zod Schema 校验并由其推导 TypeScript 类型。格式化与 Lint 工具在出现足够代码规模后独立选择。
- 理由：先固定跨工具、跨运行时都成立的质量与协作约束，同时避免在技术验证前用脚手架反向锁定待决策项。
- 代价：当前 Node 测试不覆盖真实窗口交互、原生 SQLite ABI 或安装器行为，这些边界仍需保留 Electron 实际运行和打包验证；格式化与 Lint 暂时仍依赖人工检查和 TypeScript 编译器约束。
- 复查条件：运行时、仓库组织或发布模型发生根本变化。

### D-010 · TypeScript 服务运行时

- 状态：已决定
- 日期：2026-07-19
- 决策：使用 Electron 内置的 Node.js 主进程作为可信 TypeScript Harness 运行时；第一阶段不引入 Bun 或独立的 Node.js sidecar。
- 理由：AI SDK、数据库和桌面生态可以直接运行在 Electron 的 Node.js 边界内，降低进程编排、IPC 与打包成本。
- 代价：接受 Electron 内置 Chromium 与 Node.js 带来的安装体积和资源占用；耗时或高风险任务仍可能需要 Electron utility process 或外部 Worker。
- 复查条件：关键原生依赖无法在 Electron 中可靠运行，或资源占用无法满足目标体验。

### D-011 · 桌面容器

- 状态：已决定
- 日期：2026-07-19
- 决策：桌面容器采用 Electron。React 与 VRM 运行在 sandboxed renderer；密钥、AI SDK、数据库、文件系统和高权限工具留在 main process，通过 preload 暴露最小、类型安全的 IPC 接口。
- 理由：相较 Tauri 加 Node.js sidecar，Electron 与 Node.js/TypeScript 生态直接结合，能显著降低开发、调试和打包链路的复杂度。
- 代价：Windows x64 的 Electron 运行时本身带来约百兆级下载体积和数百兆磁盘占用，需要持续控制生产依赖与静态资产体积。
- 复查条件：实际启动、内存、安装体积或安全边界验证不达标。

### D-012 · 持久化方案

- 状态：已决定
- 日期：2026-07-19
- 决策：本地持久化采用 SQLite，驱动锁定为 `better-sqlite3@12.11.1`，Schema 与类型安全查询锁定为 Drizzle ORM 稳定版 `drizzle-orm@0.45.2`，迁移生成工具锁定为 `drizzle-kit@0.31.10`。Schema 位于 main process；迁移 SQL 生成后纳入版本控制，并由 main process 在打开窗口前对用户数据目录中的数据库执行。会话元数据沿用 assistant-ui 的 `RemoteThreadListAdapter` 语义；消息通过 `ThreadHistoryAdapter.withFormat` 保存框架提供的 `id`、`parent_id`、`format` 与编码后 `content`，不复制或解析 AI SDK 的消息模型。
- 理由：该组合符合本地优先、事务可靠、旧数据迁移和 TypeScript 开发体验要求；Electron 的构建与分发工具链可处理原生模块重建，避免引入独立数据库服务。
- 代价：Electron 升级时必须验证并重建原生模块；同步查询不得在 main process 中执行长耗时工作；标准 SQLite 文件默认不提供静态加密；`drizzle-kit` 当前开发依赖链存在 moderate 级 esbuild 审计提示，虽然不进入生产依赖，仍需在后续稳定版本中复查。
- 复查条件：原生模块分发不可靠、需要近期云同步，或明确要求数据库级静态加密而现有方案无法满足。

### D-014 · 模型运行时管理

- 状态：已决定
- 日期：2026-07-19
- 决策：模型运行时统一使用 AI SDK Provider Registry。官方供应商优先使用对应的 AI SDK Provider；自定义兼容端点使用 `@ai-sdk/openai-compatible`。言奏只实现用户配置到 Provider 实例与 Registry 的薄适配层，不自研模型协议、Provider 通用接口或重复的模型注册中心。供应商配置使用 `provider_configs`：唯一且稳定的内部主键 `id` 同时负责数据库关联并作为 AI SDK Registry 的 `providerId`，`provider_type` 作为受控判别字段选择 Provider factory；其余字段为 `display_name`、可空 `base_url`、可空 `credential_ref`、可空非敏感 `settings`、`enabled`、`created_at` 与 `updated_at`。`provider_type` 与官方 Provider 包名后缀对齐，唯一来源是共享常量 `PROVIDER_TYPES`；首批枚举覆盖 Gateway、OpenAI-compatible 和七个官方厂商 Provider。运行时使用各包公开的 `create…` factory 构建实例，并在配置变化后重建 AI SDK Registry。不使用容易与 assistant-ui 混淆的 `adapter` 命名。Provider 身份单一来源由 D-023 修订确认。
- 理由：AI SDK 已提供多 Provider 注册、统一模型 ID、模型别名、默认设置、可用模型限制、middleware 与 fallback 等运行时模型管理能力。
- 代价：不同供应商的能力、选项和模型发现接口并不完全一致；产品层仍需处理配置持久化、密钥安全、连接测试和无法自动发现模型列表的端点。以 UUID `id` 组成的内部 Registry 模型标识不适合直接展示，日志和界面必须改用 `display_name` 与 `provider_type`；API Key 与 Token 不进入该表，`credential_ref` 只引用操作系统安全存储。
- 复查条件：目标供应商无法通过官方 Provider、OpenAI-compatible Provider 或 AI SDK 自定义 Provider 接入。

### D-015 · Electron 工程工具链与打包方式

- 状态：已决定
- 日期：2026-07-19
- 决策：包管理器锁定为 `npm@11.8.0`；桌面运行时锁定为 `electron@43.1.1`；开发与代码构建锁定为 `electron-vite@5.0.0` 与兼容的 `vite@7.3.6`；可分发产物锁定为 `electron-builder@26.15.3`。当前已验证 Windows x64 unpacked 产物，安装包目标格式、签名与更新配置继续作为独立分发决策。
- 理由：项目当前是单应用，npm 能减少依赖布局和原生模块工具链的额外变量；`electron-vite` 以单一配置覆盖 main、preload 与 renderer，并适合 React 开发；`electron-builder` 提供 Windows 安装包、签名、更新和 Electron 原生依赖重建能力，能覆盖 `better-sqlite3` 的分发需求。
- 代价：`electron-vite` 与 `electron-builder` 是社区工具，不属于 Electron 官方支持的 Forge 路线；Electron 42 起不再通过安装脚本下载运行时，当前开发命令需显式确保运行时已安装；加入 AI SDK、assistant-ui 与首批九种 Provider 后的 unpacked 产物约 442.54 MiB，仍需在决定安装包格式时优化依赖与原生模块解包内容并测量下载体积。
- 复查条件：工具间版本兼容性不稳定，`better-sqlite3` 无法可靠重建或分发，Windows 签名/更新能力不满足需求，或项目演进为需要 pnpm workspace 的多包仓库。

### D-017 · 用户供应商配置

- 状态：已决定
- 日期：2026-07-19
- 决策：非敏感供应商配置通过 `provider_configs` 持久化，main process 提供经过共享 Zod 契约校验的创建、读取、更新和删除能力；内部 `id` 由系统生成并保持稳定，`provider_type` 创建后保持稳定。第一批 `provider_type` 只允许 `gateway`、`openai-compatible`、`openai`、`anthropic`、`google`、`deepseek`、`xai`、`moonshotai` 与 `alibaba`。对应官方 Provider 包已按与 AI SDK 7 兼容的稳定版本锁定；数据库配置只有在启用、凭据可解析且 factory 创建成功后才进入 Runtime Registry。
- 理由：AI SDK 已提供具体厂商 Provider、OpenAI-compatible Provider 与 Provider Registry，但 Registry 不会根据数据库字符串自动创建实例。言奏只需保存用户配置并将受控 `provider_type` 映射到官方 factory。
- 代价：部分供应商不提供模型发现接口或不返回能力类别；默认模型与角色级模型选择仍须分别实现。数据库中存在配置不等于该配置已可调用。
- 复查条件：AI SDK 提供可直接承担本地配置、凭据和动态 Provider 生命周期的稳定实现，或当前字段无法表达已确定要支持的官方 Provider 配置。

### D-018 · 系统安全凭据存储

- 状态：已决定
- 日期：2026-07-19
- 决策：API Key 与 Token 使用 Electron 43 的异步 `safeStorage` API 加密，密文按不透明 UUID 引用保存在用户数据目录的独立 `credentials/` 中；SQLite 的 `provider_configs` 只保存 `credential_ref`。凭据仓库只存在于 main process；preload 只暴露替换和清除凭据的写入式操作，不暴露读取、列举 secret 或由 renderer 指定 `credential_ref` 的能力。操作系统加密不可用时失败关闭，不降级为明文。
- 理由：`safeStorage` 复用 Windows DPAPI，并由 Electron 负责异步初始化、临时不可用和密钥轮换信号；独立密文文件可保持数据库不接触 secret，同时无需增加原生凭据依赖。
- 代价：Windows DPAPI 防护边界是当前登录用户，不能抵御同一用户权限下的恶意进程；renderer 中输入的 secret 在提交前仍短暂存在于受控表单状态，提交成功后必须立即清空。开发用真实测试密钥只允许放入被 Git 忽略的 `.env.local`，且必须使用专用测试变量显式读取。
- 复查条件：目标平台需要更强的硬件密钥保护、系统凭据管理器条目共享，或 `safeStorage` 的平台安全语义不满足要求。

### D-019 · 最小模型配置与连接验证

- 状态：已决定
- 日期：2026-07-22
- 决策：`model_configs` 保存此前确认的 `id`、`provider_config_id`、`model_type`、`model_id`、可空 `display_name`、可空 `settings`、`enabled`、`created_at` 与 `updated_at`，并对 `(provider_config_id, model_id)` 建立唯一约束；删除供应商配置时级联删除所属模型。`model_type` 与当前 AI SDK Provider Registry 的方法边界一致，首批允许 `languageModel`、`embeddingModel`、`imageModel`、`transcriptionModel`、`speechModel`、`rerankingModel` 与 `videoModel`；已有记录迁移后默认为 `languageModel`。模型发现由 main process 使用安全存储中的凭据调用供应商模型接口，renderer 只接收清洗后的只读元数据；发现结果不自动写入 SQLite，用户选择后才进入预填的模型创建对话框。无法可靠判断的能力类别保持未知，不在发现阶段猜测并持久化。模型创建界面不暴露启用开关，新记录默认启用；编辑保留原有启用值。当前 `settings` 和连接测试仍只实现语言模型边界，其他类别只可登记和区分，不能被语言模型解析器调用。默认模型不放在该表，后续由应用级或角色级配置引用 `model_configs.id`。
- 理由：Provider 配置表达连接方式，模型配置同时表达该连接下允许使用的原始厂商模型 ID 与 AI SDK Registry 模型类别；运行时可以据此选择正确的 Registry 方法，并在对应能力尚未实现时显式拒绝错误调用。语言模型使用 `provider_configs.id:model_id` 交给 Registry，不复制模型协议。
- 代价：一个模型配置当前只能标记一个类别；多类别调用、类别专属设置和连接测试要在实际接入对应能力时分别实现。AI SDK 没有跨供应商统一的无费用 ping，现有语言模型连接测试必须由用户显式触发一次受限的 `generateText`，可能产生少量费用；启动和配置保存时不得自动调用。测试结果只返回状态、耗时和清洗后的错误类别。
- 复查条件：AI SDK 提供统一连接探测，或后续模型发现与角色选择需求证明当前边界不足。

### D-020 · 基础导航

- 状态：已决定
- 日期：2026-07-22（修订）
- 决策：图标统一使用 Lucide；设置入口固定在窗口左下角。设置页外层由左侧一级 Tab 和右侧设置内容区组成，当前 Tab 包含“常规”和“模型”；模型内容区内部再采用供应商列表与模型列表双栏布局。供应商列表只展示数据库中的真实配置，不展示内部启用状态；条目悬停或聚焦时提供图标化编辑、删除操作。新增与编辑供应商复用同一通用对话框，新增配置默认启用，Base URL 示例跟随锁定 Provider 的默认端点；新增与编辑模型同样复用独立对话框，避免表单占用模型列表区域。供应商和模型删除统一使用通用确认对话框，不调用浏览器系统确认框。模型区顶部只保留多字段搜索框、图标化创建和模型获取操作；本地搜索与底部类别筛选组合生效。模型区始终保留 AI SDK Registry 七种模型类别与“全部”筛选。未来会话列表复用 assistant-ui ThreadList 行为，产品层只负责布局和清晰区分历史条目与新建操作。
- 理由：保持桌面入口和设置分类位置稳定，让供应商选择、模型管理与能力类别形成清晰层级，同时避免为尚未实现的会话列表预建视觉 token。
- 代价：固定入口、双栏设置页和未来列表仍需持续验证小窗口、大量配置与键盘导航。
- 复查条件：用户测试显示左下角入口难以发现，或时间轴在大量会话下的可用性和性能无法满足要求。

### D-021 · assistant-ui 与 shadcn UI 边界

- 状态：已决定
- 日期：2026-07-22（修订）
- 决策：聊天使用 assistant-ui Registry 成品组件，通用控件使用 shadcn/ui `base-nova`、`neutral` 默认配置，底层采用 Base UI、Tailwind CSS 与 Lucide。亮色与暗色主题直接复用 shadcn 默认语义 token，通过根元素 `.dark` 类切换，并在 renderer 本地保存用户偏好；言奏不维护产品级颜色系统、基础组件包装层或平行视觉 token。真实产品差异只在使用点通过 `className` 或最小 Registry 源码修改实现。
- 理由：明暗主题是已经出现的产品需求，shadcn 默认 token 可以直接满足；继续复用上游默认能够减少样式分叉、重复文档和升级成本。
- 代价：上游 Registry 或默认样式升级可能改变视觉，升级任务需要进行截图和交互回归。
- 复查条件：官方成品 Thread 无法适配 Electron 本地流传输或言奏核心角色体验，或者接入后的体积、可访问性与升级成本无法接受。

### D-023 · Provider 身份使用单一来源

- 状态：已决定
- 日期：2026-07-22
- 背景：`provider_configs.id` 与 `registry_id` 都被定义为唯一、稳定且创建后不可变的供应商实例身份。锁定的 `ai@7.0.31` Provider Registry 只把注册对象的字符串键作为 `providerId`，并用它查找 Provider 实例；它不要求该键具有人类可读语义。
- 决策：删除 `registry_id`。`provider_configs.id` 同时作为 SQLite 主键、模型外键目标和 AI SDK Registry 的 Provider Key；`provider_type` 只负责选择 Provider factory。运行时组合标识 `${providerConfig.id}:${modelConfig.modelId}` 仅供内部解析，不在产品界面中展示。
- 理由：保留两个同样唯一且不可变的身份会增加 Schema、校验、迁移、表单和运行时映射成本，却没有已经确认的外部引用需求。复用 `id` 仍然允许同一 `provider_type` 存在多个账号或端点，并符合身份单一来源与不提前建立兼容层的原则。
- 代价：Registry 内部标识由 UUID 组成，不适合人工阅读；诊断信息应同时记录供应商显示名称与类型。已有数据库需要迁移删除冗余列和唯一索引，但模型外键与凭据引用不变。
- 复查条件：未来出现需要跨数据库导入导出、用户手写配置或外部协议稳定引用的人类可读 Provider 命名空间。
