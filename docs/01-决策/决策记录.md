# 决策记录

本页是设计阶段的决策索引。进入实现后，影响范围较大的项目可进一步拆分为独立 ADR。

## 已决定

### D-001 · 项目名称

- 状态：已决定
- 决策：项目正式工作名称为“言奏 Katarune”，仓库标识使用 `katarune`。

### D-002 · 新项目而非原仓库重构

- 状态：已决定
- 决策：言奏采用独立项目目录。ATRI Chat 作为产品规格、行为参考、资产来源和迁移数据来源，不把旧运行时边界作为兼容目标。

### D-003 · Web 技术优先

- 状态：已决定
- 决策：主要产品界面和大部分 Harness 使用 TypeScript/Web 生态构建。需要本地原生能力的部分通过清晰边界接入。

### D-004 · 使用 AI SDK 与 assistant-ui

- 状态：已决定
- 决策：AI SDK 承担模型调用、工具调用、流式输出与基础 Agent 循环；assistant-ui 承担聊天交互框架。具体版本在创建可运行原型时锁定。

### D-005 · Harness 定位

- 状态：已决定
- 决策：言奏自身是一套产品 Harness，核心投入集中在角色、记忆、语音、VRM、桌面能力与策略组合，不自研通用 Agent 框架。

### D-006 · 复用优先

- 状态：已决定
- 决策：非核心能力优先选择成熟库、Provider、协议或外部 Harness；只有不满足核心体验、安全或可控性要求时才自研。

### D-007 · 项目级 Agent Skills

- 状态：已决定
- 决策：AI SDK 与 assistant-ui 的官方 Skills 作为项目级开发配置存放在 `.agents/skills/`，并通过 `skills-lock.json` 保持来源一致。根目录 `AGENTS.md` 负责规定 Skill 路由、版本核实、升级和安全规则。
- 理由：快速迭代的外部框架容易因编码 Agent 的过时知识产生错误；项目级 Skills 能在不同电脑和不同兼容 Agent 之间复用维护者提供的过程知识。
- 代价：Skill 更新也属于供应链变更，必须经过来源和 diff 审查，不能自动追随最新版本。

### D-008 · 工程变更规范

- 状态：已决定
- 日期：2026-07-19
- 决策：项目统一采用严格 TypeScript 边界、语义化版本与 Conventional Commits；代码、文档、依赖和验证要求以[工程规范](../04-开发/工程规范.md)为准。具体格式化、检查和测试工具在 P1 技术验证中随运行时与包管理方案锁定。
- 理由：先固定跨工具、跨运行时都成立的质量与协作约束，同时避免在技术验证前用脚手架反向锁定待决策项。
- 代价：P1 完成前部分规则只能人工检查；工具落地后需要把统一命令接入本地开发与 CI。
- 复查条件：运行时、仓库组织或发布模型发生根本变化。

### D-010 · TypeScript 服务运行时

- 状态：已决定
- 日期：2026-07-19
- 决策：使用 Electron 内置的 Node.js 主进程作为可信 TypeScript Harness 运行时；第一阶段不引入 Bun 或独立的 Node.js sidecar。
- 理由：AI SDK、数据库和桌面生态可以直接运行在 Electron 的 Node.js 边界内，降低进程编排、IPC 与打包成本。
- 代价：接受 Electron 内置 Chromium 与 Node.js 带来的安装体积和资源占用；耗时或高风险任务仍可能需要 Electron utility process 或外部 Worker。
- 复查条件：关键原生依赖无法在 Electron 中可靠运行，或资源占用无法满足目标体验。

### D-011 · 桌面容器

- 状态：已决定
- 日期：2026-07-19
- 决策：桌面容器采用 Electron。React 与 VRM 运行在 sandboxed renderer；密钥、AI SDK、数据库、文件系统和高权限工具留在 main process，通过 preload 暴露最小、类型安全的 IPC 接口。
- 理由：相较 Tauri 加 Node.js sidecar，Electron 与 Node.js/TypeScript 生态直接结合，能显著降低开发、调试和打包链路的复杂度。
- 代价：Windows x64 的 Electron 运行时本身带来约百兆级下载体积和数百兆磁盘占用，需要持续控制生产依赖与静态资产体积。
- 复查条件：实际启动、内存、安装体积或安全边界验证不达标。

### D-012 · 持久化方案

- 状态：已决定
- 日期：2026-07-19
- 决策：本地持久化采用 SQLite，驱动使用 `better-sqlite3`，Schema 与类型安全查询使用 Drizzle ORM 稳定版。具体依赖版本和迁移执行流程在 P1 原型验证后锁定。
- 理由：该组合符合本地优先、事务可靠、旧数据迁移和 TypeScript 开发体验要求；Electron Forge 可处理原生模块重建，避免引入独立数据库服务。
- 代价：Electron 升级时必须验证并重建原生模块；同步查询不得在 main process 中执行长耗时工作；标准 SQLite 文件默认不提供静态加密。
- 复查条件：原生模块分发不可靠、需要近期云同步，或明确要求数据库级静态加密而现有方案无法满足。

### D-014 · 模型运行时管理

- 状态：已决定
- 日期：2026-07-19
- 决策：模型运行时统一使用 AI SDK Provider Registry。官方供应商优先使用对应的 AI SDK Provider；自定义兼容端点使用 `@ai-sdk/openai-compatible`。言奏只实现用户配置到 Provider 实例与 Registry 的薄适配层，不自研模型协议、Provider 通用接口或重复的模型注册中心。
- 理由：AI SDK 已提供多 Provider 注册、统一模型 ID、模型别名、默认设置、可用模型限制、middleware 与 fallback 等运行时模型管理能力。
- 代价：不同供应商的能力、选项和模型发现接口并不完全一致；产品层仍需处理配置持久化、密钥安全、连接测试和无法自动发现模型列表的端点。
- 复查条件：目标供应商无法通过官方 Provider、OpenAI-compatible Provider 或 AI SDK 自定义 Provider 接入。

## 待决定

### D-013 · TTS 与 ASR 边界

- 状态：待决定
- 问题：哪些 Provider 直接迁移到 TypeScript，哪些本地 Native 能力暂时保留为独立 Worker。

### D-015 · 打包方式

- 状态：待决定
- 需要验证：Electron Forge 与其他打包工具、`better-sqlite3` 原生模块分发、安装体积、代码签名与增量更新。

### D-016 · 长期记忆系统

- 状态：待决定
- 已知问题：ATRI Chat 的文件记忆过于简陋，只作为行为、数据迁移和兼容性研究来源，不直接作为言奏的目标实现。
- 需要研究：记忆的语义模型与来源、提取与确认、检索与上下文注入、更新与冲突、遗忘策略、用户可见与可编辑性、隐私边界，以及可重复的效果评估。
- 当前约束：在完成调查和旧数据分析前，不预设 `memories` 表结构，也不把记忆系统耦合到聊天消息存储或 Agent 循环。

### D-017 · 用户供应商配置

- 状态：待决定
- 已知边界：非敏感配置持久化到本地数据库；API Key 等凭据使用操作系统安全存储；renderer 不直接接触真实凭据或创建 Provider 实例。
- 需要设计：供应商与自定义端点配置、连接测试、模型列表发现与手工维护、启用模型范围、默认模型、角色级模型选择，以及配置变更后的 Provider Registry 生命周期。
- 当前约束：该产品层只编排 AI SDK 已有 Provider 能力，不复制其运行时模型管理抽象。
