# 决策记录

本页只保留选择、关键理由和替代关系。未特别标注的条目为已决定；实现细节见对应专题，进度见[路线图](../03-规划/路线图.md)。编号与原有标题保留，历史过程可从 Git 查阅。

## 产品与协作

### D-001 · 项目名称

产品、窗口和安装包统一使用 Katarune，仓库标识为 `katarune`。以统一名称建立产品身份，不再展示中文别名。

### D-002 · 新项目而非原仓库重构

采用独立项目，不以旧工程代码或用户数据兼容为目标。这样可以按当前产品边界建立实现，不引入历史迁移负担。

### D-003 · Web 技术优先

当前界面和大部分 Harness 优先采用 TypeScript/Web 生态，本地原生能力通过清晰接口接入。技术选择服务于阶段性实现，不限制数字生命的长期载体。

### D-004 · 使用 AI SDK 与 assistant-ui

AI SDK 负责模型、工具、流式输出与基础 Agent 循环；assistant-ui 负责聊天 Runtime 和交互。复用成熟框架，升级作为独立任务；具体版本以包锁为准。

### D-005 · Harness 定位

现阶段建设产品 Harness，自研集中在角色、记忆、语音、形体、桌面能力和用户控制。通用 Agent 基础继续复用框架。

### D-006 · 复用优先

框架原生类型、消息格式、协议和生命周期保持单一来源；只在 SQLite、IPC、安全及产品语义处薄适配。避免镜像模型、重复转换和没有真实迁移需求的兼容层。

### D-007 · 项目级 Agent Skills

框架 Skills 存放在仓库 `.agents/skills/` 并锁定来源，按任务加载。安装、版本核对与升级规则集中在 [AGENTS.md](../../AGENTS.md)，避免过时 API 和供应链漂移。

### D-008 · 工程变更规范

严格 TypeScript、共享 Zod 契约、语义化版本与 Conventional Commits 作为统一基线。验证按实际变更风险选择，不把工具尚未落地写成已通过。

## 运行时与工程

### D-010 · TypeScript 服务运行时

可信 Harness 使用 Electron 内置 Node.js main process，当前不增加 Bun 或独立 Node sidecar。减少运行时编排和原生依赖变量。

### D-011 · 桌面容器

采用 Electron 管理产品界面和可信服务；React 位于 sandboxed renderer，VRM 已由独立 Unity Runtime 承担。敏感能力通过最小 preload 桥接，避免向界面开放主进程权限。

### D-012 · 持久化方案

SQLite、better-sqlite3 与 Drizzle 保存产品关系数据，迁移 SQL 纳入版本控制并在开窗前执行。消息复用框架原生持久化格式；长期记忆按 D-068 一并存入 SQLite。

### D-014 · 模型运行时管理

使用 AI SDK Provider Registry；官方 Provider 优先，兼容端点和已确定的单项能力只做薄适配。不自研通用模型协议或第二套 Registry。

### D-015 · Electron 工程工具链与打包方式

使用 npm、electron-vite 与 electron-builder；Windows 采用 NSIS。成熟工具负责归档与安装生命周期，项目只维护必要扩展，资源准备见工程规范。

Electron 在 43.x 内锁定包含 Windows 退出竞态修复的运行时，最低修复版本为 43.5.0。该竞态由 V8 延迟任务在 Node 调度器停止后继续投递触发，表现为 `PostQueuedCompletionStatus (6)` 原生异常退出；采用[上游修复](https://github.com/electron/electron/pull/53013)，不通过忽略退出码或自动重跑判定测试通过。当前精确版本由包锁维护。

## 角色、模型与数据

### D-016 · 角色级 Memory Wiki

原有实现采用角色独立的 Markdown Wiki。已由 D-068 替代，旧 Wiki 不再读写，不进行历史迁移。

### D-017 · 用户供应商配置

保存非敏感供应商配置，由 Definition 创建对应 Provider；凭据仅保留引用。只有启用且实际能力可调用的配置进入运行 Registry，数据库中有记录不代表能够调用。

### D-018 · 系统安全凭据存储

凭据由 Electron safeStorage 加密，数据库只保存不透明引用；renderer 只能替换或清除，不能读取已保存 secret。加密不可用时失败关闭，不降级为明文。

### D-019 · 最小模型配置与连接验证

模型发现优先反映真实账号库存，LiteLLM 辅助类别识别和明确的官方目录回退；未知类别由用户确认。认证失败与未知自定义端点不以公共目录伪装库存，避免错误导入或虚假可用性。

### D-020 · 基础导航

聊天、角色和设置保持清晰入口；通用图标用 Lucide，供应商品牌用随包 SVG。具体界面随现行实现维护，业务操作复用标准菜单和对话框。

### D-021 · assistant-ui 与 shadcn UI 边界

聊天组件复用 assistant-ui Registry，通用组件复用 shadcn/Base UI 和默认主题 token。避免基础组件包装层、平行颜色系统及不必要的样式分叉。

### D-023 · Provider 身份使用单一来源

`provider_configs.id` 同时作为数据库主键和 Registry Provider Key，`provider_type` 只选择 factory。内部复合模型标识不用于产品展示，减少双身份同步。

### D-024 · 角色即 Agent、活动角色与会话绑定

`characters` 是角色与 Agent 的唯一实体，会话固定归属角色；角色 Runtime 独立，界面切换不取消其他角色的后台运行。角色包展示已按 D-064 替代旧裁切交互，历史记录不作为现行 UI。

### D-025 · 通用资产注册表与托管协议

资产元数据与不可变托管文件分离，使用受限资产协议访问。稳定 ID、内容哈希和引用回收支持恢复与删除，避免 Base64 持久化和真实路径泄露。

### D-026 · Electron 本地 AI 消息流

每个线程和运行独立管理原生聊天传输，通过 MessageChannel 提供背压和取消。复用 AI SDK/assistant-ui 的格式，不增加本地 HTTP 服务或镜像流协议。

### D-027 · 统一工具平面

沿用 AI SDK 与 assistant-ui Toolkit 聚合工具。前端只上传受校验的名称、描述和 Schema，不能覆盖可信同名工具或取得 main 执行权限。

### D-028 · 本地附件事实来源与按需物化

本地托管附件是唯一事实来源，当前消息临时物化，历史图片按需读取并复验会话归属。不持久化 Base64，也不预建 Provider Files API、远端引用或上传缓存。

### D-029 · 动态上下文、工具提示与缓存边界

角色规则保持稳定，main 将当前日期和 IANA 时区作为原生 call options 加入模型上下文；精确时间按需调用工具。工具专属和高频执行状态留在各自作用域，缓存策略须按 Provider 实测。

### D-030 · Renderer 统一通知中心

页面瞬时反馈使用 Toast，需在当前表单修正的错误使用作用域 Inline。通知不替代业务状态、不持久化，避免重复反馈和常驻成功文案。

### D-031 · 单次生成式 TTS、角色声音与派生缓存

TTS 作为独立 Capability，模型和音色由可信服务解析，音频是可再生缓存。后续流式交付和 Unity 播放由 D-056/D-057 扩展；音色元数据及用户默认值以 D-033 为准。

### D-032 · 首版桌面分发、安装卸载与更新策略

Windows 首版采用 `app.katarune.desktop`、x64、per-user NSIS 离线安装器与薄 Win32 绘制扩展。默认卸载保留个人数据、更新不清理数据；全部删除须显式选择并检查链接目录和文件占用。旧 Qt 安装须先正常卸载，不能混用引擎文件清单。在线更新与发布后端尚未接入；公开发布前完成 Windows IV Authenticode 云 HSM、SHA-256/RFC 3161 时间戳，以及 macOS Developer ID、公证和 Stapling。证书供应商资格与采购仍待确认，当前内部包无签名、不自动公开。

### D-033 · Provider 自主发现与模型级音色元数据

发现和检查由各 Provider Definition 自主实现；可刷新的模型 metadata 与用户 settings 分离，刷新不覆盖用户默认值。音色是模型级元数据，目录只辅助选择，所有语音模型允许手动 Voice ID，供应商负责判断实际有效性。

### D-034 · 应用默认模型与设备级常规偏好

角色专用模型优先于应用默认；显式选择不可用时不得静默回退。主题、自动朗读和减少动态效果属于设备偏好；产品模型设置进入 SQLite，避免将全部配置塞入通用 KV。

## 形体与行为

### D-035 · Unity VRM 渲染技术验证基线

数字形体采用独立 Unity、URP、UniVRM 与窗口控制组件；现行运行时仅支持 VRM 1.0。复用成熟模型适配与渲染能力，避免 Web 和原生运行时重复实现骨骼驱动。

### D-036 · Unity 程序化形体第一阶段

程序化待机方案已由 D-050/D-064 的资源基线替代。标准化形体接口仍沿用，但不把历史呼吸、摆头或阶段状态当成当前默认表现。

### D-037 · Unity 原始材质与桌面灯光基线

保留模型原始材质，柔和描边作为可逆选项，灯光与抗锯齿由场景管理。避免为了统一外观破坏角色素材，实际观感按模型验收。

### D-038 · Unity Runtime Facade 与模型事务边界

Facade 和带 revision 的 Snapshot 是统一控制与权威状态边界，模型更换使用 prepare/validate/commit 事务。失败保留旧模型，Core、Motion、UniVrm、Runtime 职责分开。

### D-039 · Unity 预设动作第一阶段

早期固定预设动作入口已由 D-052/D-064 的资源清单替代。连续混合、取消与单一动作播放器边界保留，不在运行时增加角色名称或固定动作枚举分支。

### D-040 · Unity UI Toolkit 桌宠 HUD

已废弃：Unity 产品 HUD 由 D-063 的 Electron 胶囊与面板替代。Unity 继续负责角色窗口、操作区、音频和字幕。

### D-041 · Unity 角色行为 Core 最小领域边界

行为请求、定义、计划和实例保持分离；计划及权威实例由 Unity 内部构造。Core 不引用 Clip、Provider 或模型格式，避免资产与宿主倒灌到领域层。

### D-042 · Unity 行为资产定义与通用 Humanoid 播放边界

复杂行为资产以版本化 `.kbehavior` 定义并严格导入，保存能力、通道、片段、退出和许可信息；Motion 通过 Humanoid Binding 播放。用户角色包另按 D-064 使用 VRMA，不建立第二套播放器。

### D-043 · 桌面态语音陪伴与文字对话双模式

原桌面双模式方案已由 D-061/D-063 替代。角色和会话继续共用；“进入世界”与具体玩法仍是后续探索。

### D-044 · Unity 三样片资产表达与安全退出锚点

三份历史样片已退役，保留其证明的约束：通道和 Mask 必须符合素材实际覆盖，安全退出须连接合法姿态，许可按具体素材核验。不能借用旧样片通过记录证明新素材合格。

### D-045 · Unity 行为调度器与单 PlayableGraph 接管边界

Core 调度器唯一授予与释放通道，Motion 在同一播放图执行动作和恢复。手动动作与调度身体实例互斥；取消、终态回收和队列提升保持幂等。

### D-046 · Unity 提供表演工具与 Agent 完成屏障

Unity 提供实际可用的形体能力，宿主适配为受信任工具，不复制能力目录。工具化对白与 Agent 完成屏障部分已由 D-054 替代：请求接受和实际播放完成分开。

### D-047 · 退役历史 Quiet Idle，重新建立默认姿态基线

历史 Quiet Idle 与临时静止基线已退役或被 D-049/D-050 替代。资源缺失按当前兜底规则处理，不恢复旧程序化阶段或旧测试素材。

### D-048 · 桌面角色展示采用角色转台与投影构图

当前桌面角色通过投影构图调整，调试转台和预览服务于模型/资产验收。世界玩法与物理交互不在此条提前确定。

### D-049 · 待机微动改为身体驱动二级物理

程序化呼吸/摆头主驱动已由 D-050 替代。模型二级物理仍独立运行，不把环境风等同于已完成角色专属待机美术。

### D-050 · 本机测试默认待机改用 VRMA 资产

本机曾使用 VRMA 验证默认循环与手势；当前系统动作由 D-064 角色包清单决定。默认动画未配置时保持静态姿态，不假定旧本机动作存在或可分发。

### D-051 · 手动动作采用 Unity 原生连续打断混合

手动动作采用 Unity 原生连续权重混合；连续打断保留当前贡献，重复选择不无条件重播。复用既有 PlayableGraph 和取消边界，不增加动画库或并行过渡层。

### D-052 · 外部 Humanoid 动画资源包

现有 Humanoid 动作可由外部 `.motionpack` AssetBundle 提供，动作按稳定 ID 和实际清单登记。包受 Unity 版本/平台约束；用户角色包格式以 D-064 为准。

### D-053 · 文本优先的 AI 角色控制与输入排队

文本控制闭环已完成；工具化 `speak` 与按句阻塞方案已由 D-054 替代。普通聊天保持原生文本与现有 Agent 循环。

### D-054 · Unity 消费原生 Agent 事件流

完整转发原生聊天事件，由 Unity 建立对白、表情和动作时间线；工具执行回调只等待接受确认，播放终态另报。Agent 完成不等待播放排空，后台 drain 只管理资源回收，不重复执行流中的工具事件。

### D-055 · Unity 从启动即覆盖显示器的无边框窗口

Unity 从启动即覆盖目标显示器的物理屏幕，以透明窗口和局部命中实现桌面形体。角色构图变化不等于窗口几何变化；布局归属见桌面交互设计。

## 语音、桌面与资产

### D-056 · uLipSync 实时语音口型

对白音频和时间戳补入原生对白节点，由实际 AudioSource 驱动字幕与 uLipSync。音色 Profile 独立于 VRM，唯一口型平滑和停止清零避免重复驱动。

### D-057 · 完整文本输入与增量语音交付

完整文本输入后增量交付 PCM，独立管道和有界缓冲控制消费。断流冻结有效音频位置，迟到对齐不提前翻页；只缓存完整校验产物，不能以网络读取量当作播放时钟。

### D-058 · 首版离线语音输入

离线 ASR 采用 SenseVoiceSmall INT8、Silero VAD 与 Electron utilityProcess。识别权重显式下载并纳入内部包，麦克风音频不默认保存。

### D-059 · 按能力配置默认模型与语音双选

应用默认对话模型、TTS 模型与音色可被角色分别继承或固定，ASR 为全局配置。调用时由 main 解析和校验，不在前端建立另一套默认值规则。

### D-060 · 桌宠自动轮流语音对话与常驻识别模型

模型常驻和离线断句沿用；长按开启、播放时停止收音与轮流门控已被 D-061 替代。现行语音生命周期由唯一采集端管理。

### D-061 · 桌宠全双工语音与确认式插话

播放期间持续采集，疑似人声先暂停，最终文字确认才打断旧播放，误触恢复；语音输入优先于未发送文字。绑定校验、外放防自触发、旧生成收尾与运行 ID 清理避免跨会话误控制。

### D-062 · 紧凑图标栏与单层 Tab HUD

已废弃：紧凑 Tab HUD 由 D-063 的单层 Electron 面板替代。当前控件与快捷键只在桌面交互设计维护。

### D-063 · 桌宠窗口分工与紧凑面板

Unity 拥有角色、播放和字幕；Electron main 管理胶囊、面板、显示器、布局与绑定，不建独立字幕窗口或第二时钟。具体交互以 [桌面交互设计](../00-项目/桌面交互设计.md) 为准。

### D-064 · 角色包与资源管理边界

角色包组合立绘、VRM 1.0 与系统/自定义 VRMA；作者不指定全局 ID，main 生成身份、托管资源并做内容去重，Unity 实际验证与整体激活。契约和失败回滚只在 [角色包格式](../02-架构/角色包格式.md) 维护。

### D-065 · 固定站姿与模型适配的待机兜底

已决定：角色包有 `idle` 时直接播放；缺失时由 Unity 应用内置的归一化固定人体站姿，按模型的 Spring Bone、外形、蒙皮及碰撞代理生成并缓存次级骨骼循环。默认包配置公共人体待机 VRMA，另保留两段待机变化；其 Spring Bone 跟随身体运动。持续环境风移除；兜底烘焙循环播放时暂停 Spring Bone 写回，播放预制动作时恢复物理，不让两套更新同时驱动相同骨骼。

默认模型的无 idle 兜底在分发构建前预烘焙；用户包缺少 `idle` 时，导入阶段在独立 Unity 验证进程中异步烘焙并缓存，完成后才发布角色包。取消终止准备进程，当前角色继续播放；激活时读取缓存。缓存按模型内容和姿态/运动配置校验，版本变化后重新生成。

理由：固定人体基准和稳定的次级周期运动可分别控制，并避免依赖 Python 或原角色专用骨骼。代价：导入准备时间增加，代理碰撞与骨骼分类为近似；不能适配的链保持参考姿态，完整网格碰撞与其他真实模型的表现需复查。它不是原神算法的已验证复刻。

### D-066 · 动作语义与播放实例分离

已决定：保留系统动作与自定义动作的区分。系统使用固定语义，自定义允许作者声明包内名称或编号；内部身份与播放实例由应用管理。两类入口共享 Unity 行为调度，支持一次性动作与进入／循环／退出的持续行为，以及独立的头部、表情、视线和口型通道。

AI 可以明确切换持续姿态、结束或取消行为；同一实例的重复请求不重启进入段。节奏控制只用于自动装饰动作和重复触发，不对明确的姿态切换施加固定冷却。资源不足时回报不可用，不将动画文件名当作完整能力。v2 契约、身体分段循环及独立头部／上半身混合已接入；当前未发布，移除 v1 读取分支，已有本地数据不自动迁移或删除。缺少资源的旧预设别名不进入新契约。默认资源与混合规则分别维护在角色包格式、角色行为与动画系统。

头部使用经参考姿态归零的增量，上半身遮罩保留当前髋部与腿部。只有需要保持身体姿态的手势提供裁切版本，完整源动作仍可选；跳跃、蹲起等全身协同动作不裁切。代价是遮罩手势不保留源动作的下半身配合，最终观感须在目标模型验证。

手动与 AI 循环切换均先播放旧退出段，再进入新循环；快速连续选择只保留最新请求，强制取消仍立即生效。视线在动作合成后独立叠加头颈跟随，眼球补偿原动画转向。代价是切换等待退出段，视线与大幅头部表演的最终观感仍需检查。

同通道一次性动作打断持续姿态后，保留原实例并重播 enter 再回到 loop，避免直接跳回中途姿态；未被打断的独立通道继续推进。代价是恢复耗时包含进入段，缺少 enter 的素材只能从 loop 起点混合返回。

### D-067 · 按对白锚点编排角色表演

已决定：AI 使用 `avatar_perform` 一次提交动作、表情及语义触发关系，使用 `avatar_control` 控制已接收的表演。Main 校验当前角色能力与会话绑定，解析动作身份；Unity 将提示点绑定到紧随工具之后的原生文本块，复用 Facade 和现有通道调度，不复制骨骼或动画状态机。

AI 与 Unity 共用平铺步骤格式，Main 仅将可用动作名称解析为运行时身份，不再转换成另一套节点协议。Unity 按列表顺序解析动作依赖并生成状态标识；不让模型维护引用图或内部播放命令。对白结束只请求完整收尾：一次性动作播完，循环姿态播完入场及当前循环后退出。用户取消保留立即停止语义。

AI 只选择表情名称，Unity 统一应用 100% 强度，工具与传输不携带数字权重。界面按接收确认及 Unity 实际状态显示结果，不将缺少摘要误判成执行失败，不为未发布的旧摘要维护兼容分支。错误直接沿用原生消息，参数校验由 AI SDK 与共享 Schema 承担，不在工具执行回调中重复解析。普通工具的 Agent 循环仅在 Main 执行，前端不因工具完成额外发起一轮请求，也不按工具名称维护例外。

对白仍以原生正文为唯一来源。句子触发跟随实际语音游标与可用时间戳，无声对白跟随阅读进度；动作依赖等待真实终态。工具接收确认与表演终态分开，前端使用可展开摘要显示安排，并按 Unity 回报更新当前状态。

理由：减少逐项工具调用，让同一段对白内部可以连续切换表情并组合动作。代价：句子按固定标点规则识别；无时间戳的完整音频采用时长比例近似，流式对齐未覆盖的位置等待；循环姿态默认限定于该段对白，跨回复持续表演另有真实需求时再扩展。

### D-068 · 日记、人物与纪事

角色记忆由 SQLite 保存 Markdown 正文、稳定标识、版本；与现有产品数据库共用事务和角色生命周期，不引入 Python 或外部记忆服务。人物记录用户及其他人的独立画像；纪事记录经历、约定及进展；日记按本地日期回顾当天值得留下的相处。首版不维护条目间的关联表或关联 ID，人物关系、纪事进展与时间直接写在正文中，AI 按关键词检索需要的背景。记忆条目不再单独存储创建时间或纪事状态；仅保留归属、分类、标题、正文、日记日期、用户本人标记、更新版本与时间和遗忘标记。不保存记忆到原对话的来源引用；日记任务只保留处理当天消息及每日去重所需的队列和状态。遗忘让该条记忆退出检索，不删除原聊天，也不追溯并屏蔽原消息。

对话提供 `memory_search`、`memory_read`、`memory_save`、`memory_forget` 四个工具；保存与遗忘分开，工具参数采用根级对象。人物和纪事按需即时更新，更新须匹配版本；小型目录注入上下文。搜索固定最多返回六条，800 字以内的正文完整返回并携带版本，长正文返回片段及截断标记，按需进一步读取；取得完整正文和版本后可直接更新，不重复搜索或读取。保存成功只返回标识和新版本；重复条目返回已有标识，版本冲突提示重新读取。对话与日记 Agent 复用只读工具的返回格式，日记 Agent 的搜索和读取均限制为人物与纪事。工具绑定受信任的当前角色，不接受模型指定角色。用户可在记忆页编辑和遗忘，遗忘内容退出检索与上下文。

日记由 main 中独立的 AI SDK Agent 使用角色当前生效的语言模型整理，携带角色设定，以第一人称回顾当天文字对话；提供检索、读取人物与纪事的两个只读工具，以及无执行副作用的 `finish_diary` 终止工具，用于提交草稿。使用工具参数 Schema 校验输出，不使用 `Output.object` 的 JSON Schema 响应格式，避开 DeepSeek Provider 的结构化输出兼容警告；不全局关闭 SDK 警告，也不强制工具选择，以保留思考模式兼容性。正文保持纯文本／基础 Markdown，不扩展图片、附件和 HTML，不新增媒体存储。应用运行时在本地次日 00:01 触发，启动时补处理待整理日期；同一角色、同一日记日期只自动尝试一次，没有值得记录的内容则跳过，失败或中断由用户手动重试。一次 Agent 任务可以包含多轮模型与工具调用。只处理启用后排队的消息，不扫描旧 Wiki；输出按 Schema、角色归属和当天对话变化校验后由程序保存。失败任务仅持久化受控原因分类，不保存供应商原始错误或响应；界面显示最近失败日期、原因和重试入口，历史失败未记录原因时明确说明。后台可能调用用户配置的供应商，界面显示开关和失败状态。

入口放聊天侧栏左下工具区，页面沿用现有黑白灰样式，提供「日记／人物／纪事」和角色归属；日记以素色笔记本页面呈现日期；左侧目录切换日记，长文在纸页正文区域连续滚动，不提供分页或页码。阅读与编辑共用同一个 Tiptap 实例、标题布局与滚动容器，仅切换可编辑状态，切换时保留滚动位置。使用本地富文本与 Markdown 扩展保留基础排版和撤销能力，持久化仍为 Markdown，不另存 HTML 或编辑器文档模型；当前需求不需要更换存储格式。保存须匹配版本，冲突时保留草稿；编辑期间不切换条目或离开页面。列表自动更新，不提供回收站入口或刷新按钮；每日生成日记仅保留一行开关，失败时显示重试。当前检索采用中文可用的字面关键词匹配，不引入向量服务；语义检索按真实召回需求另行评估。

### D-069 · 沉浸模式与预设镜头

已决定：在既有 Unity 角色窗口切换桌宠／沉浸模式。沉浸模式使用不穿透的全屏应用窗口，提供俯视、居中与近景预设，镜头与背景柔和过渡，退出恢复桌面构图。背景在 Unity 内以纹理和 Shader 绘制，延续参考背景的斜向排版与流动条带，以 Katarune、讲述、记忆、陪伴和共同探索的意象替换游戏内容；不嵌入 HTML、不新增 WebView 或视频依赖。

Electron 只提交模式与镜头意图、显示切换入口；Unity 继续拥有镜头、背景、原生窗口及输入。模式不写入桌宠布局偏好，重启回到桌宠；不改变对话、语音、表情、动作或模型资源，不扩展场景漫游与新的角色行为。多屏、Alt+Tab、退出恢复与实际镜头观感需分别验证。

### D-070 · 按动作配置播放独立舞蹈

已决定：保留 `avatar_perform` 的对白动作编排；独立舞蹈使用 `avatar_play({ action })`，只选择当前角色实际提供的舞蹈标识。舞蹈复用角色包自定义动作及稳定身份，播放定义使用 `kind: dance`，包含 VRMA 与可选伴奏、SRT 音乐字幕、按时间切换预设机位的配置。伴奏格式跟随现有 Unity 播放器的实际解码能力，保留原文件，不要求使用者转为 WAV；导入与实际播放使用同一解码边界。未配置媒体合法，已配置但无法加载则失败；AI 不选择配乐、字幕颜色、镜头、文件路径或播放时长。

Unity 负责准备资源、实际启动和结束后的姿态／镜头恢复。伴奏使用独立音频通道，不驱动口型；有伴奏时按实际音频游标采样动作、字幕与镜头，无伴奏时使用 Unity 播放时间。音乐字幕使用粉色，保留原有暗底以便阅读；演出期间的声音与字幕占用按 D-074 执行，空白间隔和舞蹈终态清空歌词。独立舞蹈不绑定下一段对白，不随模型生成结束或普通对白排空而停止。切换会话、卸载或停止桌宠仍释放在途舞蹈；身体动作冲突明确拒绝。

VRMA 加载器按 1.0 标准支持人体、预设／自定义表情及视线轨道，继续验证自包含资源与合法轨道结构。舞蹈期间素材独占身体、表情和视线，未提供的面部与视线保持中性；停止程序化呼吸／摆动、自动眨眼、鼠标视线跟随、情绪和语音口型写入，结束、中断或失败后恢复；Spring Bone 的头发与衣服物理保留。普通动作仅覆盖实际声明的轨道，不更改其他普通行为，表情和视线不另建过渡状态。理由是完整舞蹈应保留素材本身的时序与表达，避免运行时自动控制覆盖其演出；代价是舞蹈期间不会呈现独立的 AI 表情、视线和语音口型，最终效果需在目标 VRM 上验收。轨道留在 VRMA 内，AI 仍只选择动作标识，不扩展工具参数。

工具返回接收确认与完整生命周期按 D-074 执行，不阻塞整支舞；实际状态通过现有可信管道回报，在界面显示，并作为有界的同会话真实状态加入后续模型调用。最小范围不添加暂停、继续、状态查询工具或完成后自动唤醒模型的调度。首次验证使用隔离合成素材，真实舞蹈的观感单独验收。

### D-071 · 舞蹈镜头轨道

资源格式由 D-073 替代；同步与恢复机制沿用。

已决定：舞蹈可引用独立的 `cameraTrack` JSON 资源，与预设 `camera` 互斥。制作阶段将 VMD 镜头的位置、四元数、垂直视角及透视／正交投影烘焙为时间采样，保留切镜；运行时不导入 MMD 工程。轨道使用 Unity 坐标，原点为角色脚底中心，通过参考身高适配目标模型。Unity 以舞蹈的同一音频／播放游标采样，不对原轨道再加平滑；结束与中断恢复播放前的完整投影和构图。Main 只校验、管理资源与传递路径，AI 工具仍只选择舞蹈。

理由：VMD 自带镜头曲线和切镜，三个机位不足以表达；离线烘焙可以复用现有制作工具的曲线求解，避免在运行时重写 MMD 插值与坐标系统。代价是新增有界镜头资源，采样精度和原镜头匹配须在制作时核对；不同时扩展场景、灯光或通用 MMD 运行时。

### D-072 · 统一角色包动作库与动作筛选

已决定：角色包使用 v3，所有动作在 `actions` 中定义一次；`idle` 引用基础循环与待机变化，`bindings` 将固定用途绑定到包内动作。包内 `key` 使用稳定的小写连字符名称，显示名称可以修改；全局动作 UUID 由系统分配。`playback.kind` 为 `oneShot`、`loop`、`performance`，主动画统一使用 `motion`；同步演出的镜头统一放在带 `kind` 的 `camera` 配置。全身、上半身和头部继续作为独立作用范围。

默认包按 `avatar/` 与 `actions/<key>/` 组织文件，原有动作与音乐时序保持。桌面动作保持原下拉样式，弹层顶部增加单次动作、循环动作、舞蹈演出三个筛选标签；仅列出可用动作，选中态跟随实际播放；再次点击当前播放项停止该动作，其他通道继续运行，全部停止后回到待机。手动选择其他有效动作会中止当前舞蹈，包括配乐、歌词和镜头，并切换至所选动作。待机素材归入对应播放类型。动作库同时供导入校验、包详情、AI 和播放器使用，自动待机素材不进入 AI 可调用清单。

理由：消除系统动作、自定义动作和待机之间的重复结构，使资源、动作定义与使用规则各有明确职责。代价是旧清单需重新制作导入；已有导入记录保留，不自动迁移历史包。默认包随应用刷新，并保留现有自定义动作的全局身份。D-070 与 D-071 的播放机制沿用，清单字段以本决策为准。

### D-073 · 面向创作者的 GLB 镜头交付

已决定：连续镜头以自包含的 glTF 2.0 GLB 交付，取代包内私有 JSON 采样资源。复用 UniGLTF 的文件与访问器解析，使用标准节点动画和 `KHR_animation_pointer` 表达相机参数动画，支持 LINEAR、STEP、CUBICSPLINE。包清单只保存资源引用、可选参考身高和镜头／动画选择；跨相机切换由清单中的镜头段指定。VMD 通过离线制作入口转换为 GLB，运行时不引入 MMD 依赖。两支默认舞蹈一并迁移，音乐、歌词与动作时序保持。

理由：创作者可以在 Blender 等工具中制作、导出和重新编辑镜头，避免学习私有轨道格式。代价是补充标准镜头动画读取及有界校验，明确工具导出选项和跨相机切换约定；GLB 本身不规定演出使用哪台相机。D-071 的同步与结束恢复机制沿用，资源格式以本决策为准。

### D-074 · 完整演出的呈现占用与对白投递

已决定：原生消息继续由 AI SDK 与 assistant-ui 生成、展示和持久化。Unity 统一协调对白与完整演出的启动顺序、声音和主字幕占用；Main 仅在取得对应对白的出声许可后启动 TTS。普通动作继续绑定原生对白，不新增 speak 工具或另一份台词。

`avatar_play` 接收后返回 accepted，前面的引导对白实际播完才准备、启动舞蹈。后续正文以及演出期间的新回复只进入聊天记录，不合成语音、不显示为角色字幕，也不在演后补播。歌词空隙保持空白；用户输入反馈保留在聊天区域。Unity 回报 accepted、preparing、started、completed、cancelled、failed；生成结束不等于演出结束。

`avatar_control.cancel` 同时支持日常编排与舞蹈，停止并释放占用后才允许后续新对白出声；finish 只支持日常编排的自然收尾。演出已安排或播放期间拒绝新舞蹈及日常动作／表情编排，重复工具调用幂等。每步模型生成读取最新演出状态；完播只更新状态，不自动唤醒模型。会话切换、卸载和停止清理旧占用，迟到事件不能恢复旧对白。

理由：避免伴奏与对白混播、歌词被覆盖及过时回复积压。代价：演出期间默认通过聊天文字交流，明确停止后恢复角色出声。替代 D-070 的对白优先字幕规则与工具等待实际启动的返回语义；素材时钟和独立演出生命周期沿用。

### D-075 · 统一本地结构化日志与故障关联

已决定：Main 统一收集结构化事件，经专用写入线程持久化 JSONL；renderer、preload、ASR 与 Unity 通过现有受校验通道提交事件。复用框架及业务已有运行／请求／工具／演出标识关联链路，错误在负责处理的边界记录一次，内部保留 cause，界面使用安全提示和可复制的故障编号。

可预期的操作拒绝由可信代码显式标记，记为 WARN、`outcome=rejected` 和白名单 `reasonCode`，不生成故障编号；真正的运行故障保留 ERROR/FATAL。只把外部请求入口的 Schema 校验失败转换为 `invalid-input`，不按异常名字或自由文本猜测分类，不将内部数据／返回值校验失败降级。关键消息式入口同样记录拒绝；重复拒绝有界汇总，不承诺完整安全审计。

采用锁定版本 electron-log 5.4.4 作为写入与滚动组件，项目薄适配仅负责事件 Schema、上下文、脱敏、限流和保留策略。保持本地诊断，不默认接入远程收集，不引入完整 OpenTelemetry 运行栈；字段含义参考其日志模型。异常处理、日志与原生崩溃转储分别设计，捕获异常不代表可继续安全运行。

理由：当前控制台、Unity 文件与界面提示相互割裂，部分 catch 丢失原始原因，无法在偶发故障后还原链路。代价是接入各运行边界、维护安全字段白名单，以及覆盖日志故障和资源上限。详细评估与契约见[技术选型](../02-架构/技术选型.md#日志与诊断)，故障注入验收见[工程规范](../04-开发/工程规范.md#日志与诊断验证)。库同步传输仅在专用线程执行，主线程用有界队列及批次确认提供背压；不依赖库内部无界异步队列。

### D-076 · 通过本地音视频流接入直播软件

已决定并接入：直播输出采用本机 RTMP 音视频流，由哔哩哔哩直播姬的「多媒体」来源或 OBS 媒体源拉取，直播软件继续负责场景组合与平台推流。复用现有角色、镜头、背景和字幕能力生成直播画面，语音与舞蹈配乐按既有播放规则合成；直播输出不依赖沉浸窗口占据屏幕或保持前台。

界面仅保留源分辨率、本地端口与拉流地址，最终平台码率和帧率在直播软件中配置。本地 RTMP 素材仍需独立编码，由 main 统一提供 60 fps、按分辨率管理的码率，不接受 renderer 提交编码参数。预览复用原尺寸合成帧，不另设分辨率或帧率上限；有界队列与确认背压只防止慢接收端积压，离开页面或最小化时停止预览传输。

理由：使用者主要使用直播姬，多媒体拉流能同时接入画面与声音，不要求虚拟摄像头或 OBS 中转。采用固定版本 FFmpeg LGPL shared 构建编码 H.264／AAC、MediaMTX 提供回环 RTMP，随 Windows 包携带 DLL、许可证、来源和校验清单；Windows Job Object 监督程序回收子进程。代价是编码开销、缓冲延迟和额外资源体积。Unity 以音频累计采样为时间基准，独立二进制管道传递媒体；本机监听在采集后静音。真实接收端、持续运行及使用者体验仍按路线图分别验收。

### D-077 · 直播复用角色会话与后台主持

已决定并接入：直播是角色的独立会话，每次手动启动仅分配会话标识，首条消息产生时才保存 `kind=live`，重连沿用当前会话。复用普通对话的会话初始化与消息写入接口，由主进程在同一事务中保存直播会话和首条消息；无消息的测试启动或失败不落库，有输入但回复失败的会话仍保留。普通会话迁移为 `chat`，归档状态保持独立；直播记录进入原会话列表，只读查看，沿用原有标题与角色长期记忆、日记流程，不增加场次标题表或独立 Agent。

Main 通过哔哩哔哩官方开放平台接入弹幕、礼物与开下播事件，凭据本机加密保存。必须同时满足媒体就绪、官方连接有效、官方确认开播，才按间隔合批交给现有 ChatService／AI SDK；Unity 播放排空后才开始下一轮。未知状态不猜测为开播，观众文本不能变成官方礼物或宿主指令。

理由：直播与日常伙伴共用角色能力，但各场有独立上下文和可审阅历史。代价是后台调度、角色播放占用及停止恢复。直播期间日常会话只使用文字，胶囊与桌面控制停用；不实现平台自动开播、点歌、礼物权益、云端凭据服务或其他输出协议。

### D-078 · 直播保留官方接入并增加网页直连

已决定：官方开放平台与网页直连由使用者显式选择，不自动降级或切换。连接配置确认后锁定，进入页面自动检测；手动断开清除连接配置及凭据引用并返回配置入口，才可重新选择方式。网页登录 Cookie 沿用本机加密凭据存储；renderer 只读取是否已保存。网页连接使用 B 站房间信息、WBI 签名与消息 WebSocket，复用既有心跳、重连、去重及主持调度，平台礼物仅来自识别并校验的礼物消息。

理由：个人使用可用房间号与可选登录态接入，无需先取得开发者项目。代价是网页协议、登录态和访问校验变化需要维护；匿名模式可能缺少用户信息。网页模式在消息鉴权后查询实际开播状态，并接收后续开下播通知；未知状态仍不启动主持。新增固定版本 `protobufjs` 8.0.0 解析新版弹幕与批次礼物，避免自行实现 Protobuf 解码器；HTTP、签名、压缩与传输继续使用现有能力。

### D-079 · 直播共享编码与播放器同步预览

已决定：保留桌宠播放和直播姬 RTMP 接入，默认源画面为 1080p60，保留已有分辨率选项。直播在角色更新完成后采集，沿用现有 URP 抗锯齿设置，使用有界异步回读流水线；音频累计采样仍是素材时间轴，在音频块之间插值以独立调度视频帧。优先使用经过实际预检的 NVENC，否则预检 Media Foundation 硬件编码，不静默使用高负载软件编码。FFmpeg 的 tee 复用一份 H.264/AAC 编码，分别封装 RTMP 和以关键帧开始的分段 MP4；后者经受限 IPC 交给 Electron MediaSource 与 video 同步播放。监听在固定的 Web Audio 音频图中调整输出增益，保持音轨与播放时钟连续，不切换 video 或窗口的静音状态；关闭预览后断开音频图并挂起音频上下文。Unity 直播输出采集后始终静音；普通桌宠播放不变。

理由：逐帧 JPEG 预览重复消耗 CPU，且直接监听与图片传输没有共同播放调度。共享编码避免第二次视频编码，使用内置播放器管理音画时钟，不新增媒体库、监听端口或协议服务。预览确认只等待媒体写入，不等待可能依赖后续片段的播放启动；监听只调增益，避免静音开关扰动音频输出状态。代价是预览需要短暂分段缓冲；慢预览允许从下一个关键帧重新接入，不能阻塞 RTMP。原尺寸和源帧率保留，离页和最小化停止预览传输。实际同步、持续负载和接收端效果分别验证，不用编码帧率代替新画面帧率。
