# 角色行为与动画系统

> 状态：讨论中。本页是 Unity 角色行为、动作与模型适配架构的主设计草案。候选方案不会自动成为已决定事项；稳定结论确认后再同步到决策记录、技术选型和路线图。

> 当前基线校正：2026-09-09。A 至 D 的历史验证记录与当前运行能力分开阅读；现有通用动作播放、外部资源包和调试转台已实现，Electron/Unity 协议、真实语音协调与最终产品交互仍未完成。

实施阶段、交付物与验收条件见[角色行为与动画系统推进计划](../03-规划/角色行为与动画系统推进计划.md)。

## 文档目的

言奏需要把模型回复、语音、用户事件和角色设定转化为持续、自然且可打断的数字角色表演。本页用于确定这套系统的长期边界，使新增角色和动作主要通过能力清单与资产扩展，而不依赖全局角色阶段或动作名称分支。

## 一句话目标

Unity 是言奏的角色形体与表演运行时，而不是 AI 大脑：Electron 提交高层角色意图，Unity 在实时约束下完成调度、混合和逐帧驱动，并返回可观察的执行状态与结果。

## 期望的最终体验

角色以透明桌面形态持续存在，能够自然地待机、倾听、思考和说话，并将语音、口型、表情、视线、手势与身体动作协调为完整表演。角色可以执行挥手、解释等短动作，也可以执行跳舞、唱歌或剧情演出等长时间轴动作；用户打断时，系统根据动作策略立即退出或在安全节点自然收束。

AI 不直接控制骨骼、动画帧或混合权重。它只表达角色意图、语义动作和必要的时间约束。确定性的运行时拥有当前状态、通道所有权、优先级、抢占、混合和回退控制权。

## 目标系统边界

```text
Electron / Katarune Harness
├── 对话、记忆、Agent 循环、用户与桌面事件
├── TTS / ASR Provider、凭据和取消
├── 将 Unity 公布的能力注册为受信任 AI 工具
└── 管理 Unity 进程生命周期与可信传输

Unity Avatar Presentation Runtime
├── Capability Tool Provider：公布工具、参数 Schema 与当前可用枚举
├── Protocol Adapter：接收工具调用与控制命令并返回结果、事件和快照
├── Behavior Scheduler：排队、优先级、抢占、取消和安全打断点
├── Presentation Graph：身体、手势、表情、视线、口型和程序化附加层
├── Character Rig Binding：向上暴露稳定的形体控制能力
├── Model Adapters：VRM 与 Katarune 专属角色适配
└── Rendering / Window：材质、灯光、取景、透明窗口与桌面交互
```

## 核心领域模型与调度流程

> 状态：当前讨论决定；字段命名可在实现时调整，但职责边界不应合并。

系统使用“请求、定义、计划、实例”四种对象表达一段行为，避免把 AI 意图、动作资产和实时播放状态塞进同一个状态类：

- `BehaviorIntent` 是外部请求，只描述期望结果、语义、目标、约束和请求来源，不包含 Clip、骨骼、逐帧时间或混合权重。
- `BehaviorDefinition` 是动作或表演资产的能力声明，包含所需角色能力、通道占用、同步点、可并行关系、退出段、回退方案和参数范围。
- `PerformancePlan` 是 Unity 根据当前角色、资产定义和运行时状态编译出的内部执行计划。AI、MCP 和 Electron 不直接构造该对象。
- `PerformanceInstance` 是计划被接受后的权威运行实例，拥有稳定实例 ID、生命周期、当前阶段、通道所有权、进度标记和结束原因。

标准流程为：

```text
BehaviorIntent
  → normalize / authorize
  → resolve BehaviorDefinition
  → validate character capability
  → compile PerformancePlan
  → arbitrate channels and interruption
  → create PerformanceInstance
  → drive Presentation Graph
  → emit progress and terminal result
```

任何阶段都可以拒绝请求，并返回结构化原因，例如未知表演、当前角色不兼容、通道冲突、用户策略禁止或资源尚未就绪。系统不得默默把一个具名表演替换成另一个表演；普通语义动作允许按定义中的显式回退链降级。

`PerformanceInstance` 的候选生命周期为：

```text
requested → accepted → running → exiting → completed
                    └────────────→ cancelled
                    └────────────→ failed
```

`requested` 只存在于入口与仲裁阶段；`accepted` 表示资源和通道已预留；`running` 表示至少一个表现通道已经开始；`exiting` 表示正在等待安全点或执行恢复过渡。所有终态必须带结束原因并释放通道，重复取消和迟到事件必须可幂等处理。

### A 阶段实现基线

> 状态：已实现。该基线只固化 Core 领域边界，不表示调度器、资产格式或外部协议已经完成。

Unity Core 已将上述四类对象落实为独立领域类型。`BehaviorIntent` 和 `BehaviorDefinition` 可由入口与资产层构造；`PerformancePlan` 与 `PerformanceInstance` 的构造保持在 Unity 内部程序集边界。计划复制定义的通道申请与控制能力，不携带 Clip、路径、骨骼或模型格式对象；实例只通过受控方法改变生命周期并以单调 revision 标识实际变化。`paused` 作为可恢复运行状态与 `running` 分离，三个终态统一由 `IsTerminal` 识别并带非空结束原因语义；重复取消和重复终结不再增加 revision。

Core 同时提供无状态的通道所有权冲突策略。不同实例只要任一方对同一通道申请独占，候选申请就不能直接授予；共享与附加申请在本阶段互相兼容，精确混合规则留给真实素材验证。该策略只回答是否冲突，不保存、授予或释放所有权；后续调度器仍是唯一执行所有权变更的组件。

### B 阶段实现基线

> 状态：已实现。该基线建立资产定义与导入边界，不表示三份样片、调度器或外部协议已经完成。

行为定义源使用版本化 `.kbehavior` JSON，由严格 `ScriptedImporter` 编译为 Unity 可加载的 `BehaviorDefinitionAsset`。定义保存稳定行为 ID、版本、角色能力要求、通道申请、单个 Clip GUID、入口/循环/退出段、命名同步点与安全退出标记、回退策略和许可证元数据；它不保存本地绝对路径、模型格式类型或角色专属骨骼名。导入和独立校验分别处理未知字段、缺失 Clip、非法段/同步点、重复通道、角色能力不足和许可证元数据缺失。

通用 Humanoid 播放已从 `Katarune.Avatar.UniVrm` 移入独立的 `Katarune.Avatar.Motion` 程序集。模型适配器只把自身 Control Rig 映射为 `ICharacterRigBinding`；动作库、PlayableGraph 和播放实例只依赖该 Binding 与 Core 契约。历史首个可重复导入定义曾指向 `KataruneQuietIdle`；该技术样片已按 D-047 退役。当前本机测试已有经 VRMA 烘焙并打包的基础待机，最终可分发的正式动作资产仍未确定。

### C 阶段真实素材结论

> 状态：已实现并经三份样片验证。该结论只覆盖资产表达与独立 PlayableGraph 预览，不表示 D 阶段调度器已经完成。

单 Clip 定义足以表达首轮三份样片，但真实素材要求在 B 阶段字段上增加四项最小信息：有限循环次数、退出段所对应的命名安全同步点、可选 Humanoid `AvatarMask`，以及取得日期、原始格式、商用/修改/再分发权和仓库收录策略。可选入口、循环与退出段使用显式存在位保存，避免 Unity 序列化把 `null` 自动实例化为零长段。有限循环配合 `exitSyncPoint` 可以表达“循环十五次，再等到下一次稳定站姿进入退出段”，不需要 Timeline 或多 Clip 图。

产品 VRM 实机复查显示 UAL1 `Idle_Talking` 的头、躯干、手臂和腿共同构成动作，套用上半身 Mask 会破坏原始重心和节奏。该解释样片因此申请独占全身通道并无 Mask 播放；视线、表情和口型继续由正交的非身体通道驱动。历史短全身表演曾退出到 `KataruneQuietIdle`；该基底退役后，保留的生成工具只恢复到 Unity 中性 Humanoid 参考姿态。Root/Motion 固定与 Humanoid 肌肉无过冲仍是素材适配规则，不进入 Core 领域层。`Gesture.UpperBody` 与可选 Avatar Mask 仍是有效资产能力，但尚无真实专用样片完成观感验收。

历史三份定义验证了同一个 `.kbehavior` `ScriptedImporter`，没有增加动作枚举或运行时名称分支。当前 `KataruneQuietIdle` 定义与三份规范化 `.anim` 均已退役；Quaternius 原始 FBX 和包内许可证继续位于 Git 忽略的本地源目录。

### D 阶段调度垂直切片

> 状态：实现与自动化验证已落地；仓库外产品 VRM 的两个验收场景观感待人工确认。

Core `PerformanceScheduler` 保存唯一的通道所有权表，按 `BehaviorIntent → BehaviorDefinition → PerformancePlan → PerformanceInstance` 创建实例，并在同一处处理并行、排队、拒绝、立即取消、安全点退出、终态释放和队列提升。调度器不引用 Clip、AvatarMask、UniVRM 或 Electron；Motion 适配器从 `BehaviorDefinitionCatalog` 解析真实资产和角色能力，用资产段与同步点推进单 Clip 播放游标，再把完成或失败回报给 Core。终态实例保留在权威诊断历史中，但不再持有通道或 Playable；重复取消返回 `AlreadyTerminal`，不会二次释放或二次通知播放层。

安装有效基础 Clip 时，每个模型只有一个 `AvatarMotionInstance` 和一个 Animator 输出；其 `AnimationLayerMixerPlayable` 以基础循环为地面层，调度全身表演汇入同一个 `AnimationMixerPlayable` 后作为无 Mask 覆盖层。当前本机外部资源包已提供有效基础待机与五个手动动作，能够创建播放实例；只有缺少有效基础动作时才保留静态基础姿态，不再生成程序化呼吸或颈头微摆。调度表演分支沿用 SmoothStep 过渡：进入 0.20 秒、自然恢复 0.25 秒、安全退出恢复 0.20 秒、立即取消视觉缓冲 0.12 秒；手动动作分支按 D-051 统一使用 0.25 秒线性权重过渡。两者共享播放图，手动动作与调度身体实例互斥。通道是调度语义，不与图层一一对应；全身表演不清空 UniVRM 表情、视线和口型驱动。

基础姿态持续运行，调度身体实例通过同一个 Animator 输出和通道所有权表取得控制；表情、视线和口型保持为正交通道。外部控制通过 Facade，行为请求进入调度器；现有手动动作属于独立预览入口，与调度身体实例互斥并共享同一播放图，不代表已接通 AI 表演工具或正式行为目录。

## 表现通道与运行事实

> 状态：首版边界，后续只有在验收场景证明不足时再细分。

首版使用六类表现通道：

- `Body.Base`：站姿、待机、基础移动等持续身体底层；当前使用本机待机 Clip，缺少有效基础动作时回退静态基础姿态。基础移动尚未实现。
- `Body.FullPerformance`：舞蹈、完整剧情动作等全身主表演。
- `Gesture.UpperBody`：点头、挥手、解释和强调等可叠加手势。
- `Face.Expression`：即时表情与情绪表现。
- `Attention.Gaze`：注视目标、扫视和共同注意。
- `Speech.Viseme`：口型及与语音时间线直接绑定的面部表现。

通道不是 Animator Layer 的一一映射，而是调度层的语义资源；一个通道可以由多个 Playable、IK 或程序化控制器实现。动作定义必须声明独占、共享或附加占用，以及与其他通道的兼容关系。

需要持久化和同步的是可以直接观察的运行事实：

- 当前默认姿态与当前语义表情目标；
- 当前语音播放实例及其播放时钟；
- 当前一个或多个 `PerformanceInstance`、通道所有权和终态；
- 用户开始输入、检测到语音、明确停止等一次性交互事件。

这些事实分别驱动对应通道，不能组合成一个超级状态机。用户开始说话可以产生视线反射或取消语音，却不自动清空全身表演；模型生成过程不对应身体 Clip；语音开始和结束由实际播放实例表达。情绪在首版就是 Unity 支持的有限语义表情。

## 中断与更新命令

> 状态：当前讨论决定；具体超时值和优先级数值待原型验证。

运行时控制不能收缩成单一 `stop`。协议至少支持以下语义：

- `CancelImmediate`：立即停止指定实例或通道，用于明确停止、安全事件和无法继续的运行错误。
- `ExitAtSafePoint`：接受退出请求，在最近合法同步点进入退出段并恢复基础状态。
- `Pause`：仅对资产明确声明可暂停的实例生效，并保留可恢复上下文。
- `Resume`：从已确认的暂停状态继续；资源或上下文失效时应明确失败。

默认优先级不是唯一裁决依据。仲裁顺序应首先检查安全与明确用户控制，然后检查通道所有权和行为策略，再考虑请求优先级、排队与回退。AI 的表达请求永远不能覆盖明确停止、勿扰、安全限制或运行时能力校验。

## Unity 的职责

- 作为形体能力的工具提供方，按当前角色和已加载资源公布稳定工具、描述、受限参数 Schema 与可用枚举。
- 保存权威的实时表演状态，不要求 Electron 追踪动画帧。
- 将高层意图编译为可执行动作，并校验角色是否具备所需能力。
- 管理动作通道、优先级、并行、排队、抢占、取消与自然过渡。
- 运行 PlayableGraph、动画片段、Avatar Mask、IK、程序化动作及模型专属修正。
- 使用 TTS 提供的时间信息驱动口型和语音锚定手势，而不是让语言模型猜测帧时间。
- 在动作开始、被拒绝、到达标记、被打断、完成或失败时向 Electron 反馈事件。
- 隔离 VRM、专属角色格式及未来其他模型来源的骨骼、表情和材质差异。

## Electron 的职责

- 运行对话、记忆和 AI SDK Agent 循环，不决定动画如何逐帧播放。
- 获取并校验 Unity 的能力清单，把当前可用工具动态注册给模型；不复制表情枚举或表演目录作为第二事实来源。
- 管理 TTS、ASR、凭据、工具转发和 Unity Player 的产品生命周期，并向 Unity 提供不暴露供应商的语音合成端点。
- 只依据 Unity 返回的权威状态处理后续行为，不假设请求一定被执行。

## 行为意图的来源

> 状态：当前讨论决定；具体能力清单与传输格式待 E/F 阶段实现切片验证。

Unity 的外部工具不是 Core `BehaviorIntent` 本身，而是由 Unity 拥有并公布的稳定能力入口。AI、用户按钮和本地策略都可以调用这些入口；Unity 的 Tool Adapter 再将合法请求转换为 `BehaviorIntent`、表情命令或语音实例。Electron 负责可信传输、全局授权和取消，不再维护一套独立的动作/表情映射或意图仲裁领域模型。

行为意图至少包含以下来源：

- AI 表达选择：切换 Unity 明确支持的表情、说出一句话、点头或请求执行长表演。模型只能调用当前能力清单中的受限高层工具。
- 用户直接控制：HUD、菜单、点击角色和显式停止操作。
- 环境与产品策略：空闲计时、窗口或显示器变化、角色主动行为策略等。
- 事实事件：麦克风开关、检测到用户语音、模型请求开始/结束等只在需要时作为事件传递，不塑造成角色状态或身体 Clip。

工具 Schema 属于 Unity 的外部能力表面，但不穿透到 Clip、骨骼、帧、混合权重或 `PerformancePlan`。工具调用失败、缺失、重复或延迟时，默认姿态、眨眼、视线与用户安全控制仍须独立正确运行。非阻塞工具只返回接受或拒绝；阻塞工具的终态结果回到 Agent，普通逐帧进度不进入模型上下文。

## AI 层的责任边界

AI 层负责理解语境并作出角色化表达决策，包括要说的文本、当前语义表情、普通动作，以及唱歌、跳舞或讲故事等长行为选择。模型通过 Unity 当前公布的工具 Schema 提交这些选择，不要求估算绝对秒数或动画帧。

AI 应使用工具中受限的语义值描述普通动作和表情，而不选择具体 `AnimationClip`、素材文件、骨骼、BlendShape 或模型专属表情键。Unity 负责把语义值映射到当前角色能力。

对于跳舞、唱歌或剧情演出等具有用户可识别名称的长表演，AI 可以从受限的 `Performance Catalog` 中选择一个具体表演。表演对 AI 暴露稳定 `performanceId`、展示名称、简短语义描述、标签、预计时长和必要的可用性信息；Unity 内部的 Clip、Timeline、PlayableGraph 和角色专属实现继续隐藏。AI 可以在自然语言中提及展示名称，并用稳定 ID 提交请求，但不得假定目录之外的表演存在。

表演目录的事实来源应是角色包或动作包的清单。Unity 在模型和动作资源完成加载后报告当前真正可用的 `performanceId`；Electron 只向模型提供已安装且与当前角色兼容的候选。目录较小时可以用动态受限 Schema 直接选择，目录较大时先通过搜索或推荐缩小候选集，不把全部动作长期写入角色提示词。展示名称可以本地化或重命名，稳定 ID 不随文案变化。

AI 层不负责动作能力和权限校验、优先级与抢占裁决、冷却、队列、帧时间、混合权重、IK、过渡、TTS 合成、音频播放、音素解析、viseme 计算或模型格式差异。模型调用是受限请求；Electron 可以因全局权限或用户控制拒绝转发，Unity 根据权威运行时状态决定实际执行结果。

## AI 表达信息的传递方式

> 状态：动作、表情工具与原生流式字幕已实现；对白 TTS、时间戳字幕与 uLipSync 已按 D-056/D-057 接入；长表演语音锚点和分段编排后接。

Unity 按当前角色能力提供彼此独立的工具管道：

- `set_expression` 是非阻塞表情编排。情绪在首版等同于语义表情枚举；Unity 在工具描述中公布当前支持值，例如 `neutral`、`happy`、`sad`、`angry` 和 `surprised`。调用只等待 Unity 接受或拒绝，实际切换在时间线游标到达该工具节点时发生，并保持到下一次合法切换；Unity 负责平滑和向实际 VRM Expression/BlendShape 的映射。
- 对白使用 AI SDK 原生 `text-start`、`text-delta`、`text-end` 事件。Unity 随文本到达显示字幕并分页，按阅读时长播放，不定义对白工具。推理、工具参数和工具结果不作为对白。
- 普通动作与命名表演使用 Unity 公布的稳定 ID。普通动作复用现有 Facade 和动作库，工具在请求被接受后返回 `accepted`，实际播放终态单独报告；需要分段与安全退出的表演再使用 `PerformanceInstance`。接入简单动作无需先迁移资源格式。
- 搜索或列举表演只返回当前可用目录，不触发播放；用户停止与安全取消通过独立控制路径直接生效。

明确不从用户可见回复正文解析隐藏标签、XML、自由格式 JSON 或特殊标记，也不要求所有回复套入额外文本格式。模型未调用表达工具时，角色继续使用确定性的默认表情、视线、微动作和生命周期表现；普通回复不得因缺少动作调用而失败。

AI SDK 可以在同一个模型步骤中并行执行多个工具，文本也可以在该步骤中流式到达；是否产生过程性文本由模型决定。工具执行并发只影响请求接收，不直接决定角色的播放顺序。动作和表情工具由 Unity 接收后立即返回，不等待实际播放，因而不阻塞模型步骤。

Electron 将当前绑定会话的完整原生 `UIMessageChunk` 流转发给 Unity，不筛成最终正文，也不建立镜像事件协议。Unity 用 `text-start` 建立对白节点，用 `tool-input-available` 建立动作或表情节点，并通过原生 `toolCallId` 将受信任 `execute` 请求填入对应节点。工具事件本身只确定编排位置，不触发执行。聊天与持久化继续使用同一原生消息，不新增独立对白历史。

按 D-054，循环的继续与结束直接沿用现有 AI SDK Agent Loop。

Unity 以单一播放游标按事件顺序消费对白、表情和动作。对白节点在当前字幕页或未来音频实际结束后完成；表情节点到达游标时应用角色整体状态；动作节点等待身体通道可用并真正开始。`avatar_action.allowSpeech` 默认 true，此时动作开始即放行后续对白并与其并行；false 时等动作终态后才推进后续节点。动作和表情工具分别返回 `accepted` 与实例 ID，不阻塞 Agent；实际终态通过管道事件报告。

## 文本阶段的回合与输入队列

> 状态：已实现当前绑定会话的内存队列。

现有聊天界面接收输入，当前回复期间的新消息排队，暂不做插话打断。Electron 转发原生流结束后立即结束聊天传输并处理下一条输入；Unity 独立维护跨轮播放队列。播放时间线排空请求在后台确认，仅管理音频资源回收，不属于 AI 工具，也不决定 Agent 循环或聊天传输何时结束。Unity 断线会释放等待并显示连接错误，聊天文本仍继续传输。

字幕展示与配色见[桌面交互设计](../00-项目/桌面交互设计.md#当前优先切片聊天输入与文本字幕)。无 TTS 时按阅读时长播放字幕，有声对白由 Unity 实际音频播放游标推进；Fish 支持完整文本输入的增量 PCM 播放。

## TTS 与语音表演边界

> 状态：职责边界已决定，跨进程音频与同步实现待 E 阶段验证。

按 D-056，TTS 的供应商调用、凭据、缓存与音频格式处理留在可信的 Electron main process；Unity 负责实际播放与口型时钟。语音从原生 text 块结束事件衍生，不重新引入 `speak` 工具。main 以运行 ID 与对白 ID 补充音频准备结果，Unity 在同一个对白节点等待、播放和回报完成；最多提前准备下一块。

面向桌面形体时，Unity 是语音表演的唯一音频播放时钟，负责 viseme 和语音锚定动作。播放终态用于推进播放队列；Electron renderer 现有完整音频播放仅作为没有活动形体时的回退，同一段语音不得重复播放。

音频归入现有对白节点，由 Unity 以实际播放位置推进同一时间线。Fish 时间戳采用独立供应商模型接口，不覆盖普通合成；对齐缺失时整块字幕随声音显示。Electron 不编译 Unity 表演计划，也不让语言模型逐帧安排口型。uLipSync 分析 AudioSource，五元音经 Facade 和行为系统统一驱动；Windows 实际声画验收仍需独立记录。

## 主动陪伴与认知唤醒

> 状态：候选方向，具体用户控制、触发条件和调用预算待产品讨论。

持续陪伴不等于持续运行语言模型。系统需要区分三种不同频率的循环：

- Unity 每帧运行形体循环，持续处理眨眼、视线、身体待机微动、Spring Bone 二级物理、动画混合和正在执行的表演。
- Electron 以较低频率运行主动行为策略，评估空闲时间、安静时段、用户状态、日程事件、角色习惯、冷却和调用预算；大多数评估不调用模型。
- 只有策略判断当前可能值得进行语义交流时，才唤醒 AI。AI 可以产生一次主动回复或选择保持安静，随后复用普通对话、TTS 和行为意图链路。

当前角色展示转台主要用于模型、动作、材质和取景调试，不进入角色行为设置或 Electron 协议。正式桌面摄像机是否固定、是否允许旋转及开放哪些操作，待构建与实机调试确定；当前实现不锁定最终产品交互。一级 HUD 开关默认关闭；开启后 `AvatarSceneRig` 把 VRM 根固定在世界原点并只绕作者根轴水平旋转。Main Camera 与 `AvatarSceneRig` 由启动场景预挂载，Camera FOV、初始 `0.6×` 投影倍率、右侧/底部 `8%` 边距和画框留白可从 Inspector 调整；运行时再结合 Renderer Bounds 与屏幕比例计算最终相机距离和 `lensShift`。左键垂直拖动在上下各 `45°` 内改变摄像机俯仰，滚轮只改变投影倍率，中键只改变相对初始值的 `lensShift` 构图偏移。倍率和构图不移动角色、相机基础距离或观察中心。`AvatarWindow` 仅在该模式开启期间暂停整窗点击穿透，UI Button 仍优先于展示手势；关闭或卸载模型后恢复普通桌宠命中语义。现有鼠标视线投影继续使用最终摄像机姿态，不增加新的视线状态或可达性规则。

不需要语言推理的主动行为，例如换一个待机姿态、看向别处、伸懒腰或进入休息状态，应由本地策略和 Unity 动作目录直接完成。问候、提醒、基于记忆继续话题或针对环境事件作出语义回应才进入 AI。用户必须能控制主动程度、最短间隔、安静时段和总开关；停止与勿扰规则不依赖模型自律。

## 交互事件与表演打断

> 状态：当前讨论决定；精确优先级、通道和默认策略仍需通过长表演切片验证。

用户输入只产生交互事件，不自动等价为停止当前动作、重置表情或切换到任何全局对话状态。身体表演、语音或音乐、视线、表情、对话接收和认知运行必须分别仲裁。角色可以在继续跳舞时转头看向用户并接收问题，再根据请求和表演策略决定继续、暂停或在安全节点退出。

每个长表演必须声明交互能力和退出策略，至少包括身体通道所有权、是否可听、是否可说、视线策略、默认打断策略、安全退出标记，以及明确停止是否立即生效。普通文字可以排队而不停止表演；用户开始说话可以先触发本地注意反射；普通问题可以请求在最近安全点退出；“继续跳”“边跳边听”和“停止表演”等明确指令应覆盖默认策略；紧急停止和安全事件不等待模型并立即释放相关通道。

调度器负责无需语义推理的即时反射、音频压低、通道抢占和安全退出。AI 可以在获得用户语义后建议后续继续、暂停或更换表演，但不能覆盖明确用户停止、安全规则和运行时能力。Agent 生成或工具执行本身的取消、续跑和新输入转向属于 Electron Agent Runtime 的独立生命周期，不与 Unity 动画取消混成一个状态。

当前表情是 Unity 公布的有限语义枚举，保持到下一次合法切换或模型卸载；默认值为 Unity 对当前角色公布的中性表情。输入、模型生成和音频播放均由各自事件或实例表达。

## 外部宿主与协议复用

> 状态：架构兼容方向；当前阶段只实现 Katarune 宿主，不提前建设完整插件或 MCP 生态。

Unity Avatar Runtime 应保持 Agent 与宿主无关。它以宿主中立的能力清单、工具调用信封、控制命令、权威快照和执行结果事件为稳定边界，不引用 Katarune 聊天消息或 AI SDK 类型。Katarune Electron Harness 是首个宿主，并负责把该能力表面适配为当前 AI SDK 工具。

未来可以通过适配器将同一 Unity 能力表面包装为 MCP 工具、其他 Agent 的插件或本地应用接口；适配器不得穿透行为调度器直接控制骨骼或动画资源。普通请求式工具本身不会在用户沉默时唤醒 Agent，需要持续主动行为的宿主仍须提供计时、环境订阅、策略、长连接状态和认知唤醒能力。

## 模型与格式定位

VRM 是首个模型适配器和通用用户导入入口，不是言奏角色领域模型的上限。言奏可以为重点角色提供专属骨骼绑定、表情映射、动作集、材质策略和角色特有修正，不追求所有角色能力完全通用。

不同格式最终都应映射到统一的 `Character Rig Binding`。行为调度器只理解身体、表情、视线、口型和能力描述，不应依赖 UniVRM 类型或直接访问具体模型层级。

## 参考架构与可借鉴原则

> 状态：调研记录，不代表已选定第三方框架。目标是吸收成熟概念，并用言奏自己的 TypeScript / C# 数据契约实现；不直接引入 BML XML、完整 Gameplay Ability System 或研究型动作生成模型。

### 具身对话代理：意图、计划与实现分离

[BEAT](https://www.media.mit.edu/gnl/publications/siggraph2001.pdf) 将语言分析、非语言行为建议和最终动画/语音实现分开；[SmartBody](https://ict.usc.edu/pubs/SmartBody-%20Behavior%20Realization%20for%20Embodies%20Conversational%20Agents.pdf) 则把一份表演描述交给 Behavior Realizer，在运行时协调语音、凝视、手势、移动和动画控制器。它们支持当前边界：Electron 负责交际语义和高层请求，Unity 将请求实现为受约束的实时表演。

候选映射为三层，而不是让 AI 直接提交最终动画：

1. `BehaviorIntent`：为什么表达、面向谁、情感和语义动作是什么。
2. `PerformancePlan`：选中了哪些行为单元、它们如何同步、占用哪些通道、允许怎样退出。
3. `PerformanceInstance`：Unity 中正在执行的实例、当前阶段、权威进度和结果。

### 同步点优于绝对帧

[Behavior Markup Language 1.0](https://repository.cs.ru.is/attachments/download/843/bml-standard-1.pdf) 用命名同步点约束不同模态，而不是要求上层猜测逐帧时间。例如手势可具有 `start / ready / stroke / relax / end`，语音可提供词语或短语标记，面部动作可具有峰值与回落阶段。

言奏可以借用这一语义，但不照搬 XML：短手势以 `stroke` 对齐语音语义锚点；舞蹈、歌曲和剧情以稳定的命名标记描述段落边界、安全退出点和关键事件。绝对秒数只在资产实现层产生，AI 和外部宿主只引用语义标记。

### 柔性打断与基础状态恢复

[AsapRealizer 2.0](https://pub.uni-bielefeld.de/download/2690254/2690266/asaprealizer2.pdf) 的重要启发是增量计划和 graceful interruption：中断不是清空所有控制器，而是为受影响的行为生成返回基础姿态或基础凝视目标的过渡。[连续交互研究](https://ris.utwente.nl/ws/files/6035043/thesis_H_van_Welbergen.pdf) 还区分选择性中断、运行中参数更新和与外部事件重新同步。

因此候选规则是：

- 每个通道维护可恢复的 `GroundState`，例如基础姿态、默认凝视和默认语义表情。
- 取消请求可以选择通道，不自动清除整场表演。
- 行为声明可安全中断阶段；处于手势回收、落地或舞蹈转身等阶段时，可先完成短过渡再释放通道。
- 视线目标、表达强度、音频压低等参数允许在行为运行中更新，无需重启整个动作。
- 运行时返回已接受取消、等待安全点、开始退出和已恢复基础状态等进度事件。

### 游戏能力系统：自包含行为与标签仲裁

[Unreal Gameplay Ability System](https://dev.epicgames.com/documentation/en-us/unreal-engine/understanding-the-unreal-engine-gameplay-ability-system) 把能力建模为有生命周期的自包含执行单元，并通过标签表达激活条件、阻塞和取消关系。言奏不需要复制其战斗属性、联网预测和效果系统，但适合借鉴以下结构：

- 动作资产定义与运行时实例分离，同一动作可多次执行且各自有状态。
- 每个实例具有 `requested / accepted / running / exiting / completed / cancelled / failed` 等明确生命周期。
- 使用稳定语义标签描述通道占用与关系，例如 `Body.Full`、`Gesture.UpperBody`、`Speech.Active`、`Attention.User`，避免在中心调度器里持续增加动作名称特判。
- 标签只辅助声明约束；最终冲突仍由显式的通道所有权、优先级、用户指令和安全策略裁决。

[GDC 的多角色行为编排案例](https://media.gdcvault.com/GDC2014/Presentations/Bell_Brian_Multi_Actor_Behavior.pdf) 还提示长行为应预留可跳过的尾段或填充段，以便在等待后续条件时保持自然，又能及时响应。这适合转化为动作资产的可中断尾段和等待循环，而不是让调度器硬切动画。

### 对话输入不是统一的打断信号

全双工对话研究通常把用户声音进一步区分为反馈、抢话和真正接管话轮，而不是使用“检测到声音即停止”的单一规则。[Duplex Conversation](https://arxiv.org/abs/2205.15060) 将用户状态、backchannel 与 barge-in 分开处理；[DiscoRT](https://personales.upv.es/thinkmind/ACHI/ACHI_2014/achi_2014_16_20_20152.html) 也把参与度、轮次、打断、反馈和凝视作为协作模块。

这支持将输入先规范化为 `InteractionEvent`，再由本地策略和语义层判断：简短附和只触发注意或表情反馈，普通问题可以排队或请求安全退出，明确停止立即取消。ASR 尚未给出完整语义时，可以先做可逆的本地反射，不应抢先摧毁当前表演。

### 视线与主动行为都应选择合适模态

[虚拟代理凝视研究](https://www.microsoft.com/en-us/research/publication/designing-effective-gaze-mechanisms-for-virtual-agents/) 表明凝视同时承担关系建立和对象指示等交际功能，因此它应是独立语义通道，而非待机装饰。主动陪伴也不应默认等于主动说话：策略可以根据情境选择视线、表情、姿态、无声动作或语言，把语音留给确有交际价值的时刻。

程序化视线统一经过 Core 的 `HeadEyeGazeCoordinator`，不会由待机与鼠标跟踪分别控制骨骼。对外设置只保留 `PointerGazeTrackingEnabled`：默认 `false` 时固定正前方，用户从一级 HUD 开启后持续跟踪指针；不再提供自动定时切换、随机偏移目标或外部手动角度。开关目标变化提交 `Fixation`，连续指针提交 `Tracking`；眼睛先响应，头部仅对越过死区且持续的偏角延迟跟随，并使用 `SmoothDamp` 保持速度连续。由于 UniVRM 的手动 Yaw/Pitch 相对当前头部朝向，最终眼球输入会扣除已由头颈承担的角度，使两者共同收敛到同一个屏幕目标。鼠标输入不再将归一化屏幕偏移直接乘固定角度：Runtime 使用 Unity [`Camera.ScreenPointToRay`](https://docs.unity3d.com/ja/current/ScriptReference/Camera.ScreenPointToRay.html) 生成世界射线，与摄像机和 VRM 眼睛原点之间的摄像机朝向虚拟窗口平面求交，再按角色根朝向计算 viewport-relative yaw/pitch；当前窗口深度比例 `0.45` 是桌面视觉调参，不进入设置协议。世界物体或行为系统也只负责在边界层求出同一角度输入，不复制协调算法。这一分层参数化方式参考 [A Head-Eye Coordination Model for Animating Gaze Shifts of Virtual Characters](https://www.microsoft.com/en-us/research/publication/a-head-eye-coordination-model-for-animating-gaze-shifts-of-virtual-characters/)，但当前实现保持确定性轻量，不引入新的动画包。

当前默认测试待机的源文件为 `KataruneLocal/Motions/idle-standing-breathing.vrma`，由编辑器 `AvatarVrmaLibraryImporter` 烘焙为独立 Humanoid `.anim`，经 `AvatarMotionPackBuilder` 打包为 `.motionpack`；运行时加载资源包，由 Motion 层的 `AvatarMotionInstance` 在同一 PlayableGraph 中播放，UniVrm 只提供标准化 Control Rig 适配。修改源 VRMA 或 `.anim` 后需要重新烘焙或打包，运行时不会直接读取替换后的源文件。Core 不再生成程序化呼吸或颈头慢摆；缺少有效基础动作时使用静态基础姿态。视线、表情、眨眼、口型和环境风继续独立，视线补偿作者动作的头部朝向。Spring Bone 在身体动作之后产生二级物理，不修改模型的刚度、阻尼、重力或碰撞体。本机测试素材不进入版本控制或公开产物。

### 暂不采用的部分

- 不引入 BML XML 作为产品协议；仅借用行为块、同步点、进度反馈和 Realizer 分层。
- 不完整移植 Unreal GAS；仅借用自包含实例、生命周期、标签与取消关系。
- 不在首期采用文本到手势或生成式人体动作模型；它们可作为素材扩展实验，不能替代确定性调度。
- 不因未来可能接入 MCP 或插件而提前暴露逐帧控制接口。

### 对当前开放问题的直接结论

- 数据契约应同时表达 `BehaviorIntent`、`PerformancePlan`、同步标记、通道声明和实例反馈。
- 长表演实际需要打断时，再接入相应的立即取消、安全退出或暂停能力；当前文本控制切片先复用现有播放与停止入口。
- 同步点、退出段和等待循环由具体表演需要决定，普通一次性动作不以齐备这些字段作为接入条件。
- 第一轮原型应专门记录调度时间线，显示每个通道的所有者、阶段、标记和取消原因；否则多通道问题会很难诊断。
- 后续需要动作资产预览与校验工具，但它属于资产管线阶段，不阻塞首个运行时切片。

## 当前实现的初步判断

### 值得保留

- 独立 Unity Runtime 与透明桌面窗口方向。
- Core、Motion、UniVrm、Runtime 的依赖分层。
- `IAvatarRuntimeFacade` 单一外部控制入口。
- 带 Revision 的权威 Snapshot。
- 模型 `prepare → validate → commit` 事务与失败回滚。
- UniVRM 标准化 Control Rig、表情、视线和模型生命周期适配。

### 已完成的结构调整

- 已移除覆盖整个角色身体的全局对话阶段，身体、表情、视线和显式口型输入分别驱动。
- 外部动作包已按稳定字符串 ID 和显示名称扩展动作；预设枚举仅保留既有调用别名，新增动作无需增加枚举。
- 通用 Humanoid 播放已移入 Motion 程序集，UniVrm 只提供模型适配与标准化 Rig Binding。
- 请求、定义、计划、实例、权威快照与逐帧姿态已有独立边界，调度器已实现通道所有权与取消语义。

### 仍需完成与验证

- 当前本机手动动作包不等于正式行为目录；历史三样片退役后，调度验收场景需重新绑定有效定义与真实素材。
- 上半身专用手势、长表演安全退出和多通道混合仍需产品模型的观感验收，不能沿用退役样片的通过记录。
- 已按 D-053 接入 Electron 管理的 Player、最小能力协议、动作/表情/文本工具与聊天输入队列；E/F 阶段的自动重连、完整长表演与真实语音时钟仍待接入。
- 正式桌面界面与摄像机交互依据产品构建和实机调试确认，当前转台用于调试。

## 首批验收场景

以下场景用于检验架构，不代表最终动作美术：

1. 角色说话时同时保持口型、看向用户并播放一次全身解释动作；基础身体平滑让出并在动作结束后恢复，不裁切原动作的腿、头或重心。
2. 角色执行长时间轴舞蹈时，全身动作获得身体通道所有权，表情和视线仍可按策略运行；用户打断后在指定安全节点退出并自然回到待机。
