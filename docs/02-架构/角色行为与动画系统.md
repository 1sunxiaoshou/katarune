# 角色行为与动画系统

> 状态：讨论中。本页是 Unity 角色行为、动作与模型适配架构的主设计草案。候选方案不会自动成为已决定事项；稳定结论确认后再同步到决策记录、技术选型和路线图。

实施阶段、交付物与验收条件见[角色行为与动画系统推进计划](../03-规划/角色行为与动画系统推进计划.md)。

## 文档目的

言奏需要把模型回复、语音、用户事件和角色设定转化为持续、自然且可打断的数字角色表演。本页用于确定这套系统的长期边界，避免继续在当前四态循环和固定动作白名单上堆叠功能后产生大规模重构。

## 一句话目标

Unity 是言奏的角色形体与表演运行时，而不是 AI 大脑：Electron 提交高层角色意图，Unity 在实时约束下完成调度、混合和逐帧驱动，并返回可观察的执行状态与结果。

## 期望的最终体验

角色以透明桌面形态持续存在，能够自然地待机、倾听、思考和说话，并将语音、口型、表情、视线、手势与身体动作协调为完整表演。角色可以执行挥手、解释等短动作，也可以执行跳舞、唱歌或剧情演出等长时间轴动作；用户打断时，系统根据动作策略立即退出或在安全节点自然收束。

AI 不直接控制骨骼、动画帧或混合权重。它只表达角色意图、语义动作和必要的时间约束。确定性的运行时拥有当前状态、通道所有权、优先级、抢占、混合和回退控制权。

## 目标系统边界

```text
Electron / Katarune Harness
├── 对话、记忆、角色策略、用户与桌面事件
├── 生成高层 Character Intent / Behavior Plan
└── 管理 Unity 进程生命周期与可信控制协议

Unity Avatar Presentation Runtime
├── Protocol Adapter：接收意图并返回状态、事件和结果
├── Behavior Scheduler：排队、优先级、抢占、取消和安全打断点
├── Presentation Graph：身体、手势、表情、视线、口型和程序化附加层
├── Character Rig Binding：向上暴露稳定的形体控制能力
├── Model Adapters：VRM 与 Katarune 专属角色适配
└── Rendering / Window：材质、灯光、取景、透明窗口与桌面交互
```

## 核心领域模型与调度流程

> 状态：当前讨论决定；字段命名可在实现时调整，但职责边界不应合并。

系统使用“请求、定义、计划、实例”四种对象表达一段行为，避免把 AI 意图、动作资产和实时播放状态塞进同一个状态类：

- `BehaviorIntent` 是外部请求，只描述期望结果、语义、目标、约束和请求来源，不包含 Clip、骨骼、逐帧时间或混合权重。
- `BehaviorDefinition` 是动作或表演资产的能力声明，包含所需角色能力、通道占用、同步点、可并行关系、退出段、回退方案和参数范围。
- `PerformancePlan` 是 Unity 根据当前角色、资产定义和运行时状态编译出的内部执行计划。AI、MCP 和 Electron 不直接构造该对象。
- `PerformanceInstance` 是计划被接受后的权威运行实例，拥有稳定实例 ID、生命周期、当前阶段、通道所有权、进度标记和结束原因。

标准流程为：

```text
BehaviorIntent
  → normalize / authorize
  → resolve BehaviorDefinition
  → validate character capability
  → compile PerformancePlan
  → arbitrate channels and interruption
  → create PerformanceInstance
  → drive Presentation Graph
  → emit progress and terminal result
```

任何阶段都可以拒绝请求，并返回结构化原因，例如未知表演、当前角色不兼容、通道冲突、用户策略禁止或资源尚未就绪。系统不得默默把一个具名表演替换成另一个表演；普通语义动作允许按定义中的显式回退链降级。

`PerformanceInstance` 的候选生命周期为：

```text
requested → accepted → running → exiting → completed
                    └────────────→ cancelled
                    └────────────→ failed
```

`requested` 只存在于入口与仲裁阶段；`accepted` 表示资源和通道已预留；`running` 表示至少一个表现通道已经开始；`exiting` 表示正在等待安全点或执行恢复过渡。所有终态必须带结束原因并释放通道，重复取消和迟到事件必须可幂等处理。

### A 阶段实现基线

> 状态：已实现。该基线只固化 Core 领域边界，不表示调度器、资产格式或外部协议已经完成。

Unity Core 已将上述四类对象落实为独立领域类型。`BehaviorIntent` 和 `BehaviorDefinition` 可由入口与资产层构造；`PerformancePlan` 与 `PerformanceInstance` 的构造保持在 Unity 内部程序集边界。计划复制定义的通道申请与控制能力，不携带 Clip、路径、骨骼或模型格式对象；实例只通过受控方法改变生命周期并以单调 revision 标识实际变化。`paused` 作为可恢复运行状态与 `running` 分离，三个终态统一由 `IsTerminal` 识别并带非空结束原因语义；重复取消和重复终结不再增加 revision。

Core 同时提供无状态的通道所有权冲突策略。不同实例只要任一方对同一通道申请独占，候选申请就不能直接授予；共享与附加申请在本阶段互相兼容，精确混合规则留给真实素材验证。该策略只回答是否冲突，不保存、授予或释放所有权；后续调度器仍是唯一执行所有权变更的组件。新领域模型尚未接入现有 `IAvatarRuntimeFacade`、权威 Snapshot、四态循环或白名单动作，现有模型事务与表现闭环保持不变。

### B 阶段实现基线

> 状态：已实现。该基线建立资产定义与导入边界，不表示三份样片、调度器或外部协议已经完成。

行为定义源使用版本化 `.kbehavior` JSON，由严格 `ScriptedImporter` 编译为 Unity 可加载的 `BehaviorDefinitionAsset`。定义保存稳定行为 ID、版本、角色能力要求、通道申请、单个 Clip GUID、入口/循环/退出段、命名同步点与安全退出标记、热更新参数名、回退策略和许可证元数据；它不保存本地绝对路径、模型格式类型或角色专属骨骼名。导入和独立校验分别处理未知字段、缺失 Clip、非法段/同步点、重复通道、角色能力不足和许可证元数据缺失。

通用 Humanoid 播放已从 `Katarune.Avatar.UniVrm` 移入独立的 `Katarune.Avatar.Motion` 程序集。模型适配器只把自身 Control Rig 映射为 `ICharacterRigBinding`；动作库、PlayableGraph 和播放实例只依赖该 Binding 与 Core 契约。首个可重复导入定义指向仓库已有的 `KataruneQuietIdle`，按 Unity Companion License 记录为可分发原型。当前四态、白名单动作、Facade、Snapshot 和模型事务仍沿用原运行基线，直到 D 阶段调度器完成接管。

### C 阶段真实素材结论

> 状态：已实现并经三份样片验证。该结论只覆盖资产表达与独立 PlayableGraph 预览，不表示 D 阶段调度器已经完成。

单 Clip 定义足以表达首轮三类样片，但真实素材要求在 B 阶段字段上增加四项最小信息：有限循环次数、退出段所对应的命名安全同步点、可选 Humanoid `AvatarMask`，以及取得日期、原始格式、商用/修改/再分发权和仓库收录策略。可选入口、循环与退出段使用显式存在位保存，避免 Unity 序列化把 `null` 自动实例化为零长段。有限循环配合 `exitSyncPoint` 可以表达“循环十五次，再等到下一次稳定站姿进入退出段”，不需要 Timeline 或多 Clip 图。

上半身解释样片在定义中申请附加的上半身手势通道，并引用只启用躯干、双臂与手指的 Humanoid Mask；头、根节点、腿和手脚 IK 保持关闭，因此视线与口型仍由正交通道驱动。短全身表演申请独占全身通道，退出段从明确的稳定姿势烘焙回 `KataruneQuietIdle`。规范化时 Root/Motion 曲线固定为待机基线，Humanoid 肌肉退出曲线使用无过冲插值；这两项是素材适配规则，不进入 Core 领域层。

三份定义继续通过同一个 `.kbehavior` `ScriptedImporter` 加载，没有增加动作枚举或运行时名称分支。仓库只保存规范化 `.anim` 与 `.mask`；Quaternius 原始 FBX 和包内许可证继续位于 Git 忽略的本地源目录。现有四态、白名单动作、Facade、Snapshot 和模型事务仍由旧基线负责，直到 D 阶段调度器实际接管。

## 表现通道与状态正交性

> 状态：首版边界，后续只有在验收场景证明不足时再细分。

首版使用六类表现通道：

- `Body.Base`：呼吸、站姿、待机、基础移动等持续身体底层。
- `Body.FullPerformance`：舞蹈、完整剧情动作等全身主表演。
- `Gesture.UpperBody`：点头、挥手、解释和强调等可叠加手势。
- `Face.Expression`：即时表情与情绪表现。
- `Attention.Gaze`：注视目标、扫视和共同注意。
- `Speech.Viseme`：口型及与语音时间线直接绑定的面部表现。

通道不是 Animator Layer 的一一映射，而是调度层的语义资源；一个通道可以由多个 Playable、IK 或程序化控制器实现。动作定义必须声明独占、共享或附加占用，以及与其他通道的兼容关系。

以下状态保持正交，不再合并为一个超级状态机：

- `Mood`：持续、衰减的角色心境，是姿态和表情选择的参数来源。
- `ConversationSignals`：倾听、思考、说话等应用生命周期信号。
- `InteractionState`：用户是否在输入、是否抢话、是否明确要求停止等互动事实。
- `PerformanceInstance`：当前实际执行的一个或多个行为实例。

调度器根据这些状态选择默认表现，但任何单一状态都不自动清空其他状态。例如用户开始说话可以改变视线和注意表现，不必取消全身舞蹈；进入 `Speaking` 可以启动口型和手势建议，不必覆盖当前心境。

## 中断与更新命令

> 状态：当前讨论决定；具体超时值和优先级数值待原型验证。

运行时控制不能收缩成单一 `stop`。协议至少支持以下语义：

- `CancelImmediate`：立即停止指定实例或通道，用于明确停止、安全事件和无法继续的运行错误。
- `ExitAtSafePoint`：接受退出请求，在最近合法同步点进入退出段并恢复基础状态。
- `Pause`：仅对资产明确声明可暂停的实例生效，并保留可恢复上下文。
- `Resume`：从已确认的暂停状态继续；资源或上下文失效时应明确失败。
- `UpdateChannels`：在不中止主体行为的情况下更新视线、表情强度、音频压低或其他允许热更新的参数。

默认优先级不是唯一裁决依据。仲裁顺序应首先检查安全与明确用户控制，然后检查通道所有权和行为策略，再考虑请求优先级、排队与回退。AI 的表达请求永远不能覆盖明确停止、勿扰、安全限制或运行时能力校验。

## Unity 的职责

- 保存权威的实时表演状态，不要求 Electron 追踪动画帧。
- 将高层意图编译为可执行动作，并校验角色是否具备所需能力。
- 管理动作通道、优先级、并行、排队、抢占、取消与自然过渡。
- 运行 PlayableGraph、动画片段、Avatar Mask、IK、程序化动作及模型专属修正。
- 使用 TTS 提供的时间信息驱动口型和语音锚定手势，而不是让语言模型猜测帧时间。
- 在动作开始、被拒绝、到达标记、被打断、完成或失败时向 Electron 反馈事件。
- 隔离 VRM、专属角色格式及未来其他模型来源的骨骼、表情和材质差异。

## Electron 的职责

- 决定角色为何行动以及期望表达的语义，不决定动画如何逐帧播放。
- 根据对话、记忆、角色设定和用户事件产生有限、结构化的行为请求。
- 管理 AI、TTS、ASR、工具调用和 Unity Player 的产品生命周期。
- 只依据 Unity 返回的权威状态处理后续行为，不假设请求一定被执行。

## 行为意图的来源

> 状态：候选方案，待 AI 表达规划与 Electron 协调器设计确认。

Unity 接收的行为意图不应等同于 AI 工具调用。Electron 应提供统一的意图入口，将不同来源的请求规范化为同一种 `BehaviorIntent`，完成权限、能力和策略校验后再提交 Unity。Unity 不需要知道意图来自模型、用户按钮还是应用生命周期。

行为意图至少包含以下来源：

- 应用生命周期：开始倾听、模型开始生成、TTS 开始或停止播放等确定性事件。这些基础状态不依赖模型主动调用。
- AI 表达选择：开心回应、点头、解释手势或提议执行长表演等具有角色表达意义的选择。模型只能提交受限的高层请求。
- 用户直接控制：HUD、菜单、点击角色和显式停止操作。
- 环境与产品策略：空闲计时、窗口或显示器变化、角色主动行为策略等。

AI 工具调用可以作为首个 `BehaviorIntent` 适配器，但不应成为 Unity 控制协议或行为领域模型。工具调用失败、缺失、重复或延迟时，应用生命周期和安全控制仍须独立正确运行。普通动画帧、混合进度和常规完成事件只返回 Electron 协调器，默认不重新注入模型上下文；只有结果会改变对话决策时，才由上层选择性地形成模型可见信息。

## AI 层的责任边界

AI 层负责理解语境并作出角色化表达决策，包括回复内容、交际意图、情感建议、语义动作建议、注意目标、语音表演提示，以及唱歌、跳舞或讲故事等长行为提议。语音同步提示应使用词语、短语或语义片段作为锚点，不要求模型估算绝对秒数或动画帧。

AI 应使用交际语义描述普通动作，例如“轻微点头表示确认”或“以解释手势强调这句话”，而不选择具体 `AnimationClip`、素材文件、骨骼或模型专属表情键。Electron 的策略和映射层负责把语义建议转换成当前角色可用的动作请求。

对于跳舞、唱歌或剧情演出等具有用户可识别名称的长表演，AI 可以从受限的 `Performance Catalog` 中选择一个具体表演。表演对 AI 暴露稳定 `performanceId`、展示名称、简短语义描述、标签、预计时长和必要的可用性信息；Unity 内部的 Clip、Timeline、PlayableGraph 和角色专属实现继续隐藏。AI 可以在自然语言中提及展示名称，并用稳定 ID 提交请求，但不得假定目录之外的表演存在。

表演目录的事实来源应是角色包或动作包的清单。Unity 在模型和动作资源完成加载后报告当前真正可用的 `performanceId`；Electron 只向模型提供已安装且与当前角色兼容的候选。目录较小时可以用动态受限 Schema 直接选择，目录较大时先通过搜索或推荐缩小候选集，不把全部动作长期写入角色提示词。展示名称可以本地化或重命名，稳定 ID 不随文案变化。

AI 层不负责应用生命周期状态、动作能力和权限校验、优先级与抢占裁决、冷却、队列、帧时间、混合权重、IK、过渡、TTS 合成、音频播放、音素解析、viseme 计算或模型格式差异。模型输出始终是受限提议；Electron 可以采用、替换、延迟或忽略，Unity 则根据权威运行时状态决定实际执行结果。

## AI 表达信息的传递方式

> 状态：当前讨论决定；具体工具数量、参数和 AI SDK 运行行为仍需实现切片验证。

不同语义不应共用一种传递机制：

- `Listening / Thinking / Speaking` 等应用生命周期状态由 Electron 根据用户输入、模型运行和 TTS 播放事件直接产生，不经过模型输出或工具调用。
- AI 主动选择的情感、注意目标和普通手势使用受 Schema 约束的表达工具。工具只提交建议性高层参数，由 Electron 验证并转换为短生命周期 `BehaviorIntent`；工具不得直接修改 Unity Facade 或权威状态。
- 舞蹈、歌曲和剧情演出等命名长行为通过目录搜索与显式执行工具完成。模型需要时先查询候选，再用稳定 ID 请求执行；目录不长期注入上下文。

明确不从用户可见回复正文解析隐藏标签、XML、自由格式 JSON 或特殊标记，也不要求所有回复套入额外文本格式。模型未调用表达工具时，角色继续使用确定性的默认表情、视线、微动作和生命周期表现；普通回复不得因缺少动作调用而失败。

工具调用只是 AI 意图入口，不是 Unity 协议。表达工具应尽量组合一次回复所需的情感、普通手势和注视建议，避免为同一表达产生多个细碎工具调用；目录型长行为则保持“搜索候选”和“请求执行”分离。实现切片需要验证工具是否导致额外模型步骤、首字延迟、消息历史噪音和自动续跑，并据此确定工具结果对模型与聊天 UI 的可见方式。

## TTS 与语音表演边界

> 状态：候选方案，待跨进程音频与同步切片验证。

TTS 应拆分为“语音生成能力”和“实时表演时钟”。供应商调用、凭据、取消、缓存与音频格式标准化继续留在可信的 Electron main process；Unity 不接触 Provider SDK 或凭据，只消费已经生成的音频、可用的词语或音素时间线，以及与本次语音关联的表演意图。

面向桌面形体时，候选方向是由 Unity 作为单次语音表演的唯一音频播放时钟，并在同一实时循环中驱动 viseme、表情和语义手势。Unity 向 Electron 返回 `started`、时间标记、`interrupted`、`completed` 和失败事件。Electron renderer 现有的完整音频播放可以保留为没有活动形体时的回退输出，但同一段语音不得由两个运行时同时播放或分别估算进度。

未来可以在 Electron 建立语音协调器，将最终文本、TTS 音频、时间线和表演意图组合成一次 `SpeechPerformance`。该协调器属于产品 Harness，不进入通用 Agent 循环，也不让语言模型逐帧安排口型。

## 主动陪伴与认知唤醒

> 状态：候选方向，具体用户控制、触发条件和调用预算待产品讨论。

持续陪伴不等于持续运行语言模型。系统需要区分三种不同频率的循环：

- Unity 每帧运行形体循环，持续处理呼吸、眨眼、视线、动画混合和正在执行的表演。
- Electron 以较低频率运行主动行为策略，评估空闲时间、安静时段、用户状态、日程事件、角色习惯、冷却和调用预算；大多数评估不调用模型。
- 只有策略判断当前可能值得进行语义交流时，才唤醒 AI。AI 可以产生一次主动回复或选择保持安静，随后复用普通对话、TTS 和行为意图链路。

不需要语言推理的主动行为，例如换一个待机姿态、看向别处、伸懒腰或进入休息状态，应由本地策略和 Unity 动作目录直接完成。问候、提醒、基于记忆继续话题或针对环境事件作出语义回应才进入 AI。用户必须能控制主动程度、最短间隔、安静时段和总开关；停止与勿扰规则不依赖模型自律。

## 交互事件与表演打断

> 状态：当前讨论决定；精确优先级、通道和默认策略仍需通过长表演切片验证。

用户输入只产生交互事件，不自动等价为停止当前动作、重置情绪或切换到单一 `Listening` 全局状态。身体表演、语音或音乐、视线、表情、对话接收和认知运行必须分别仲裁。角色可以在继续跳舞时转头看向用户并接收问题，再根据请求和表演策略决定继续、暂停或在安全节点退出。

每个长表演必须声明交互能力和退出策略，至少包括身体通道所有权、是否可听、是否可说、视线策略、默认打断策略、安全退出标记，以及明确停止是否立即生效。普通文字可以排队而不停止表演；用户开始说话可以先触发本地注意反射；普通问题可以请求在最近安全点退出；“继续跳”“边跳边听”和“停止表演”等明确指令应覆盖默认策略；紧急停止和安全事件不等待模型并立即释放相关通道。

调度器负责无需语义推理的即时反射、音频压低、通道抢占和安全退出。AI 可以在获得用户语义后建议后续继续、暂停或更换表演，但不能覆盖明确用户停止、安全规则和运行时能力。Agent 生成或工具执行本身的取消、续跑和新输入转向属于 Electron Agent Runtime 的独立生命周期，不与 Unity 动画取消混成一个状态。

心境与即时表情也必须分离。`Mood` 是持续较长并缓慢衰减的角色状态；`Expression` 是针对当前事件的短暂表现，可以临时覆盖心境后回落。用户一次输入不会自动清空心境。`Listening / Thinking / Speaking` 更适合作为对话与注意通道的活动信号，而不是覆盖身体表演、心境和其他通道的唯一全局状态。

## 外部宿主与协议复用

> 状态：架构兼容方向；当前阶段只实现 Katarune 宿主，不提前建设完整插件或 MCP 生态。

Unity Avatar Runtime 应保持 Agent 与宿主无关。其稳定边界是高层行为意图、资源能力查询、权威状态和执行结果事件，而不是 Katarune 的聊天消息、AI SDK 类型或工具调用记录。Katarune Electron Harness 是首个宿主和产品实现。

未来可以通过适配器将同一意图协议包装为 MCP 工具、其他 Agent 的插件或本地应用接口，例如表达、搜索表演和执行表演；这些适配器不得穿透行为调度器直接控制骨骼或动画资源。MCP 工具可以让外部 Agent 主动调用角色，但普通请求式工具本身不会在用户沉默时唤醒 Agent。需要持续主动行为的宿主仍须提供计时、环境订阅、策略、长连接状态和认知唤醒能力。

## 模型与格式定位

VRM 是首个模型适配器和通用用户导入入口，不是言奏角色领域模型的上限。言奏可以为重点角色提供专属骨骼绑定、表情映射、动作集、材质策略和角色特有修正，不追求所有角色能力完全通用。

不同格式最终都应映射到统一的 `Character Rig Binding`。行为调度器只理解身体、表情、视线、口型和能力描述，不应依赖 UniVRM 类型或直接访问具体模型层级。

## 参考架构与可借鉴原则

> 状态：调研记录，不代表已选定第三方框架。目标是吸收成熟概念，并用言奏自己的 TypeScript / C# 数据契约实现；不直接引入 BML XML、完整 Gameplay Ability System 或研究型动作生成模型。

### 具身对话代理：意图、计划与实现分离

[BEAT](https://www.media.mit.edu/gnl/publications/siggraph2001.pdf) 将语言分析、非语言行为建议和最终动画/语音实现分开；[SmartBody](https://ict.usc.edu/pubs/SmartBody-%20Behavior%20Realization%20for%20Embodies%20Conversational%20Agents.pdf) 则把一份表演描述交给 Behavior Realizer，在运行时协调语音、凝视、手势、移动和动画控制器。它们支持当前边界：Electron 负责交际语义和高层请求，Unity 将请求实现为受约束的实时表演。

候选映射为三层，而不是让 AI 直接提交最终动画：

1. `BehaviorIntent`：为什么表达、面向谁、情感和语义动作是什么。
2. `PerformancePlan`：选中了哪些行为单元、它们如何同步、占用哪些通道、允许怎样退出。
3. `PerformanceInstance`：Unity 中正在执行的实例、当前阶段、权威进度和结果。

### 同步点优于绝对帧

[Behavior Markup Language 1.0](https://repository.cs.ru.is/attachments/download/843/bml-standard-1.pdf) 用命名同步点约束不同模态，而不是要求上层猜测逐帧时间。例如手势可具有 `start / ready / stroke / relax / end`，语音可提供词语或短语标记，面部动作可具有峰值与回落阶段。

言奏可以借用这一语义，但不照搬 XML：短手势以 `stroke` 对齐语音语义锚点；舞蹈、歌曲和剧情以稳定的命名标记描述段落边界、安全退出点和关键事件。绝对秒数只在资产实现层产生，AI 和外部宿主只引用语义标记。

### 柔性打断与基础状态恢复

[AsapRealizer 2.0](https://pub.uni-bielefeld.de/download/2690254/2690266/asaprealizer2.pdf) 的重要启发是增量计划和 graceful interruption：中断不是清空所有控制器，而是为受影响的行为生成返回基础姿态或基础凝视目标的过渡。[连续交互研究](https://ris.utwente.nl/ws/files/6035043/thesis_H_van_Welbergen.pdf) 还区分选择性中断、运行中参数更新和与外部事件重新同步。

因此候选规则是：

- 每个通道维护可恢复的 `GroundState`，例如基础姿态、默认凝视和心境表情。
- 取消请求可以选择通道，不自动清除整场表演。
- 行为声明可安全中断阶段；处于手势回收、落地或舞蹈转身等阶段时，可先完成短过渡再释放通道。
- 视线目标、表达强度、音频压低等参数允许在行为运行中更新，无需重启整个动作。
- 运行时返回已接受取消、等待安全点、开始退出和已恢复基础状态等进度事件。

### 游戏能力系统：自包含行为与标签仲裁

[Unreal Gameplay Ability System](https://dev.epicgames.com/documentation/en-us/unreal-engine/understanding-the-unreal-engine-gameplay-ability-system) 把能力建模为有生命周期的自包含执行单元，并通过标签表达激活条件、阻塞和取消关系。言奏不需要复制其战斗属性、联网预测和效果系统，但适合借鉴以下结构：

- 动作资产定义与运行时实例分离，同一动作可多次执行且各自有状态。
- 每个实例具有 `requested / accepted / running / exiting / completed / cancelled / failed` 等明确生命周期。
- 使用稳定语义标签描述通道占用与关系，例如 `Body.Full`、`Gesture.UpperBody`、`Speech.Active`、`Attention.User`，避免在中心调度器里持续增加动作名称特判。
- 标签只辅助声明约束；最终冲突仍由显式的通道所有权、优先级、用户指令和安全策略裁决。

[GDC 的多角色行为编排案例](https://media.gdcvault.com/GDC2014/Presentations/Bell_Brian_Multi_Actor_Behavior.pdf) 还提示长行为应预留可跳过的尾段或填充段，以便在等待后续条件时保持自然，又能及时响应。这适合转化为动作资产的可中断尾段和等待循环，而不是让调度器硬切动画。

### 对话输入不是统一的打断信号

全双工对话研究通常把用户声音进一步区分为反馈、抢话和真正接管话轮，而不是使用“检测到声音即停止”的单一规则。[Duplex Conversation](https://arxiv.org/abs/2205.15060) 将用户状态、backchannel 与 barge-in 分开处理；[DiscoRT](https://personales.upv.es/thinkmind/ACHI/ACHI_2014/achi_2014_16_20_20152.html) 也把参与度、轮次、打断、反馈和凝视作为协作模块。

这支持将输入先规范化为 `InteractionEvent`，再由本地策略和语义层判断：简短附和只触发注意或表情反馈，普通问题可以排队或请求安全退出，明确停止立即取消。ASR 尚未给出完整语义时，可以先做可逆的本地反射，不应抢先摧毁当前表演。

### 视线与主动行为都应选择合适模态

[虚拟代理凝视研究](https://www.microsoft.com/en-us/research/publication/designing-effective-gaze-mechanisms-for-virtual-agents/) 表明凝视同时承担关系建立和对象指示等交际功能，因此它应是独立语义通道，而非待机装饰。主动陪伴也不应默认等于主动说话：策略可以根据情境选择视线、表情、姿态、无声动作或语言，把语音留给确有交际价值的时刻。

### 暂不采用的部分

- 不引入 BML XML 作为产品协议；仅借用行为块、同步点、进度反馈和 Realizer 分层。
- 不完整移植 Unreal GAS；仅借用自包含实例、生命周期、标签与取消关系。
- 不在首期采用文本到手势或生成式人体动作模型；它们可作为素材扩展实验，不能替代确定性调度。
- 不因未来可能接入 MCP 或插件而提前暴露逐帧控制接口。

### 对当前开放问题的直接结论

- 数据契约应同时表达 `BehaviorIntent`、`PerformancePlan`、同步标记、通道声明和实例反馈。
- 打断协议不能只有 `stop`；至少区分立即取消、最近安全点退出、暂停、继续和分通道更新。
- 长表演资产除了 Clip 或 Timeline，还必须携带同步点、退出段、等待循环、通道策略和恢复信息。
- 第一轮原型应专门记录调度时间线，显示每个通道的所有者、阶段、标记和取消原因；否则多通道问题会很难诊断。
- 后续需要动作资产预览与校验工具，但它属于资产管线阶段，不阻塞首个运行时切片。

## 当前实现的初步判断

### 值得保留

- 独立 Unity Runtime 与透明桌面窗口方向。
- Core、UniVrm、Runtime 的依赖分层思想。
- `IAvatarRuntimeFacade` 单一外部控制入口。
- 带 Revision 的权威 Snapshot。
- 模型 `prepare → validate → commit` 事务与失败回滚。
- UniVRM 标准化 Control Rig、表情、视线和模型生命周期适配。

### 需要重新设计

- 固定的 `Idle / Listening / Thinking / Speaking` 不应同时充当产品状态和动画状态机全部结构。
- 固定 `AvatarPresetAction` 枚举、位标志 Capability 与全量动作库有效性不适合扩展动作资产。
- 当前“基础循环 + 全身单次动作”无法完整表达上半身手势、长表演和多通道所有权。
- 通用 Humanoid 动作播放不应归属于 UniVrm 适配层。
- `AvatarBehaviorSettings`、`AvatarPoseFrame` 与 Facade 需要重新划分意图、调度状态、表现参数和逐帧结果的职责。

## 首批验收场景

以下场景用于检验架构，不代表最终动作美术：

1. 角色说话时同时保持口型、看向用户并播放一次上半身解释手势，身体基础动作不中断。
2. 角色执行长时间轴舞蹈时，全身动作获得身体通道所有权，表情和视线仍可按策略运行；用户打断后在指定安全节点退出并自然回到待机。

- VRM Adapter 与 Katarune 专属角色包的能力边界。

- TTS 字词或音素时间线、流式语音和用户打断的接入顺序。
