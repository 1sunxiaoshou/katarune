# 技术选型

本页描述当前系统组成和责任边界。进度见[路线图](../03-规划/路线图.md)，选择的理由见[决策记录](../01-决策/决策记录.md)。

## 系统组成

| 部分 | 技术与职责 |
| --- | --- |
| 桌面宿主 | Electron；可信 main process 运行 Harness、模型调用和数据服务 |
| 产品界面 | React、assistant-ui、shadcn/Base UI、Tailwind CSS |
| 模型与工具 | AI SDK、Provider Registry 和 Provider Definition 薄适配 |
| 本地数据 | SQLite、better-sqlite3、Drizzle；记忆正文共用本地数据库 |
| 跨进程契约 | 共享 Zod Schema、最小 preload IPC 与原生消息流 |
| 语音 | 独立 TTS Capability；sherpa-onnx、SenseVoiceSmall INT8 与 Silero VAD |
| 数字形体 | 独立 Unity Runtime、URP、UniVRM、UniWindowController 与 uLipSync |
| 工具链 | npm、electron-vite、electron-builder/NSIS、Vitest 与 Unity CLI |

Node/npm 基线以 `.node-version` 和 `package.json` 为准，JS 依赖以 `package-lock.json` 为准。Unity Editor 和 Package 版本以 `ProjectVersion.txt`、`manifest.json` 与 UPM 锁文件为准；文档不重复维护完整版本清单。

## 责任边界

```text
Electron
├── Renderer：聊天、角色、设置、语音采集与普通朗读
├── Preload：受校验的最小 IPC
└── Main：Agent、模型/工具、角色、记忆、资产、凭据、语音服务
    ├── SQLite / 托管资源
    ├── 离线 ASR utilityProcess
    └── Unity 生命周期、会话绑定与可信管道

Unity Avatar Runtime
├── Core：行为契约、实例、通道与调度
├── Motion：Humanoid 动作与统一播放图
├── UniVrm：模型、Control Rig、表情与材质适配
└── Runtime：Facade、模型事务、音频、字幕、窗口、输入与沉浸镜头/背景
```

密钥、文件系统、数据库和工具执行权限留在可信边界。renderer 只通过 preload 提交受限请求；main 校验归属和权限，不相信前端给出的模型、系统提示词或授权状态。

外部框架已有的类型、消息格式、编码器和生命周期直接复用。SQLite、Electron IPC 与产品领域语义只做必要薄适配，不维护第二套 Agent Runtime、消息模型或通用 Provider 协议。

## 数据与模型

- `characters` 是角色与 Agent 的唯一身份；会话固定绑定角色，切换界面不改变已有会话归属。
- SQLite 保存角色、会话、模型配置与产品设置；消息使用 assistant-ui/AI SDK 原生持久化格式，Schema 与版本化迁移位于 `src/main/database/` 和 `drizzle/`。
- 长期记忆分为日记、人物和纪事，SQLite 保存 Markdown 正文、稳定标识、版本。阅读与原位编辑共用同一个 Tiptap 实例，只切换可编辑状态；标题布局与日记正文滚动容器保持不变，切换状态保留滚动位置，保存后的后台刷新不重建正文；长文连续滚动，不计算页数。其 Markdown、表格和任务列表扩展保持基础排版；文档模块进入记忆条目时按需加载，不引入编辑器云服务或新的存储格式。人物与纪事通过角色绑定的 `memory_search/read/save/forget` 按需读写；关键词检索和小型目录注入不依赖外部服务，短正文连同版本直接返回，长正文按需读取。人物关系与纪事进展写在正文中，不维护条目关联表或对话来源表；更新在事务中提交，遗忘内容退出检索。旧 Wiki 已退役，不迁移旧数据。
- 日记使用 main 中独立 AI SDK Agent，携带角色设定与当天文字对话，以第一人称生成纯文本／基础 Markdown；人物、纪事的检索和读取工具提供背景，`finish_diary` 无执行副作用地提交最终草稿，程序负责校验与保存。工具参数承载输出 Schema，不请求 JSON Schema 响应格式，不强制工具选择，不全局屏蔽 SDK 警告。按消息入库时的本地日期及时区排队，本地次日 00:01 及启动时处理待整理日期，每个角色的同一日记日期只自动尝试一次，失败或中断后手动重试。任务状态和受控失败原因分类持久化，不存储供应商原始错误；日记页显示最近失败日期、原因和重试入口，旧失败未记录原因时明确说明。输出经 Schema 与当天对话变化校验后写入，无内容则跳过。用户可在日记页关闭，退出应用取消在途生成。
- 托管资产以不可变文件和注册记录为事实来源；界面使用受限资产协议，不获得原始路径。附件仅在需要调用模型时物化，历史图片按需读取，不持久化 Base64。
- 凭据由 Electron `safeStorage` 加密，数据库只保存不透明引用；加密不可用时失败关闭。
- Provider Definition 负责供应商发现、模型检查和能力适配，Registry 负责模型解析。真实账号库存与用户配置决定可用性，公共目录只辅助识别，不能冒充自定义端点库存。
- 应用默认模型、TTS 模型与音色可由角色继承或显式覆盖；显式配置不可用时不静默回退。音色元数据刷新不覆盖用户设置。

## 对话、语音与形体

聊天沿用 AI SDK 原生流和 assistant-ui Runtime。每次运行使用独立 MessageChannel，具有背压和取消；模型、工具和凭据留在 main，不引入本地 HTTP 服务。

TTS 与 ASR 独立于 Agent 循环。普通朗读由 renderer 播放；匹配当前会话的桌宠由 Unity 播放，避免重复朗读。ASR 在 utilityProcess 离线推理，聊天 renderer 拥有唯一采集生命周期，胶囊只展示和控制。

Electron 将当前绑定会话的原生事件转发给 Unity，并提供按对白锚点编排日常动作与表情的 `avatar_perform` 和受限的 `avatar_control` 工具。配置了舞蹈的角色另有 `avatar_play({ action })`，伴奏和镜头由动作资源决定，播放独立于对白；Unity 先确认接收，再按前文播放顺序准备和启动，回报完成、取消或失败；演出占用声音和主字幕，期间回复仅保留在聊天记录，Main 获得逐块出声许可后才调用 TTS。实际状态在每步模型调用中提供，不自动唤醒 Agent。Main 解析能力与身份，Unity 拥有提示点执行、通道调度及播放时间线，Agent 完成不等待音频排空；正文直接作为对白，不定义 `speak` 工具。详细顺序、插话与资源回收见[角色行为与动画系统](角色行为与动画系统.md)。

角色包的身份、去重、绑定和导入事务由 main 管理，Unity 实际校验与加载模型/动画。导入准备使用独立 Unity 子进程，缺少 `idle` 时异步生成模型适配的次级骨骼循环并缓存；默认模型在构建前预烘焙。main 管理取消和发布，骨骼测量及播放仍由 Unity 拥有。角色包统一使用 v3：动作在 `actions` 定义，`idle` 与 `bindings` 引用稳定 key；单次动作、循环动作和同步演出共用主动画字段 `motion`。Unity 复用 Core 实例调度，main 不复制动画状态机。契约见[角色包格式](角色包格式.md)。窗口、输入、布局和字幕归属见[桌面交互设计](../00-项目/桌面交互设计.md)。

## 日志与诊断

D-075 已决定并接入。目标是通过本地诊断回答故障发生在哪个进程、操作和阶段，保留错误类型、HTTP 状态、原因链与安全栈位置，不索取聊天正文或密钥。原先 Main 的零散控制台、Unity 原始 Player 文件和界面提示不能组成完整记录；旧故障中已经丢弃的原因无法追溯恢复。

```text
Main / IPC 业务边界 ────────────────────────┐
Renderer / Preload ─ 最小 IPC ─────────────┤
ASR Worker ─ 原有进程消息 ─────────────────┤
Unity ─ 原有本地管道 ─────────────────────┤
                                         ↓
                Main：Schema 校验 → 安全字段投影 → 关联 / 限流 / 去重
                                         ↓
                有界队列 → 专用写入线程 → electron-log → JSONL
                                         ↓
                         设置页打开日志目录；内部接口提供状态与本地导出
```

### 存储与资源边界

- 唯一常规写入入口位于 `src/main/diagnostics/`；共享契约在 `src/shared/diagnostics.ts`。日志存于当前数据目录的 `logs/diagnostics/`，开发与安装版继续隔离，不使用业务数据库。
- 复用 electron-log 5.4.4 的文件传输、格式和轮转接口。同步 I/O 在专用 Worker 运行，Main 不等待磁盘；每批最多 32 条，收到完成确认后再发送。避免直接使用库内部没有容量限制的异步队列。[组件官方文档](https://github.com/megahertz/electron-log/blob/master/docs/transports/file.md)
- 单文件目标 5 MiB，目录最多 50 MiB，归档最长 7 天，活动文件定期滚动；单条最多 8 KiB。Main 全局待发队列 512 条、故障后备内存 512 条，优先淘汰 DEBUG。重复 ERROR 归并为同一故障编号并输出计数摘要；满载丢弃计数保留在诊断状态和退出事件中。
- Renderer 每来源每秒 20 条、突发 100 条。Main 从真实发送窗口确定身份，拒绝子 frame；renderer 不指定路径、进程身份或任意属性。不接管 console，不开放 electron-log 自带的任意对象 renderer 入口。
- 写入失败进入有限内存降级，10 秒后尝试重建写入线程，成功后补写并报告恢复。关闭最多等待 1.5 秒；硬崩溃与持续磁盘故障可能丢失末尾事件，不承诺零丢失。
- Unity 线程日志回调只提取安全字段并入队，独立计时器发送，避免音频/渲染线程做磁盘操作；断连时写 `avatar-runtime/unity-fallback.jsonl`，当前与旧文件分别约 512 KiB。该安全后备文件与常规日志隔离，不自动纳入导出。[Unity 6000.3 线程约束](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Application-logMessageReceivedThreaded.html)
- 生产 Player 以 `-nolog` 禁止原始引擎文件；工作清单位于 `avatar-runtime/avatar-package.json`。测试的原始 Editor 日志、截图与音频仍是显式验收产物，不进入诊断包。旧 logs 目录中的历史文件不自动删除或导出。

### 关联与异常责任

每条记录包含 schemaVersion、UTC timestamp / observedTimestamp、level、稳定 event、component、source、bootId、processInstanceId 和 Main sequence；Unity 原始序号另存 sourceSequence。按事件选用 operationId、parentOperationId、runId、dialogueId、toolCallId、performanceId、bindingEpoch、durationMs、outcome 与 incidentId。IPC 异步上下文使用 AsyncLocalStorage 透传，沿用现有业务 ID，不维护另一套播放状态，也不将 UUID 称为 OpenTelemetry TraceId。

目前接入启动/数据库打开/缓存降级/退出、受控 IPC 异常、AI 步骤与工具结果、流失败、对白出声许可、TTS 生成及首音、ASR 请求和子进程退出、Unity 错误、舞蹈与表演终态、播放状态、包验证失败及日记失败。普通级别不记录 token、音频帧、字幕每帧或麦克风数据。SDK 自身重试仍由 SDK 管理，保留 RetryError 与末次错误链，不虚构尚未开放的逐次重试回调。

负责处理失败的边界记录原始异常的安全投影；同一 Error 传播时复用故障编号。TTS、聊天与 IPC 错误提示携带编号，通知支持复制；降级记录结果，用户主动取消为正常终态。IPC 的 rejection 重新构造安全提示，避免 Electron 自动将原始异常、cause 与绝对栈路径打印到控制台。

错误投影只允许错误名、已审查错误码、HTTP 状态、可重试性、最多四层原因和十二条相对栈位置。自由 message 一律标记 messageRedacted；不序列化 SDK 请求/响应对象。API Key、认证头、Cookie、聊天/记忆/识别正文、SQL 参数、工具参数、音频、图片、完整 URL、用户名和绝对路径不进入日志。先白名单投影，再限长和编码；导出重新校验契约并投影错误字段。[OWASP 原则](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

### 生命周期与使用入口

日志在数据库、凭据和 AI 服务前初始化。启动写 session.pending；正常关闭且日志排空后删除，下次发现残留仅报告“上次未正常结束”。Main 未捕获异常/拒绝及初始化失败记录 FATAL 后以非零退出，不继续运行。Electron 记录 renderer 与 child 退出，ASR/Unity 记录退出码。Renderer 全局错误、拒绝与 React 根错误分别收集；Preload 采用 Electron preload-error 入口，避免重复订阅跨世界 window 事件。

设置 → 常规仅提供“打开日志目录”入口，与其他设置保持简洁一致；不展示日志统计、导出选项或详细诊断开关。打开失败沿用普通错误通知。状态、导出与临时 DEBUG 保留为内部诊断接口；导出按最近 1 小时/24 小时/7 天筛选，确认范围、事件数量和大小后保存本地 JSON，排除数据库、凭据、资源、原始引擎日志与转储。DEBUG 最长 30 分钟，重启恢复 INFO。无远程上传。

原生内存转储仍为待单独授权的可选诊断能力，默认不采集；普通 JS 日志不等于原生崩溃栈，Electron 也不覆盖独立 Unity Player 的原生崩溃。验证入口和当前边界见[工程规范](../04-开发/工程规范.md#日志与诊断验证)。

## 分发与扩展

舞蹈镜头使用自包含的 glTF 2.0 GLB，由标准节点动画和 `KHR_animation_pointer` 表达位姿与相机参数。复用 UniGLTF 文件解析，Unity 直接求值标准曲线；参考身高、动画选择与跨相机切换放在包清单。Main 进行有界容器校验并管理资源，Unity 验证实际时长、按舞蹈音频游标采样和恢复构图。VMD 在制作阶段转换，不增加运行时 MMD 依赖。格式与制作入口见[角色包格式](角色包格式.md)，选择依据见决策 D-073。

Windows 内部包通过 electron-builder/NSIS 分发，已包含 Unity Player、默认资源与离线语音权重；默认卸载保留个人数据，覆盖更新不清理数据。构建准备和验证入口见[工程规范](../04-开发/工程规范.md#windows-内部发行包)。

当前技术边界服务于数字生命的阶段性实现。游戏、虚拟世界、实体躯体以及 MCP/ACP 等扩展按具体需求选择方案，不提前建立平台适配或通用工作流。
