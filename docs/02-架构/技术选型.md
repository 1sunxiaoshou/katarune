## 逻辑架构

```text
Electron Desktop
├── Sandboxed Renderer
│   ├── assistant-ui
│   ├── Chat and Asset Management
│   └── Audio Input / Playback
├── Preload
│   └── Minimal Typed IPC Bridge
└── Trusted Main Process / Katarune Harness
    ├── AI SDK Agent
    ├── Provider Registry
    ├── Character Context and Policy
    ├── TTS / ASR Capabilities
    ├── SQLite Thread and Message Store
    └── Optional Utility Processes / Protocol Clients
```

长期记忆不等于会话历史。P1 与 P2 先建立可恢复的线程和消息存储；记忆的提取、检索、更新、遗忘与用户控制在独立调查后再确定，不提前创建记忆表或工具接口，也不迁移 ATRI Chat 的旧文件记忆。

VRM 仍属于言奏的目标能力，但渲染技术、资产边界和驱动接口尚未确定。当前原型不引入 VRM Runtime 或 VRM 工具；相关组件只在独立技术调查通过后进入上述运行时边界。

## 已验证的数据库与打包基线

- Drizzle Schema 位于 `src/main/database/schema.ts`；使用 `drizzle-kit@0.31.10` 生成版本化 SQL，并提交 `drizzle/` 目录。
- main process 启动时先打开用户数据目录中的 `katarune.sqlite` 并启用 WAL 与 busy timeout；执行需要重建表的版本化迁移时暂时关闭外键约束，迁移提交后立即恢复外键并通过 `foreign_key_check` 验证引用完整性。renderer 只能通过 preload 的最小类型化 IPC 读取状态。
- `threads` 保存 assistant-ui 线程元数据，并以不可变的 `character_id` 外键绑定角色；所有线程 IPC 和 adapter 查询均携带角色范围。`messages` 保存 `ThreadHistoryAdapter.withFormat` 产生的框架原生记录；renderer 使用对应 format adapter 的 `encode` / `decode`，言奏不维护第二套消息结构。线程删除通过 SQLite 外键级联清理消息。
- `provider_configs` 保存非敏感 Provider 创建配置；系统生成的 UUID `id` 同时作为数据库主键与 AI SDK Registry Provider Key，共享 Zod 契约限制可选 HTTP(S) Base URL、JSON 设置和已支持的 `provider_type`，API Key 与 Token 不进入 SQLite。
- `model_configs` 保存供应商外键、动态检查得到的单一 AI SDK Registry 模型类别、厂商原始模型 ID、可空显示名称、模型级 `speech_metadata`、能力设置和启用状态。Speech 元数据只包含音色 ID、展示名称、可选描述和模型默认 Voice ID；`voices = null` 表示无法枚举。唯一约束为供应商配置与模型 ID；删除供应商时级联删除模型。Provider/model settings 的共享 IPC 外层为最大 64 KiB 的 JSON Object 或 `null`，写入和 Runtime 解析前由对应 Definition/Capability Schema 再次验证。无 Adapter 或 settings 失效的记录不自动删除或改写。
- `characters` 是角色与 Agent 的唯一实体，保存角色名称、立绘资产外键、卡片专用的 `0–1` 焦点位置与 `1–3` 缩放、可空语言模型软引用、成对出现的可空声音模型软引用与 voice、系统提示词和时间戳，并按创建时间倒序展示。单行 `app_state` 以外键保存活动角色。角色表为空时从经过 Schema 校验的 `resources/characters/default-character.json` 初始化；已有数据库始终优先。新角色先作为 renderer 草稿存在，离开且有实际改动时才由 main process 生成 UUID 并一次写入；无改动草稿不进入 IPC 或 SQLite。删除角色显式事务清理所属线程，消息沿线程外键级联删除；若删除活动角色则先切换到相邻角色，唯一角色拒绝删除。语言或声音模型被删除、禁用或改变类别后保留原 ID，由角色编辑页显示不可用状态。
- `assets` 是通用资产注册表；`ready` 记录必须具备 MIME、字节数、SHA-256 和原始文件名，`missing` 记录保留稳定引用但不伪造元数据。文件保存在用户数据目录的不可变 `assets/<uuid>` 对象中，renderer 通过受限 `katarune-asset://asset/<uuid>` 协议消费，不接收 Base64、storage key 或绝对路径。当前 PNG/JPEG/WebP 立绘先经 `asset-staging/<uuid>.tmp` 暂存，renderer 仅可通过 `no-store` 的 `katarune-asset://staged/<uuid>` 预览当前进程登记项；保存时文件、资产记录、角色与卡片取景参数整体提交，失败恢复暂存供重试，取消与下次启动负责清理。
- 聊天附件采用“本地资产事实来源、发送时按 Provider 能力物化”的目标边界，尚未实现。assistant-ui 继续负责附件 UI 和 `AttachmentAdapter` 生命周期；`KataruneAttachmentAdapter` 只负责经 preload/IPC 导入托管资产并产生 AI SDK 原生 `FileUIPart`。SQLite 消息保存 `katarune-asset://asset/<uuid>`，不保存 Base64 或原始绝对路径；main process 调用模型前再优先注入缓存的 `providerReference`，或通过 AI SDK `uploadFile()`、临时内联字节/Data URL 转换为当前 Provider 可接受的输入。附件库允许保存未知格式，模型不支持时在发送阶段明确报错，不把本地保存能力伪装成模型理解能力。消息资产引用索引只服务关系查询和垃圾回收，Provider 引用缓存不取代本地资产身份。
- 模型发现和检查由对应 `ProviderDefinition` 实现，main process 编排器只负责安全凭据、Schema 校验和持久化。导入时 `inspectModel()` 的明确类型覆盖 renderer 提示，冲突时拒绝；未知类型必须由用户确认。Speech 检查结果随模型写入 SQLite，刷新失败不覆盖旧元数据。Gateway 原生目录、LiteLLM 类型补充、完整快照与在线未命中回退规则保持不变：401/403 不回退，未知自定义 Base URL 与 Gateway 失败时不以静态目录伪装实时库存。
- 随应用分发的 LiteLLM 目录位于 `src/main/ai/litellm-models.json`，`litellm-models.meta.json` 记录上游来源、许可证与获取时间。维护者使用 `npm run models:snapshot` 显式更新并审查两份文件的差异；安装、启动和构建均不自动联网刷新。在线未命中回退只在当前 main process 内复用，不写回快照或用户数据库。
- 开发环境和 Windows x64 unpacked 产物均通过首次迁移、写入、关闭、二次启动和同记录恢复验证；打包产物包含迁移文件，并为 Electron ABI 重建和 ASAR 解包 `better-sqlite3`。
- `npm run test:database` 会在 Electron ABI 下创建隔离的临时数据库，验证线程与 `ai-sdk/v6` 消息、Provider/模型配置的写入、同类型 Provider 多实例、同一 Provider/model ID 禁止重复、模型类型纠正、关闭重开恢复、更新和级联删除；角色边界覆盖固定默认值、确定性倒序、唯一角色拒删、非活动角色删除、活动角色原子切换、普通与归档线程计数、消息级联、立绘资产保留和失败回滚；同时覆盖已执行旧本地 Provider 身份迁移的数据库升级到合并后迁移链且保持 Provider、模型与外键引用，并在结束后清理测试数据。
- 当前 Windows x64 unpacked 目录约 382.96 MiB，其中 `app.asar` 约 32.08 MiB，`app.asar.unpacked` 约 1.83 MiB 且只包含 `better_sqlite3.node`。无签名 `Katarune-Setup-0.1.0.exe` 约 111.30 MiB，配套 blockmap 约 120.59 KiB；`latest.yml` 引用与实际文件名一致。ASAR 已排除 source map、依赖测试目录以及 `better-sqlite3` 的源码和构建中间文件；只供 renderer 使用的 React、assistant-ui 与其他 UI 依赖由 Vite 打入 renderer，不再作为生产 `node_modules` 重复进入 ASAR。main process 仍使用 assistant-ui Toolkit 的两个入口，但在 main 构建时树摇内联，并显式保留其运行时所需的 `@ai-sdk/mcp` 与 `assistant-stream`。隔离用户目录的首启、默认立绘资产协议和 SQLite 原生模块烟测通过；实际安装后的占用、差分下载量及其他平台产物仍须单独验证。
- 正式应用标识为 `app.katarune.desktop`。Windows x64 目标为 per-user one-click NSIS，macOS 为分别面向 x64/arm64 的 DMG 与 ZIP，Linux x64 为 AppImage 与 DEB；当前不提供 Portable、NSIS Web、MSI 或 Squirrel。
- Windows 卸载器继续使用 electron-builder 默认 `.nsi`，只通过 `resources/installer.nsh` 增加原生清理范围页。手动卸载默认保留数据库、角色资产、会话、设置与凭据，只清理明确允许的缓存和暂存目录；可选的全部删除不接受用户路径。静默更新跳过页面和数据清理。
- Windows NSIS 保持 normal、7z 与差分感知包，Linux AppImage使用 blockmap；当前 Windows 产物、blockmap 与更新元数据已生成并确认无签名。更新 Runtime、托管后端、签名和公证尚未接入，不应把生成更新元数据等同于已具备在线更新。

## 已验证的 AI 框架基线

- AI SDK 7 以 ESM 形式运行在 Electron main process；无密钥验证使用 `ai/test` 的确定性 mock model，覆盖 Provider Registry、`ToolLoopAgent` 和流式文本。
- `provider_configs.id` 是供应商实例身份的单一来源，同时作为数据库主键、模型外键目标与 AI SDK Registry 的稳定 `providerId`；`provider_type` 选择代码级 Provider Definition。共享 Provider 配置只声明 renderer 表单所需的 `credentialMode`。Definition 提供 discovery、inspection、settings Schema、AI SDK factory 和实际 Capability Adapter；可调用模型 ID 由 main process 根据这些方法与当前配置动态返回，不维护供应商支持类型数组。
- `provider_type` 的唯一来源是 `src/shared/providers.ts`。当前枚举包含 `gateway`、`openai-compatible`、`openai`、`anthropic`、`google`、`fish-audio`、`deepseek`、`xai`、`moonshotai` 与 `alibaba`。其中 `gateway` 使用 AI SDK 的 Gateway Provider；`openai-compatible` 用于兼容端点并允许无凭据的本地服务；Fish Audio 没有已锁定的官方 AI SDK Provider，项目内只实现其 `SpeechModelV4` 薄适配，不新增 SDK 依赖。统一 AI SDK Provider Registry 同时解析语言与语音模型；其他类别或供应商是否可调用继续由 Definition 的实际 Capability 方法决定。
- 当前 `ai` 核心包直接包含 AI Gateway；已锁定 `@ai-sdk/openai-compatible@3.0.12`、`@ai-sdk/openai@4.0.16`、`@ai-sdk/anthropic@4.0.16`、`@ai-sdk/google@4.0.18`、`@ai-sdk/deepseek@3.0.12`、`@ai-sdk/xai@4.0.16`、`@ai-sdk/moonshotai@3.0.15` 与 `@ai-sdk/alibaba@2.0.14`。Runtime 只使用这些包公开的 factory，并在配置变化后重建 Registry。Ollama、OpenRouter 等社区或兼容服务当前通过 `openai-compatible` 表达。
- `model_configs.settings` 的语言能力 Schema 当前对应 AI SDK 通用 `LanguageModelCallOptions` 的受控子集，包括最大输出 token、temperature、top-p、top-k、存在/频率惩罚、停止序列和 seed；Runtime 使用 `wrapLanguageModel` 与 `defaultSettingsMiddleware` 应用默认值，不建立第二套调用设置。不同 Provider 或模型类别的差异留在各自 Definition/Capability Schema；未经验证的数据不得持久化或调用，其他模型类别不会回退到语言模型。
- main process 使用 Electron 异步 `safeStorage` 加密凭据，密文保存在用户数据目录的独立文件中，SQLite 只保存 `credential_ref`。preload 只接受替换和清除凭据的写入式请求，不提供读取、列举 secret 或由 renderer 指定 `credential_ref` 的方法；操作系统加密不可用时不启动 AI Runtime。`npm run test:credentials` 已在真实 Electron 进程验证加密、解密和删除。
- `npm run test:ai:deepseek` 只在显式执行时从被 Git 忽略的 `.env.local` 读取 `KATARUNE_TEST_DEEPSEEK_API_KEY`，并已验证 `safeStorage → credential_ref → DeepSeek factory → Registry → model_configs → generateText` 的真实链路。该命令会调用付费外部 API，不属于普通 `npm test`。
- assistant-ui 的 `useChatRuntime`、`RemoteThreadListAdapter`、格式化 `ThreadHistoryAdapter` 与 `AssistantRuntimeProvider` 已在 sandboxed renderer 中成功挂载。标题流使用其官方底层包 `assistant-stream@0.3.26` 的 `createAssistantStream`，不手写流分块。角色存在模型软引用时允许发送；未选择模型时保持发送禁用。角色存在可用 OpenAI SpeechModel 与 voice 时，`useChatRuntime` 注入 `KataruneSpeechSynthesisAdapter`，消息操作区直接使用 assistant-ui 原生朗读/停止状态。
- main process 的 TTS 服务按角色权威配置解析同一个 Provider Registry 中的 SpeechModel，并把角色保存的不透明 Voice ID 原样交给 Provider；音色目录只服务 UI 选择，不参与保存或调用白名单。OpenAI、Google Gemini 与 Fish Audio Adapter 都请求并校验 WAV；Google Provider 包负责把返回的裸 PCM 无损封装为 WAV。角色界面按 `speechModel` 类型构建“可搜索目录 + 手动 Voice ID”编辑区，目录为空时只显示手动输入。缓存、取消、错误清洗和 renderer 播放继续沿用单次生成式 TTS 边界。
- Provider Factory、动态 Registry、显式模型连接测试、Provider/模型设置页、角色级模型选择与受信任密钥录入已接入；应用级默认模型尚未实现。renderer 为窗口内访问过的每个角色按需保留独立 `RemoteThreadListRuntime`，每个线程 Runtime 再持有独立 `AssistantChatTransport`；其自定义 Electron fetch 通过 preload 管理的每次运行独立 `MessageChannel` 接收 main process 产生的 AI SDK SSE 字节流。pull 帧提供背压，cancel 或端口关闭触发 main 中的 `AbortController`，不同线程和角色可并发生成且传输状态互不复用。main 根据线程绑定读取角色、模型和系统提示词，不信任 renderer 提交的模型或 Agent 配置，并登记活动流以在线程、角色或窗口销毁前定向取消。聊天 Agent 通过应用级 `AISDKToolkit` 聚合层合并 main 中的可信工具、当前模型对应的 Provider 原生工具与 IPC 校验后的 frontend tools；前端只上传名称、描述和 JSON Schema，不上传执行函数，且不能覆盖任一可信同名工具。`ToolLoopAgent` 最多执行 8 步，renderer 在前端工具结果或审批响应完成后使用 AI SDK 官方条件自动续跑。默认 main 工具只有无参数、无高权限的 `get_current_time`，按需返回用户设备当前的带 UTC 偏移本地时间和 IANA 时区；OpenAI、Anthropic、Google、xAI 及其 AI Gateway 上游模型按各 SDK 官方名称条件化装配原生 Web Search/Web Fetch/URL Context，其他 Provider 不伪装支持，当前不接第三方搜索后端或自研计算器。首次对话完成后，assistant-ui 的标题生命周期通过普通 invoke IPC 请求 main 创建独立标题 Agent；该 Agent 复用角色绑定模型和系统提示词但不复用聊天实例或工具，输出限制为 80 token、结果限制为 30 字符并直接写入 SQLite。当前不恢复应用退出时仍在运行的流。
- renderer 使用 assistant-ui Registry 成品 Thread、受控 Model Selector 与 shadcn/ui `base-nova`、`neutral` 默认配置，底层为 Tailwind CSS 4、Base UI 与 Lucide；Provider 品牌图标来自 Lobe Icons 的静态 SVG 包并随应用打包，OpenAI-compatible 继续使用通用网络图标。亮色/暗色主题复用 shadcn 默认语义 token，以根元素 `.dark` 类切换并将偏好保存在 renderer 本地，不维护产品级颜色系统、基础组件包装层或平行视觉 token。设置页以“常规 / 模型”一级 Tab 组织；模型页实时展示 SQLite 中的供应商配置，并按共享 `model_type` 契约展示模型列表与类别筛选。发现模型只展示模型名称、ID 和已确定的单一类型；目录未知或冲突时显示问号，添加时强制选择。供应商条目通过悬停或聚焦操作编辑和删除，供应商与模型的创建/编辑分别复用通用 Dialog，删除复用通用确认 Dialog。模型区顶部只保留搜索、创建和获取操作；搜索对名称、ID、类别、状态和供应商执行本地分词 AND 匹配，并与类别筛选叠加。
- renderer 根节点挂载统一通知中心。业务通过言奏通知 API 发送通知，Base UI Toast 只承担右上角 Portal、三条上限、计时、键盘导航和播报，Zustand 内存 store 按 scope 管理 Inline；两种渠道均不进入 IPC、SQLite 或重启恢复。页面级一次性操作的成功、警告、失败与短时加载统一使用 Toast，模型列表、角色页和会话列表不挂载 Inline outlet；只有需要用户在当前 Dialog 或表单中就地修正的错误才使用对应 scope 的 Inline。页面加载/空状态、角色自动保存、确认框内部错误以及 assistant-ui 模型生成、流和工具错误继续由所属状态表达，不并入通用通知。
- 聊天页使用可完全收起的弹性左侧栏：顶部直接复用角色页列表的 `CharacterCard`，中段通过 assistant-ui `ThreadListPrimitive.Root/New/Items` 和 `ThreadListItemPrimitive.Root/Trigger/Title` 渲染当前角色的普通会话，左下角始终悬浮无容器底板的设置与内容显隐图标按钮，侧栏在展开状态下为其预留底部空间。会话项不建立镜像状态，切换、重命名、归档和删除直接使用当前角色的 `RemoteThreadListAdapter`；消息持久化后调用线程列表 `reload()`，使 assistant-ui 在窗口运行期间同步最新标题、消息活动时间和排序。SQLite 的 `last_message_at` 只随消息写入更新，普通 `updated_at` 继续记录标题、归档等元数据修改，列表按前者排序。Base UI Context Menu 只承担右键菜单交互。归档项不进入星轨，管理入口待后续规划。角色卡与列表作为同一可访问性区域分层显隐；隐藏时侧栏收至零宽度，聊天主区扩展至完整窗口，左下角按钮的几何位置与外观保持不变。显隐偏好仅保存到 renderer 本地，不进入 SQLite、IPC 或角色状态。

## 动态上下文与缓存边界

[D-029](../01-决策/决策记录.md#d-029--动态上下文工具提示与缓存边界) 将后续角色、工具和环境信息按 AI SDK 原生作用域组织，避免形成随功能增长的全局工具提示词：

| 信息 | AI SDK 位置 | 模型可见性 | 言奏约束 |
| --- | --- | --- | --- |
| 角色身份、长期行为与安全规则 | 稳定 `instructions` | 可见 | 由 main process 从角色配置构造，不接受 renderer system message |
| 当前日期与用户时区 | `callOptionsSchema` + `prepareCall` → `instructions` 末尾两行文本 | 可见 | main process 产生并传入 call options；字段、顺序和格式固定，不包含时分秒 |
| 其他模型确实需要的请求级动态数据 | `callOptionsSchema` + `prepareCall` | 由 `prepareCall` 显式加入后可见 | 只传可信、最小、与当前回答相关的数据 |
| Agent 共享执行状态 | `runtimeContext` | 默认不可见 | 用于请求 ID、feature flag、步骤状态和生命周期，不承载给模型看的说明 |
| 工具专属配置与敏感值 | `toolsContext` + `contextSchema` | 默认不可见；动态 description 可选择性读取 | 每个工具只接收自己的 context；密钥、绝对路径和内部 ID 不进入描述 |
| 工具选择提示 | `description` 与参数 Schema 描述 | 可见 | 基础描述保持稳定；只在模型决策确实依赖当前 context 时动态生成 |
| 工具可用范围、顺序与审批 | `activeTools`、`toolOrder`、`toolApproval` | 以工具定义或审批结果体现 | 权限由可信配置执行，不用自然语言提示代替授权 |
| 多步循环中的变化 | `prepareStep` | 取决于返回的 messages、instructions、tools 或 context | 只用于步骤间真实变化、消息压缩和 Provider 缓存断点 |

每次聊天模型调用使用以下固定格式，并将内容追加在角色 instructions 之后：

```text
Current date: 2026-07-28
Time zone: Asia/Shanghai
```

`currentDate` 必须由 main process 按 `timeZone` 计算为 `YYYY-MM-DD`，`timeZone` 必须是已解析的 IANA 时区标识；二者作为 call options 传入 Agent，经 `callOptionsSchema` 校验后由 `prepareCall` 写入 instructions。renderer 不得直接提供或覆盖这些值。未来增加 locale、设备状态或工具相关字段时，不得直接扩展这段内容，必须先确认模型是否需要、值多久变化以及是否更适合放入工具 context。

缓存优化遵循“稳定前缀、变量后置、按 Provider 验证”：

- 稳定的角色 instructions、工具名称、Schema、基础 description 与工具顺序优先进入可复用前缀；`toolOrder` 用于保持发送给 Provider 的工具顺序稳定。
- 高频变化但不影响模型判断的数据只留在 `runtimeContext` 或 `toolsContext`。动态 description 也是模型输入，变化时同样可能截断可缓存前缀。
- 两行环境说明固定放在稳定角色 instructions 之后，不写入时分秒；同一日期和时区内保持逐字节一致。日期跨天或用户时区变化时，该位置之后的缓存前缀可能失效，这是为保证模型默认具备日期与时区认知而接受的低频代价。
- 当前只在 instructions 中提供日期和时区；需要精确时分秒时调用 `get_current_time`，不假设存在隐式系统能力，也不依赖历史工具结果。
- Anthropic 可按 AI SDK Dynamic Prompt Caching 模式在 `prepareStep` 中为最后消息设置 `cacheControl`，OpenAI 使用对应的 prompt cache options/key，Google 使用隐式缓存或 cached content；这些分支保留在 Provider 边界，不抽象成同构能力。
- 接入缓存优化前后记录 `usage.inputTokenDetails.cacheReadTokens` 与 `cacheWriteTokens`，并使用 `include.requestMessages` 或 Provider request body 检查最终发送内容。短上下文可能达不到 Provider 最小缓存 token，不以存在配置项作为命中证据。

当前已实现日期与时区的 call options、Schema 校验和 `prepareCall` instructions 注入，以及按需返回带 UTC 偏移本地时间与 IANA 时区的 `get_current_time`；动态工具 context、缓存断点与缓存观测尚未实现。后续每接入一种工具，先判断提示属于全局角色规则、请求动态上下文、工具 description、参数 Schema 还是不可见执行 context，再决定最小放置位置。
