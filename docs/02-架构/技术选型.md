# 技术选型

本文只记录当前共识与需要验证的候选项，不提前锁定尚未讨论完成的依赖版本、打包和长期记忆方案。

## 已确认的方向

| 领域 | 方向 | 状态 |
| --- | --- | --- |
| 语言 | TypeScript 优先 | 已决定 |
| UI | React + assistant-ui | 已决定 |
| Agent 基础 | AI SDK | 已决定 |
| 产品形态 | Web 技术驱动的 Windows 桌面应用 | 已决定 |
| 桌面容器 | Electron | 已决定，待原型验证 |
| Harness 运行时 | Electron 内置 Node.js | 已决定，待版本锁定 |
| 数据 | SQLite + `better-sqlite3` + Drizzle ORM 稳定版 | 已决定，待版本与迁移流程锁定 |
| 模型运行时管理 | AI SDK Provider Registry + 官方 Provider + OpenAI-compatible Provider | 已决定 |
| 用户供应商配置 | 本地配置 + 系统安全凭据 + Registry 薄适配 | 待设计 |
| 通用扩展 | 优先 MCP、ACP 或成熟实现 | 原则已决定 |
| TTS/ASR | 独立 Capability，不与 Agent 循环耦合 | 架构方向已确认 |
| VRM | 言奏原生核心能力 | 已决定 |
| 长期记忆 | 重新调查与设计，旧文件记忆仅作迁移参考 | 待决定 |

## 逻辑架构

```text
Electron Desktop
├── Sandboxed Renderer
│   ├── assistant-ui
│   ├── Chat and Asset Management
│   ├── VRM Runtime
│   └── Audio Input / Playback / Lip Sync
├── Preload
│   └── Minimal Typed IPC Bridge
└── Trusted Main Process / Katarune Harness
    ├── AI SDK Agent
    ├── Provider Registry
    ├── Character Context and Policy
    ├── VRM Tools
    ├── TTS / ASR Capabilities
    ├── SQLite Thread and Message Store
    └── Optional Utility Processes / Protocol Clients
```

长期记忆不等于会话历史。P1 与 P2 先建立可恢复的线程和消息存储；记忆的提取、检索、更新、遗忘、用户控制与旧文件迁移在独立调查后再确定，不提前创建记忆表或工具接口。

## 首个原型需要回答的问题

首个技术原型应使用一条最小链路验证已选组合，并暴露仍待解决的版本与打包风险：

1. 启动桌面应用。
2. 读取本地供应商配置。
3. 流式完成一次模型回复。
4. 执行一个类型安全的前端 VRM 工具。
5. 将线程写入 SQLite 并在重启后恢复。
6. 完成 Windows 开发构建和可分发构建。

需要记录的指标包括：

- 冷启动时间与空闲内存。
- 安装包和解压后的体积。
- Electron main、preload 与 renderer 的 TypeScript 开发体验和调试链路。
- `better-sqlite3`、音频和 ASR 等原生依赖的重建与打包难度。
- AI SDK、assistant-ui 与测试工具的兼容性。
- Windows 签名、更新和崩溃诊断能力。

## 暂不引入的抽象

- 自定义 Agent 基类体系。
- 自定义模型 Provider 通用协议。
- 与 AI SDK 重复的消息流协议。
- 为每个工具实现自有远程调用标准。
- 在验证单 Agent 闭环前设计多 Agent 平台。
