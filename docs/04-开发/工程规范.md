# 工程规范

本文定义言奏共同遵守的代码、文档、版本和提交规则。P1 已锁定类型检查、构建与测试入口；格式化、Lint 和发布自动化在对应需求明确后独立选择，工具尚未落地不影响以下规则生效。

## 任务闭环

每项变更开始前说明：

- 用户价值：变更解决什么实际问题。
- 范围：本次会修改哪些系统边界或交付物。
- 非目标：哪些相邻问题明确留待后续处理。
- 验收条件：用什么可观察结果判断完成。

实现时只修改完成任务所需的范围。提交前检查差异，并按变更风险运行当前仓库已经提供的格式、类型、测试、构建或实际交互检查。仓库尚未提供的命令不得在文档或交付说明中声称已经通过。

## 代码规则

### TypeScript

- 新增 TypeScript 工程必须启用严格类型检查；不得用全局关闭严格模式来绕过局部问题。
- 对外部输入、持久化数据、跨进程消息和工具参数进行运行时校验；TypeScript 类型不能替代边界校验。
- 共享契约保持单一来源，由调用方复用或推导类型，不在 renderer、preload、main process 和可选 Worker 间手工维护重复结构。
- 外部框架已有公开类型、消息格式、编码器或 adapter 时直接复用，不为“解耦”复制一套同构接口。必要转换只能出现在明确边界中，并集中在一个可测试 adapter 内。
- 不为尚不存在的数据迁移或多版本运行需求提前编写兼容层。真实兼容需求出现时，记录来源版本、目标版本、淘汰条件和回归测试。
- 优先使用显式、可组合的函数和数据结构；只有存在稳定的领域不变量时才增加抽象层。
- `any`、非空断言和类型强制转换只用于已经验证但类型系统无法表达的边界，并在邻近位置说明原因。

### 模块与安全边界

- 角色、记忆、语音、VRM 和桌面能力通过明确接口连接，不把供应商细节泄漏到产品领域模型。
- 密钥、文件系统、数据库和高权限工具留在受信任边界；不将真实凭据、个人数据或本地绝对路径写入源码、测试夹具和日志。
- TTS 与 ASR 保持独立 Capability；工具调用和消息流沿用 AI SDK、assistant-ui 或已选协议，不建立重复的通用 Runtime。
- 新依赖必须解决明确问题，记录采用理由，并提交对应锁文件；依赖升级不得顺带混入普通功能变更。

### 命名与文件组织

- 代码标识符与文件名使用英文；产品文案和项目文档以中文为主，保留必要的英文术语与官方名称。
- React 组件使用 `PascalCase`，普通变量与函数使用 `camelCase`，常量仅在确为固定值时使用 `UPPER_SNAKE_CASE`。
- 测试靠近被测模块或放入该模块约定的测试目录；同一子项目内保持一种方式。
- 不创建含义宽泛的 `utils`、`helpers` 或 `common` 聚合层；文件和模块名称应表达所属领域与职责。

### Renderer 设计系统

- 产品视觉要求与上游默认值的边界以 `design-system/katarune/MASTER.md` 为准。它是约束与决策记录，不是另一套基础组件库。
- 通用聊天界面从 assistant-ui 官方 Registry 成品组件开始；通用控件从 shadcn 组件开始。不得为了包装相同 props 或 class 名再创建一层 Button、IconButton、Surface 等镜像组件。
- 自定义顺序为：shadcn 语义颜色变量 → 使用点 `className` → Registry 组件的最小源码修改。只有前一层无法表达已确认的产品需求时才进入后一层。
- 字体、组件内部内容宽度、动效、间距、状态与可访问行为在上游已有合理实现时直接采用，不创建言奏 token。页面自身布局没有上游所有者时才在页面范围定义。
- 普拉娜与阿洛娜主题只覆盖 shadcn 标准语义颜色及确有需要的会话扩展色，不复制圆角、阴影、字体、动效或组件结构。
- 图标统一使用 Lucide。图标按钮必须具有可访问名称；Tooltip、焦点、禁用和加载状态优先使用 shadcn 现成能力。
- assistant-ui 官方 Thread 的 `components` 覆盖接口可以使用；被弃用的是 Primitive 迭代器旧式 `components` prop。直接使用 primitives 的新代码应采用 children render function、`MessagePrimitive.Parts` 或 `GroupedParts`，不使用 `MessagePrimitive.Content` 或 Primitive `.If`。

### 自动化工具

- 格式化、Lint、类型检查和测试命令一旦在 P1 锁定，应通过根级脚本提供统一入口，并可在 Windows 开发环境和 CI 中非交互运行。
- 自动生成文件应标明来源并通过命令可复现；除非构建或分发确实需要，不提交构建产物。
- 不用自动格式化或批量重写掩盖无关差异。

当前统一入口：

- `npm test`：以 Vitest 非交互运行全部自动化测试。
- `npm run test:watch`：本地开发时监听测试变化，不用于 CI。
- `npm run validate:ai`：只运行 AI SDK 确定性兼容测试。
- `npm run test:database`：在 Electron ABI 下验证 SQLite 迁移、线程消息与 Provider/模型配置的重启恢复和删除语义。
- `npm run test:credentials`：在真实 Electron main process 中验证 `safeStorage` 加密、解密和删除，不使用真实凭据。
- `npm run test:ui`：构建后在不可见 Electron 窗口中验证设置页、左下角入口和普拉娜/阿洛娜语义颜色主题；不会打开需要手动关闭的窗口。
- `npm run test:ai:deepseek`：显式读取 `.env.local` 中的 `KATARUNE_TEST_DEEPSEEK_API_KEY` 并执行一次最小真实模型调用；可能产生费用，不进入普通测试或 CI，也不得输出密钥和回复内容。
- `npm run typecheck`：检查 main、preload、renderer、共享代码和测试类型。
- `npm run build`：先执行类型检查，再构建 Electron 三个上下文。

共享 IPC 契约位于 `src/shared/ipc.ts`。Schema 是运行时结构与 TypeScript 类型的单一来源；main process 产生跨进程数据时校验，preload 在暴露给 renderer 前再次校验。新增 channel 必须同时增加 Schema、推导类型和有效/无效输入测试。

## 文档规则

- README 只保留项目定位和导航；产品定义、决策、架构、规划与开发规则分别进入现有 `docs/` 主题。
- 使用“已决定”“待决定”“暂缓”等状态明确区分事实与候选方案，不把倾向写成当前实现。
- 新架构选择先记录到决策记录；系统边界变化同步技术选型；路线或优先级变化同步路线图。
- 文档应说明当前状态与理由，避免复制外部框架手册；外部事实链接官方来源，具体 API 以项目锁定版本为准。
- 文件重命名或导航变化时同步修复仓库内链接。仅做代码实现且事实和决策未变化时，不为制造记录而修改文档。

## 版本规则

- 项目发布版本遵循语义化版本 `MAJOR.MINOR.PATCH`，Git 标签使用 `vMAJOR.MINOR.PATCH`。
- 在首个稳定公开版本前使用 `0.y.z`：兼容范围扩大或形成新的可验证里程碑递增 `MINOR`，向后兼容的修复递增 `PATCH`。
- 进入 `1.0.0` 后，不兼容的公开契约或用户数据格式变化递增 `MAJOR`，向后兼容的功能递增 `MINOR`，向后兼容的修复递增 `PATCH`。
- 尚未发布的工作记录在路线图、提交和 Pull Request 中；需要面向用户维护变更日志时，在首次可分发版本前建立，不提前维护空壳日志。
- 发布必须来自可追溯提交。版本号、标签、锁文件和发布产物中的版本信息必须一致；预发布使用 `-alpha.N`、`-beta.N` 或 `-rc.N` 标识。

## 分支与提交规则

- `main` 保存已验证、可继续开发的状态。功能和修复在短生命周期分支完成；分支名前缀使用 `feat/`、`fix/`、`docs/`、`chore/` 或当前协作工具要求的等价前缀。
- 提交遵循 Conventional Commits：`<type>(<optional-scope>): <summary>`。
- 常用类型为 `feat`、`fix`、`docs`、`refactor`、`test`、`build`、`ci`、`chore` 和 `revert`。破坏性变化使用 `!` 并在正文写明迁移影响。
- 摘要使用简短祈使句，中文或英文均可；同一 Pull Request 内保持一致。正文记录必要的理由与权衡，不逐行复述差异。
- 一个提交只表达一个可审查意图。不要混入无关格式化、依赖升级、生成物或用户本地修改。
- 提交前至少检查暂存差异和敏感信息，并运行与风险相称且仓库实际存在的验证命令。没有通过的检查必须在交付说明中明确列出。

示例：

```text
docs(process): define engineering conventions
feat(chat): stream assistant responses
fix(storage): preserve thread order after restart
```

## 评审与合并

- 评审首先检查用户价值、正确性、数据与权限安全、架构边界和回归风险，其次才是风格偏好。
- Pull Request 说明应包含变更范围、非目标、验证结果，以及仍待决定或需要后续处理的事项。
- 不通过降低类型、测试或安全约束来让检查变绿。紧急修复可以缩小验证范围，但必须明确风险和补验计划。
- 只有实际完成且通过适当验证的事项才在路线图中标记完成。
