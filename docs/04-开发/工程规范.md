# 工程规范

本文定义言奏共同遵守的代码、文档、版本和提交规则。P1 已锁定类型检查、构建与测试入口；格式化、Lint 和发布自动化在对应需求明确后独立选择，工具尚未落地不影响以下规则生效。

## 任务闭环

每项变更开始前说明：

- 用户价值：变更解决什么实际问题。
- 范围：本次会修改哪些系统边界或交付物。
- 非目标：哪些相邻问题明确留待后续处理。
- 验收条件：用什么可观察结果判断完成。

实现时只修改完成任务所需的范围。提交前检查差异，并按变更风险运行当前仓库已经提供的格式、类型、测试、构建或实际交互检查。仓库尚未提供的命令不得在文档或交付说明中声称已经通过。

## 代码规则

### TypeScript

- 新增 TypeScript 工程必须启用严格类型检查；不得用全局关闭严格模式来绕过局部问题。
- 对外部输入、持久化数据、跨进程消息和工具参数进行运行时校验；TypeScript 类型不能替代边界校验。
- 共享契约保持单一来源，由调用方复用或推导类型，不在 renderer、preload、main process 和可选 Worker 间手工维护重复结构。
- 外部框架已有公开类型、消息格式、编码器或 adapter 时直接复用，不为“解耦”复制一套同构接口。必要转换只能出现在明确边界中，并集中在一个可测试 adapter 内。
- 不为尚不存在的数据迁移或多版本运行需求提前编写兼容层。真实兼容需求出现时，记录来源版本、目标版本、淘汰条件和回归测试。
- 优先使用显式、可组合的函数和数据结构；只有存在稳定的领域不变量时才增加抽象层。
- `any`、非空断言和类型强制转换只用于已经验证但类型系统无法表达的边界，并在邻近位置说明原因。

### 模块与安全边界

- 角色、记忆、语音、VRM 和桌面能力通过明确接口连接，不把供应商细节泄漏到产品领域模型。
- 密钥、文件系统、数据库和高权限工具留在受信任边界；不将真实凭据、个人数据或本地绝对路径写入源码、测试夹具和日志。
- TTS 与 ASR 保持独立 Capability；工具调用和消息流沿用 AI SDK、assistant-ui 或已选协议，不建立重复的通用 Runtime。
- 新依赖必须解决明确问题，记录采用理由，并提交对应锁文件；依赖升级不得顺带混入普通功能变更。

### 命名与文件组织

- 代码标识符与文件名使用英文；产品文案和项目文档以中文为主，保留必要的英文术语与官方名称。
- React 组件使用 `PascalCase`，普通变量与函数使用 `camelCase`，常量仅在确为固定值时使用 `UPPER_SNAKE_CASE`。
- 测试靠近被测模块或放入该模块约定的测试目录；同一子项目内保持一种方式。
- 不创建含义宽泛的 `utils`、`helpers` 或 `common` 聚合层；文件和模块名称应表达所属领域与职责。

### Renderer UI

- UI 基线以 [D-021](../01-决策/决策记录.md#d-021--assistant-ui-与-shadcn-ui-边界) 为准：聊天使用 assistant-ui Registry，通用控件使用 shadcn `base-nova`、`neutral` 默认配置。
- 不创建基础组件包装层、产品级颜色系统或平行视觉 token。真实产品差异先在使用点通过 `className` 表达，必要时再最小修改 Registry 源码。
- 常规图标使用 Lucide；表情与鼠标操作沿用仓库内标明来源的 Tabler、Phosphor SVG。图标按钮必须具有可访问名称；Tooltip、焦点、禁用和加载状态优先使用 shadcn 现成能力。
- assistant-ui 官方 Thread 的 `components` 覆盖接口可以使用；被弃用的是 Primitive 迭代器旧式 `components` prop。直接使用 primitives 的新代码应采用 children render function、`MessagePrimitive.Parts` 或 `GroupedParts`，不使用 `MessagePrimitive.Content` 或 Primitive `.If`。

### 自动化工具

- 格式化、Lint、类型检查和测试命令一旦在 P1 锁定，应通过根级脚本提供统一入口，并可在 Windows 开发环境和 CI 中非交互运行。
- 自动生成文件应标明来源并通过命令可复现；除非构建或分发确实需要，不提交构建产物。
- 不用自动格式化或批量重写掩盖无关差异。
- 测试优先覆盖数据保持、安全边界、状态切换与失败恢复。同一行为优先在实际业务路径验证，避免再用简单包装函数或纯框架示例重复覆盖；可逆的文案、样式调整不单独增加测试，也不通过源码字符串断言锁定实现。涉及卸载数据保护等无法在普通测试中安全执行的逻辑，可保留必要的静态检查。

- `npm run test:ai:google-tts`：显式读取 `KATARUNE_TEST_GOOGLE_API_KEY` 并验证 Google Gemini TTS、模型默认 `Kore`、WAV 与缓存链路；可能产生费用，不进入普通测试或 CI。
- `npm run test:ai:fish-audio-tts`：显式读取 `KATARUNE_TEST_FISH_AUDIO_API_KEY` 与 `KATARUNE_TEST_FISH_AUDIO_VOICE_ID`，使用免费开发层模型验证 Fish Audio、WAV 与缓存链路；不进入普通测试或 CI，免费层政策变化时仍可能产生费用或调用失败。

### 已知本地数据库迁移历史

附件迁移 `0014_futuristic_arclight` 曾以时间戳 `1785685134232` 在本地执行，合并后 journal 使用 `1785688523544`，SQL 内容未变。启动时仅对这组已知时间戳及 SHA-256 匹配的最后一条迁移记录校正时间戳，再交给 Drizzle 执行后续迁移；不以“表已存在”推定迁移完成，不修改附件类型或业务数据。未知历史仍报错，禁止通过删库或给建表语句统一添加 `IF NOT EXISTS` 掩盖冲突。此修复在停止支持该开发历史时才可移除；`test:database` 覆盖数据保持、连续重启和未知哈希拒绝。

共享 IPC 契约位于 `src/shared/ipc.ts`。Schema 是运行时结构与 TypeScript 类型的单一来源；main process 产生跨进程数据时校验，preload 在暴露给 renderer 前再次校验。新增 channel 必须同时增加 Schema、推导类型和有效/无效输入测试。

## 语音与 uLipSync 开发验收

普通 `SpeechModelV4.doGenerate()` 和连接测试保持原样。需要时间戳的调用经 `resolveSpeechModel().generateWithTimestamps`，由语音服务选择能力；不在聊天或 Unity 内判断供应商品牌。Fish WAV 流接收完毕后才交付，缓存目录 `tts-cache/timestamped-v1` 中每个 JSON 原子保存音频、内容哈希和片段，普通缓存不迁移。时间戳数值和顺序统一由 Electron 在供应商响应解析、缓存读取边界校验，允许开始与结束时间相等；音频完整后校验结束时间不超出音频时长。文本对齐和 Unity 字幕分页不重复校验时间数值，Unity 只核对片段文字与当前全文或流式前缀的对应关系。

音色 Profile 使用上游原生 JSON，保存到应用 userData 的 `speech-profiles/<voiceKey>.json`。`voiceKey` 为 UTF-8 `JSON.stringify([providerConfig.id, modelConfig.modelId, character.speechVoice])` 的 SHA-256 小写十六进制。三个值对应供应商配置实例、实际模型 ID、实际 Voice ID，不能用显示名称代替。缺失或无效文件使用默认示例，Player 日志明确记录 `source=default-example`；它不代表已校准。

开发校准步骤：

1. 使用真实音色录制或合成 A/I/U/E/O，以及呼吸、噪声样本。导入本地忽略目录 `Assets/KataruneLocal/SpeechCalibration`，音频使用 Decompress On Load。

## 版本规则

- 项目发布版本遵循语义化版本 `MAJOR.MINOR.PATCH`，Git 标签使用 `vMAJOR.MINOR.PATCH`。
- 在首个稳定公开版本前使用 `0.y.z`：兼容范围扩大或形成新的可验证里程碑递增 `MINOR`，向后兼容的修复递增 `PATCH`。
- 进入 `1.0.0` 后，不兼容的公开契约或用户数据格式变化递增 `MAJOR`，向后兼容的功能递增 `MINOR`，向后兼容的修复递增 `PATCH`。

- 发布必须来自可追溯提交。版本号、标签、锁文件和发布产物中的版本信息必须一致；预发布使用 `-alpha.N`、`-beta.N` 或 `-rc.N` 标识。

## Unity 编辑器动态程序集排错（2026-09-27）

本机 Unity 6000.3.11f1、Pipeline 0.8.0-exp.1、Windows 中文工程路径下，执行 CLI `eval` 后，动态生成的 `PipelineEval_*` 程序集在 `Assembly.GetName()` → `GetCodeBase()` 处抛出 `ExecutionEngineException: String conversion error: Illegal byte sequence encounted in the input.`。Unity 内置 QuickInstaller 的更新回调扫描这些程序集后会连续刷错，并影响其他主线程命令。这不是 C# 编译错误；也没有证明单独降级 Pipeline 就能解决。

现场验证：正常脚本域重载后逐程序集检查无失败；再次执行 `eval` 后，两份新生成的 `PipelineEval_*` 均可复现异常。恢复方式是保存当前场景，通过正常脚本重编译/域重载或重启 Editor 卸载动态程序集，再清理历史 Console 条目并观察新增错误。不要通过修改 PackageCache、屏蔽 QuickInstaller 或更改全局系统编码处理。

当前规避：此环境禁用 `eval` / `eval_file`，使用原生已注册命令；复杂操作放入正常编译的 Editor 脚本。截图优先使用 `capture_game_view` 的 `source=screen`，避免为了捕获 UI 临时执行 `ScreenCapture`。测试前保存未命名场景，防止保存对话框阻塞 CLI。此规避并非 Unity/Mono 上游缺陷修复，升级相关版本后需重新验证。

恢复验证：189 项 EditMode 通过；PlayMode 11 项通过、3 项因本地动作资产或测试模型未配置而跳过、0 失败。退出播放后 Editor Console 错误数为 0，无编译失败；先前测试超时不能再当作项目测试失败的证据。
